# T3.23 — Le `pyproject.toml` devient la source unique des dépendances Python, et `configure` teste l'API

> Numéro : T3.21 était pris (extrait `del_param` de T3.20), T3.22 par la surveillance pip.
> **T3.23 est le premier libre.**
>
> Corrige **F-DEP-1**. Prérequis de fond de **T3.22**. Composable avec la branche
> `chore/dependabot-2026-08-24` (aucun fichier en commun).

## Le défaut

Le sidecar MCP de l'image publiée **ne démarrait pas**. Reproduit sur
`ghcr.io/calaos/calaos_base:dev` (digest `sha256:75485fc6…71df2`) :

```
/opt/bin/calaos_mcp --help
  → /opt/lib/calaos/calaos_mcp/server.py:25  from mcp.server.fastmcp import FastMCP
  → ModuleNotFoundError: No module named 'mcp.server.fastmcp'
```

Versions mesurées dans cette image : **`mcp 2.0.0`**, `fastapi 0.141.1`, `starlette 1.6.0`,
`uvicorn 0.52.4`. Dans `mcp 2.0.0` le module `mcp.server.fastmcp` a disparu.

**Cause racine.** `Dockerfile:38` (stage `dev`) et `Dockerfile:69` (stage `runner`) faisaient :

```
RUN pip install "mcp[cli]" uvicorn fastapi websockets --break-system-packages
```

Sans **aucune** borne de version. Chaque reconstruction attrapait ce que PyPI servait ce jour-là.
`src/bin/calaos_mcp/pyproject.toml` — le fichier que Dependabot surveille, celui qui porte en tête
« *All runtime dependencies pinned […] no floating versions* » — **n'était lu par aucun chemin de
build**. Les pins étaient de la documentation, pas un contrat.

**Et le garde-fou ne voyait rien.** `configure.ac:220` testait `import mcp, uvicorn, fastapi`, ce
qui **passe** avec `mcp 2.0.0` : le paquet existe, c'est le sous-module qui manque. Vérifié
côte à côte sur l'image cassée :

| sonde | image `mcp 2.0.0` |
|---|---|
| `import mcp, uvicorn, fastapi` (ancienne) | **exit 0** — le mensonge |
| `from mcp.server.fastmcp import FastMCP` (nouvelle) | **ModuleNotFoundError** |

Un `configure` qui passe alors que le binaire ne démarrera pas est pire qu'absent : il rassure.

## Le correctif

### 1. Une source unique de vérité — le manifeste, pas un second jeu de pins

Épingler des numéros **dans le `Dockerfile`** aurait créé un deuxième endroit à maintenir, qui
aurait divergé à son tour. Le build lit donc désormais le `pyproject.toml`.

`pip install ./src/bin/calaos_mcp` a été écarté : cela installerait aussi le **paquet**
`calaos_mcp` dans `site-packages`, en doublon du `/opt/lib/calaos/calaos_mcp` que
`Makefile.am` installe et que le wrapper `calaos_mcp.in` met dans `PYTHONPATH` — deux copies du
même code, dont une jamais mise à jour.

Retenu : **`scripts/pyproject-requirements.py`**, qui lit `[project].dependencies` via `tomllib`
(stdlib, python ≥ 3.11 — ce que `requires-python` exige déjà) et l'émet en liste requirements.
Les deux stages du `Dockerfile`, le `.devcontainer/Dockerfile` et la CI copient **le même
manifeste** et appellent **le même script**. Rien à synchroniser : il n'y a plus qu'un endroit.

Seul le `pyproject.toml` est copié dans le stage — pas l'arbre — pour que la couche pip ne soit
invalidée que quand les dépendances changent. Aucun outillage de build n'est ajouté au stage
runtime : il avait déjà `python3-pip`, il n'a rien de plus.

### 2. Une seule passe de résolveur, pour tout

`mcp`, `fastapi` et `starlette` sont **couplés** (`fastapi 0.115.12` exige
`starlette>=0.40.0,<0.47.0` ; c'est ce couplage qui a rendu la PR Dependabot #175 irrésoluble).
Installer paquet par paquet laisse une passe ultérieure écraser silencieusement ce qu'une passe
antérieure avait épinglé. Le build fait donc **un seul** `pip install` :

```
pip install --no-cache-dir --break-system-packages -r requirements.txt roonapi reolink-aio
```

**`roonapi` et `reolink-aio`** ne sont **pas** dans le `pyproject.toml`, et n'y entrent pas : ce
sont des intégrations optionnelles de `calaos_server` (extern procs), pas des dépendances du
sidecar. Elles restent **non pinnées, comme avant** — mais elles partagent maintenant la passe de
résolution. Conséquence voulue : si l'une d'elles devient incompatible avec le jeu épinglé, le
**build échoue bruyamment** au lieu de publier une image où l'une des deux a été dégradée en
silence. Mesuré après correctif : `roonapi 0.1.6`, `reolink-aio 0.21.11`, `configure` les détecte
toutes les deux.

### 3. Un garde-fou qui teste l'API, pas la présence

`configure.ac` importe désormais **exactement** ce que le sidecar importe, relevé sur les sources
(`src/bin/calaos_mcp/python/calaos_mcp/*.py`) et non listé de mémoire :

```
from mcp.server.fastmcp import FastMCP
from mcp.server.transport_security import TransportSecuritySettings
from fastapi import FastAPI, Request, Response
from fastapi.responses import JSONResponse
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.routing import Route
from pydantic import BaseModel, Field
import uvicorn, websockets
FastMCP.streamable_http_app
```

Cela ajoute **cinq** distributions que l'ancienne sonde ignorait : `starlette`, `pydantic`, et
surtout **`websockets`** — importé par `client.py:16`, installé par la même ligne `pip`, et jamais
sondé (signalé par l'agent E4.5d pendant la réécriture de `docs/15_mcp_server.md`). Les six
distributions sondées sont **toutes** déclarées dans le `pyproject.toml` : le passage à la source
unique n'en fait disparaître aucune de l'image — vérifié, pas déduit.

Et la sonde **ne s'arrête pas aux imports** : `server.py` atteint `FastMCP` par trois attributs
qu'aucun `import` ne révélerait, dont un **privé**. La sonde **rejoue la séquence** :

| exercé | source | pourquoi |
|---|---|---|
| `mcp.settings.transport_security = …` | `server.py:64` | affectation au niveau module |
| `mcp.streamable_http_app()` | `server.py:167` | construit l'app ASGI |
| `mcp._session_manager` | `server.py:171` | **API privée** — exactement le genre de symbole qui disparaît sans préavis, comme vient de le faire `mcp.server.fastmcp` |

`pydantic` a été **retiré** de la sonde : le seul module qui l'importe, `models.py`, **n'est
importé par personne** (code mort, versé en FINDINGS). Il reste épinglé dans le `pyproject.toml`
comme transitive de `mcp`/`fastapi`, et une `pydantic` manquante ferait de toute façon échouer
l'import de `fastapi` juste au-dessus.

En cas d'échec, `configure` **imprime la trace d'import** au lieu de dire seulement « no ».

### 4. Un job CI qui voit enfin le sidecar

> ⚠️ **Ce ticket améliore la détection, pas le blocage.** `docker-publish-dev.yml` est un workflow
> **séparé**, déclenché sur tout push vers `master`, **sans `needs:`** — et `master` n'est pas
> protégée, donc aucun *required status check*. Un job CI rouge **n'empêche pas** la publication
> de l'image.
>
> ⛔ **CORRECTION (2026-08-25, décision utilisateur — `DECISIONS.md`, « DEUX canaux de
> publication »).** ~~Ce paragraphe se terminait par « Rendre `mcp-sidecar-deps` bloquant est une
> décision de configuration du dépôt (protection de branche + status check requis) », c'est-à-dire
> par une **recommandation implicite de protéger `master`**.~~ **Elle est retirée.** `master` est
> le **canal de préversion** — c'est par lui qu'on produit les `:dev` et les `.deb` de préversion,
> que seuls l'utilisateur et les développeurs consomment ; les **releases** sont ce qui atteint
> tout le monde. **Protéger `master` empêcherait son usage prévu.** ⇒ l'image `:dev` cassée par
> F-DEP-1 était **une préversion cassée sur le canal fait pour ça**, pas un artefact livré : la
> **gravité tombe**, le correctif ci-dessous reste juste, sa **justification** change.

`build-and-test` n'installe aucune dépendance Python : `HAVE_PYTHON_MCP` y vaut « no » et le
sidecar est entièrement sauté. C'est ainsi que les PR Dependabot pip passaient vertes sans rien
dire (F-DEP-2). Le job **`mcp-sidecar-deps`** installe ce que le `pyproject.toml` déclare — même
fichier, même script, même passe unique que le `Dockerfile` — puis importe l'API réelle **et**
exerce `FastMCP.streamable_http_app()` + `_session_manager`, l'API **privée** dont dépend
`server.py:167-169` et que rien en amont ne promet.

### 5. `calaos_mcp --help`

L'entrée n'acceptait aucun argument : `--help` tombait dans « CALAOS_MCP_SOCKET is required »
(exit 2). Ajout de `--help` / `--version`, traités dans `main()` — donc **après** les imports de
module. C'est délibéré : `calaos_mcp --help` traverse toute la chaîne d'import (mcp, fastapi,
starlette, pydantic, uvicorn, websockets) sans socket, sans config et sans effet de bord. C'est la
commande d'une ligne qui répond à « est-ce que le binaire de cette image peut démarrer ».

### 6. Distribution

`pyproject.toml` entre dans l'`EXTRA_DIST` de `src/bin/calaos_mcp/Makefile.am` (il n'y était pas,
noté par F-DEP-1) et `scripts/pyproject-requirements.py` dans celui de la racine.

## Reste ouvert

- **✅ Le `.deb` : vérifié, rien à faire.** `calaos/pkgdebs` a été lu (via `gh`) pendant la revue.
  Chaîne complète : `docker-publish-dev.yml` → `repository_dispatch build_deb` (`image_src`) →
  `build_deb.yml` → un `Makefile` dont **tout** le `build` écrit **deux lignes** dans
  `container.source`. **Le `.deb` n'embarque ni l'image ni le moindre `site-packages`** : c'est un
  wrapper podman (`ExecStart=/usr/bin/podman run --pull=never ${IMAGE_SRC}`, image tirée au
  `postinst`). **Corriger le `Dockerfile` suffit ; aucune action côté `pkgdebs`.** Seul le contenu
  de `pull_calaos_image` reste non lu.
- **F-DEP-2 reste ouvert.** `mcp-sidecar-deps` garde le jeu de dépendances et l'API ; il ne
  construit pas `create_app()` et ne frappe pas `/healthz`. Cela a été fait **à la main** ici (et
  par le passage Dependabot), pas en CI. La suite `tests/python/test_mcp_server.py` de F-DEP-2
  reste à écrire.
- **`pydantic-settings 2.15.0`**, transitive non pinnée de `mcp`, émet à chaque démarrage un
  `IncompleteFieldDefinitionWarning` sur le champ `lifespan`. Cosmétique (le sidecar fonctionne),
  mais c'est la **même classe de défaut** : une transitive flottante dans un jeu qui se veut
  épinglé. Non traité ici pour garder la branche disjointe du `pyproject.toml`.
