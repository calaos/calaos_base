## Pourquoi un seul ticket
La tentative de faire le sweep de signatures seul s'est arrêtée avant toute modification :
- `Room::Load/SaveToXml` n'est appelé que depuis `CalaosConfig.cpp:294,320` ; `Rule::Load/SaveToXml`
  que depuis `CalaosConfig.cpp:383,409`.
- Les virtuelles `IOBase.h:141-142` sont surchargées par `IO/InPlageHoraire.h:100-101` et
  `IO/RemoteUI/RemoteUI.h:59-60`.
- `IOFactory::CreateIO` appelle `io->LoadFromXml(node)` (même virtuelle) ; `IntValue`, `IPCam`,
  `AudioPlayer`, `AVReceiver` surchargent aussi ; `RulesFactory` et les 9 Action/Condition sont
  atteints depuis `Rule.cpp`.
Retyper la base entraîne donc mécaniquement le cœur. **Seul `src/lib/ConfigStore.cpp` est
réellement indépendant** et peut rester une tranche séparée (E4.4d-bis) si besoin.

## 🚨 ÉTAPE 0 OBLIGATOIRE — poser `override` AVANT de toucher aux types
`IO/InPlageHoraire.h:100-101` déclare `LoadFromXml`/`SaveToXml` **sans `override`**. Si on
retype le paramètre de la base sans corriger ça d'abord, **le code compile sans un warning**,
les deux méthodes cessent d'être des surcharges, et **chaque IO de plage horaire se charge vide
puis se réenregistre vide** → perte silencieuse de toutes les plages à la première sauvegarde.

Donc, en **premier commit séparé, sans aucun changement de type** : ajouter `override` sur
**toutes** les surcharges de `LoadFromXml`/`SaveToXml` de l'arbre (`InPlageHoraire`, `RemoteUI`,
`IntValue`, `IPCam`, `AudioPlayer`, `AVReceiver`, `Room`, `Rule`, Actions, Conditions…), et
vérifier que ça compile. À partir de là **le compilateur devient le filet** : toute signature
oubliée pendant le sweep devient une erreur au lieu d'un silence.

### Le site à paramètre de sortie (unique dans tout l'arbre)
`CalaosConfig.cpp:289` : `room_node->Attribute("hits", &hits)`, déjà gardé par
`if (room_node->Attribute("hits"))` en :288. Portage fidèle :
```cpp
pugi::xml_attribute a = room_node.attribute("hits");
int hits = a ? a.as_int(0) : 0;
```
`if (a)` préserve le cas **absent** ; `as_int(0)` ne reproduit le « laisse inchangé si invalide »
de TinyXML que parce que la cible vaut 0 au départ — présent-mais-vide et présent-mais-invalide
doivent continuer d'atterrir sur 0.
