# T2.15 — JsonApi : UAF/leak audio-player dans buildJsonState + token RemoteUI constant-time

**Type** : fix (sec)
**Phase** : 2

## Contexte

**Item 1 — UAF + leak (FINDINGS wave 4, transverse).** `JsonApi::buildJsonState`
(`JsonApi.cpp:421-537`) construit l'état des audio-players via 6 callbacks asynchrones
imbriqués (`get_playlist_current` → `get_volume` → … → `get_songinfo`) qui capturent par
`[=]` des **pointeurs bruts** : `this`, `jio`, `jplayer`, `player`. Si le client WS se
déconnecte ou si l'`AudioPlayer` est détruit pendant qu'une réponse squeezebox est en vol,
les callbacks écrivent dans de la mémoire libérée (UAF classique, même classe que les
dangling-this de T1.18/T2.1). En plus, `JsonApi.cpp:515` utilise `json_object_set` (et non
`_new`) sur `jplayer` → refcount jamais rendu, **fuite** à chaque état construit. Ce pattern
concerne tous les handlers WS qui passent par `buildJsonState`.

**Item 2 — canal auxiliaire temporel (FINDINGS « Sécurité », même classe que F2).**
`RemoteUIManager::getRemoteUIByToken` (`RemoteUIManager.cpp:80-101`) compare `auth_token`
avec `string ==` (`io->get_param("auth_token") == token`) — timing side-channel sur le token
lui-même (pas le MAC, déjà couvert par T1.6). `JsonApi::secureCompare` (`JsonApi.h:103`,
`JsonApi.cpp:111`) existe et se réutilise tel quel. Appelants :
`HMACAuthenticator.cpp:90,137`, `RemoteUIManager.cpp:205`.

**Pourquoi un seul ticket** : les deux items sont petits, adjacents JsonApi/RemoteUI, de même
nature (durcissement post-T1.4/T1.6), et leurs fichiers (`JsonApi.cpp` vs
`RemoteUIManager.cpp`) sont disjoints entre eux — pas de raison de payer deux overheads de
ticket. Attention en revanche : **T2.18 touche aussi `JsonApi.cpp`** → ne jamais scheduler
T2.15 et T2.18 dans la même wave.

## Travail

Fichiers : `src/bin/calaos_server/JsonApi.{cpp,h}`,
`src/bin/calaos_server/RemoteUI/RemoteUIManager.cpp`.

1. Alive-token sur la chaîne de callbacks audio : `shared_ptr<bool>` (pattern déjà en place
   dans `Timer.h`, `ActionPush.h`, `RemoteUIWebSocketHandler.h`) capturé par valeur ; chaque
   callback vérifie le token avant de toucher `this`/`jio`/`jplayer`. Alternative acceptable :
   porter le JSON en construction par `shared_ptr` + capturer un weak handle sur la session.
   Couvrir aussi la survie de `player` (IO supprimable via l'API pendant le vol).
2. `JsonApi.cpp:515` : `json_object_set` → `json_object_set_new` (ou `json_decref` explicite)
   — plus aucune référence perdue sur `jplayer`.
3. Balayer `buildJsonState`/`buildJsonStates` pour les autres `json_object_set` sans `_new`
   et les captures `[=]` du même pattern.
4. `getRemoteUIByToken` : remplacer `==` par `JsonApi::secureCompare(io->get_param("auth_token"),
   token)` ; garder le comportement « premier match » inchangé.
5. Tests : reproduire l'UAF sous ASan (client détruit avant retour du callback audio, pattern
   des tests T2.1/T1.18) ; test unitaire simple sur le chemin token (bon/mauvais token).

## Acceptation

- Build docker + `make check` verts, ASan clean sur le scénario « déconnexion pendant
  get_playlist_current en vol ».
- Plus de `json_object_set(` sans `_new` dans le chemin audio de `buildJsonState`.
- `getRemoteUIByToken` ne contient plus de `==` sur `auth_token` (grep).
