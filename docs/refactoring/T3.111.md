# T3.111 — la liste des huit vient d'une table de dispatch, pas d'une décision

> **État : 📋 OUVERTE.** Ouverte par [`T3.60`](T3.60.md) (2026-09-06), qui a déplacé la garde sans
> toucher un seul de ses membres — délibérément : changer la portée **et** sa liste dans le même
> ticket aurait mêlé un déplacement mesurable à un arbitrage de produit.
> **Aucune ligne de `src/` n'a été écrite.**

## Le défaut

`JsonApi::serviceScopeDeniedCommands()` porte exactement les huit commandes que
`JsonApiHandlerWS` gardait : `set_param`, `del_param`, `audio_db`, `set_timerange`, `autoscenario`,
`eventlog`, `register_push`, `settings`. Cette liste **n'a jamais été dérivée de la question « que
peut faire une session de service »** ; elle a été composée à partir de la table de dispatch d'un
transport, et elle en porte les trous.

⭐ **Le trou qui compte est `config`.** `type=get` rend `io.xml`, `rules.xml` et
`local_config.xml` **en clair** ; `type=put` les **réécrit**. La commande n'est pas dans les huit
pour une seule raison : son code est **commenté** dans `JsonApiHandlerWS::processApi()`. Depuis
[`T3.60`](T3.60.md) la garde suit la session, donc une session de service ouverte un jour sur le
transport HTTP se verrait refuser un `set_param` sur **un** paramètre et autoriser le téléversement
de `local_config.xml` **entier** — le fichier où vit le jeton de service lui-même.

`get_mcp_info` est le second cas : elle rend le **jeton porteur** du proxy MCP, et elle non plus
n'est pas dans la liste.

## Ce qui n'est pas en cause

⛔ **Rien n'est exploitable aujourd'hui** : aucune session HTTP ne peut être en portée de service,
mesuré maillon par maillon dans [`T3.60.md`](T3.60.md) §1. C'est un trou **par construction** dans
la liste, qui s'ouvrira le jour où la portée deviendra atteignable sur un autre transport.

## Ce qui reste à faire

**Une décision de produit avant une ligne de code** : une session de service a-t-elle le droit de
**lire** la configuration ? de l'**écrire** ? de lire le jeton du proxy ? Les trois réponses ne sont
pas forcément les mêmes, et l'arbitrage antérieur sur `autoscenario` (refus au **message**, jamais à
la sous-commande — [`DECISIONS.md`](DECISIONS.md), E4.6e) dit qu'inventer une grammaire par
sous-commande n'est pas la voie : `config` se refuserait donc **en entier** ou pas du tout.

⚠️ **Et la liste doit cesser d'être un miroir de dispatch** : quel qu'en soit le résultat, la fiche
qui la fixe doit écrire **pourquoi** chaque commande y est, sans quoi le prochain transport ajoutera
un verbe et la liste redeviendra fausse en silence.
