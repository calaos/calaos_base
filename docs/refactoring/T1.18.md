# T1.18 — ActionMail/ActionPush dangling-this

| Phase | Type | Depends on | Status |
|---|---|---|---|
| 1 | fix | Phase 0 | 📋 Backlog |

## Owned files
- `src/bin/calaos_server/Rules/ActionMail.{cpp,h}`
- `src/bin/calaos_server/Rules/ActionPush.{cpp,h}`

## Findings

### Major — lifetime: camera-download completion callback captures `this` with no guard
`ActionMail.cpp:59` — `dl->m_signalComplete.connect([this](int status){ … this->sendMail(); }); … dl->httpGet(…);`. The `Action` base (`Action.h`) is **not** `sigc::trackable`, and `UrlDownloader` completes asynchronously (self-deleting via `Idler`). If the action/rule is destroyed (config reload, IO deletion) while the download is in flight, the completion callback dereferences freed `this` → **UAF**. `ActionPush.cpp:78-84` has the identical pattern (`this->sendNotif()`). **Fix:** make `Action` `sigc::trackable` (or capture a shared/weak lifetime token) so the callback is severed when the action is destroyed.

### Minor — correctness: HTTP success check uses `status < 20` (typo for 200), duplicated
`ActionMail.cpp:61` — `if (status < 20 || status >= 300) mail_attachment_tfile.clear();`; the lower bound is a copy-paste typo (should be `200`), and the same appears in `ActionPush.cpp:80`. The whole camera-download block is duplicated across the two actions. **Fix:** use `200` as the lower bound and factor the shared camera-download logic into one helper.

## Acceptance
- Destroying an action/rule mid camera-download does not crash (ASan) — the callback is a no-op.
- The 2xx success band is `[200,300)`; the camera-download logic exists in one place.

## Verification
`make check`; ASan on "start an ActionMail/ActionPush with an attachment download, then delete the rule before completion" → no UAF; unit test that a 1xx response is not treated as success.
