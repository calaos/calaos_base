## Constats

### F9 — majeur : buffering non borné (DoS pré-auth)
- Pas de limite de corps HTTP : `_parser_body_complete` (`HttpClient.cpp:124-131`) accumule tout le corps dans `bodymessage` avant tout handler. Un gros POST épuise la mémoire **avant auth**. (Le check 1 Mo de RemoteUI `RemoteUIProvisioningHandler.cpp:94` s'exécute *après* buffering complet.)
- Cap message WS `MAX_MESSAGE_SIZE_IN_BYTES = INT_MAX-1` (`WebSocket.cpp:36`) et frame `MAX_FRAME_SIZE_IN_BYTES = INT_MAX-1` (`WebSocketFrame.cpp:23`) → ~2 Go accumulables, quasi non borné pour un petit équipement.
- Aucun cap de connexions ni timeout idle/header dans `HttpServer::addConnection` ; le keep-alive WS ne démarre qu'après handshake (`WebSocket.cpp:201`) → slowloris (client muet gardé indéfiniment).

**Remédiation** : limites de taille corps/message/frame réalistes ; cap de connexions concurrentes ; timeout de lecture header/idle.

### F10 — mineur (logique) : dispatch d'une frame en violation de protocole
`WebSocket::processFrame` (`:454-490`) : les 3 branches de violation (continuation sans début, non-continuation en cours de fragmentation, message trop grand) appellent `reset()` + `sendCloseFrame(...)` mais **sans `return`/`continue`** → exécution tombe sur `currentData.append(...)` (`:490`) et peut quand même dispatcher.
**Remédiation** : sortie anticipée après chaque violation.

### F12 — majeur/mineur : cycle de vie `McpProxyHandler`
`WebSocket.cpp:121` : `mcpProxy = new McpProxyHandler(client_conn, buffered)` partage le `client_conn` du `HttpClient` ; `teardown()` (`McpProxyHandler.cpp:291-306`) ferme `client->close()` puis le proxy est `delete` **synchrone** depuis `~WebSocket` (`WebSocket.cpp:55`). Les callbacks uvw (`connectToSidecar`, `:215-234`) capturent `this` brut ; close uvw async → un `DataEvent`/`ErrorEvent` tardif après delete = UAF. Le flag `closed` ne protège pas les callbacks à `this` brut.
**Remédiation** : détacher les callbacks avant delete, ou lifetime `shared_ptr`/`weak_ptr`.

## Acceptance
- POST géant → rejeté sans OOM (limite configurable).
- Frame WS > cap → rejetée proprement, connexion fermée.
- Client muet → fermé sur timeout.
- Frame en violation → non dispatchée (F10).
- Fermeture `/mcp` en cours de trafic sidecar → pas de UAF (ASan).
