# T3.41 — `getClientIp()` ne regarde pas la famille d'adresse : un pair IPv6 est lu `"0.0.0.0"`

**Statut** : 📋 · **Type** : fix · **Phase** : 3 · **Effort : petit, mais le test coûte plus que le correctif**
**Dépend de** : rien (défaut **préexistant**, antérieur à T3.39)
**Origine** : revue de [T3.39](T3.39.md), réserve 3. Consigné en **F-IP6-1** (`FINDINGS.md`).

---

## 1. Le défaut

`HttpClient::getClientIp()` (`HttpClient.cpp:700-722`) essaie `peer<uvw::IPv4>()` d'abord et le
renvoie **dès qu'il est non vide**, en gardant `peer<uvw::IPv6>()` comme repli :

```cpp
auto addr = client_conn->peer<uvw::IPv4>();
if (!addr.ip.empty())
    return addr.ip;
auto addr6 = client_conn->peer<uvw::IPv6>();      // jamais atteint
```

Or **le repli n'est jamais atteint**, parce que la première branche ne peut pas échouer. `uvw`'s
`details::address<I>()` (`src/lib/uvw/src/uvw/util.hpp:384-398`) demande le pair dans un
`sockaddr_storage` puis le **`reinterpret_cast` en `sockaddr_in` sans regarder `ss_family`** :

```cpp
int err = std::forward<F>(f)(handle, reinterpret_cast<sockaddr *>(&ssto), &len);
if(0 == err) {
    typename IpTraits<I>::Type *aptr = reinterpret_cast<typename IpTraits<I>::Type *>(&ssto);
    addr = address<I>(aptr);        // uv_ip4_name() sur un sockaddr_in6
}
```

Sur un pair IPv6, `uv_ip4_name()` lit donc `sin_addr` **là où se trouvent les quatre premiers
octets de `sin6_flowinfo`** — nuls pour une socket acceptée — et rend la chaîne `"0.0.0.0"`, qui
est **non vide** et gagne.

## 2. Mesuré, pas déduit

Programme C reproduisant **exactement** la séquence d'uvw (`getpeername` dans un `sockaddr_storage`,
puis `inet_ntop(AF_INET, …)` sur le cast), sur une connexion `::1` **réellement acceptée** :

```
real peer family      = 10 (AF_INET6)
peer<IPv6>().ip       = "::1"
sin6_flowinfo         = 0x00000000
peer<IPv4>().ip       = "0.0.0.0"   (empty? NO)
=> getClientIp() returns: "0.0.0.0"
```

## 3. Ce que ça coûte aujourd'hui

- **Sur la configuration livrée : rien.** `listen_address` vaut `"0.0.0.0"`
  (`ConfigOptions.cpp:499`, `HttpServer.cpp:29-31`), l'écoute est IPv4, **tout pair est `AF_INET`**,
  et la branche `127.` de `TransportLimits::isTrustedProxyPeer()` fonctionne.
- **Les deux branches IPv6 de la garde T3.39 sont donc du code mort.** `::1` et `::ffff:127.x` ne
  se déclenchent **jamais** en production. Elles restent en **défense en profondeur** ; la note de
  `HttpClient.h` le dit désormais explicitement, au lieu de promettre une protection qui n'opère
  pas. **C'est ce ticket qui les rendra vivantes.**
- ⚠️ **Sur `listen_address = "::"` (valeur légale d'une clé documentée) : régression de
  disponibilité.** Tout pair devient `AF_INET6`, `getClientIp()` rend `"0.0.0.0"` pour **tout le
  monde**, la garde de T3.39 refuse ce pair, l'en-tête est écarté et **toute l'installation
  retombe dans un seau unique** — le défaut T3.24, pour cette configuration-là.
  La garde **échoue en fermeture** (aucune identité n'est forgée, aucun backoff n'est esquivé) :
  c'est une régression de **disponibilité**, **pas** un trou de sécurité. Mais c'en est une contre
  master **pour cette valeur**, et elle est écrite plutôt que tue — cf. `RELEASE_NOTES.md`.

## 4. Correctif

⛔ **ATTENTION AU COÛT RÉEL — ce n'est PAS un correctif local de dix lignes.** Mesuré : **uvw
n'expose aucun accesseur public au handle brut**. `UnderlyingType::get()` est **`protected`**
(`src/lib/uvw/src/uvw/underlying_type.hpp:23-30`), il n'existe pas de `raw()`, et `HttpClient`
**détient** un `std::shared_ptr<uvw::TcpHandle>` — il n'en dérive pas, donc il ne peut pas y
accéder. ⇒ appeler `uv_tcp_getpeername()` soi-même **exige de patcher uvw vendu**
(`src/lib/uvw/`) : soit y ajouter un `raw()` public, soit — plus juste — **corriger
`details::address<I>()` pour qu'il teste `ss_family`**, ce qui bénéficierait à **tous** les
utilisateurs d'uvw de l'arbre (`UDPServer`, `PipeHandle`, `HttpServer::addConnection`…) mais
**diverge d'amont** et doit être assumé comme tel. **C'est ce qui justifie un ticket séparé plutôt
qu'un avenant à T3.39.**

⛔ **Le raccourci à NE PAS prendre** : « si `peer<IPv4>().ip` vaut `"0.0.0.0"`, essayer l'IPv6 ».
Une ligne, et **faux dès que `sin6_flowinfo` est non nul** (valeur légale) — `uv_ip4_name()` rendrait
alors un quadruplet quelconque qui n'est pas `"0.0.0.0"`, et le défaut persisterait **en silence**,
sur du code qui *aurait l'air* corrigé. Pire que de documenter.

Une fois l'accès au handle obtenu, la forme visée est : demander le pair à libuv et **router sur
`ss_family`**.

```cpp
sockaddr_storage ss;
int len = sizeof(ss);
if (uv_tcp_getpeername(client_conn->raw(), reinterpret_cast<sockaddr *>(&ss), &len) != 0)
    return "unknown";
char name[INET6_ADDRSTRLEN] = {0};
if (ss.ss_family == AF_INET6)
    { if (uv_ip6_name(reinterpret_cast<sockaddr_in6 *>(&ss), name, sizeof name) == 0) return name; }
else if (ss.ss_family == AF_INET)
    { if (uv_ip4_name(reinterpret_cast<sockaddr_in *>(&ss), name, sizeof name) == 0) return name; }
return "unknown";
```

⚠️ Formes que `uv_ip6_name()` émet réellement, et que la garde reconnaît déjà : `"::1"` et
`"::ffff:127.0.0.1"`. Les formes **non** reconnues (`0:0:0:0:0:0:0:1`, `::1%lo`, `::0001`,
`::FFFF:127.0.0.1` en majuscules, `::ffff:7f00:1`) restent en **échec fermé** assumé — `inet_ntop`
ne les produit pas.

## 5. ⛔ Le point dur : le test

Ce chemin **n'est pas atteignable par un test unitaire sans socket réelle** — c'est précisément
pourquoi `getClientIp()` a été rendu `virtual` par T3.39, pour que les tests **contournent** la
socket. Un test qui se contente de relier `HttpClient.o` ne prouve **rien** : c'est la dette
**`F-LINK-1`** (« lié » n'est pas « exercé »), et **six** déclarations de ce type sont tombées.

⇒ **Ne pas déclarer ce chemin « couvert » sans l'avoir mesuré.** La forme honnête est un test qui
**ouvre une vraie socket d'écoute `::1`**, se connecte à lui-même, et lit `getClientIp()` sur le
handle accepté — sur le modèle du programme de §2. À défaut, dire dans la fiche de livraison que
le correctif est **vérifié par mesure manuelle et non par la suite**, plutôt que de laisser croire
l'inverse.

## 6. Acceptation

1. Sur un pair `::1` réellement accepté, `getClientIp()` rend **`"::1"`** (et non `"0.0.0.0"`).
2. Sur un pair IPv4, la valeur est **inchangée** — aucune régression sur la configuration livrée.
3. Les deux branches IPv6 de `isTrustedProxyPeer()` deviennent **atteignables**, et une mutation
   qui en retire une **rougit** (elles ne rougissaient jusqu'ici que sur la fonction pure).
4. **La note « UNREACHABLE BY CONSTRUCTION » de `HttpClient.h` est supprimée**, ainsi que la
   réserve `listen_address = "::"` de `RELEASE_NOTES.md`. **F-IP6-1 fermé.**
