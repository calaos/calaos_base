# T3.142 — le tampon d'une réponse UDP peut survivre à la chaîne qui le possède

**Statut** : 📋 · **Type** : fix (**divulgation de mémoire**) · **Phase** : 3
**Origine** : lu en écrivant [T3.135](T3.135.md) ; ⛔ **MESURÉ à la revue de merge du lot 147**,
2026-09-07. **Préexistant à `T3.135`.**

---

## 1. Ce qui est lu

`uvw::UDPHandle::send(const sockaddr &, char *data, unsigned int len)`
(`src/lib/uvw/src/uvw/udp.hpp:396`) construit sa `SendReq` avec un **suppresseur qui ne fait rien** :

```cpp
std::unique_ptr<char[], details::SendReq::Deleter>{ data, [](char *) {} }
```

Le tampon n'est **ni copié ni possédé** : `uv_buf_init` pointe dessus, et libuv le lit quand la
requête est dépilée. Or `UDPServer::processRequest()` lui donne le `c_str()` d'une `string`
**locale** :

```cpp
string packet = "CALAOS_IP ";
packet += ip;
sendTo(remoteIp, remotePort, packet);   // packet meurt au retour
```

Tant que la file d'envoi du handle est vide, `uv__udp_send` appelle `uv__udp_sendmsg`
**immédiatement** et le tampon est lu avant le retour. Ce n'est plus vrai dès qu'un envoi est déjà
en attente : `send_queue_count != 0` fait mettre la requête en file, et elle est lue au tour de
boucle suivant, quand `packet` n'existe plus.

⭐ **Que la mise en file arrive réellement est mesuré** — c'est ce sur quoi repose le cas
`TwoOutstandingAnswersAreNamedInTheOrderPosted` de `core/UdpSendFailureIsolation_test` : deux
réponses postées dos à dos sont toutes les deux en attente au même moment. Ce cas garde ses tampons
en vie **exprès**, précisément parce que la production ne le fait pas.

## 2. ⛔⭐⭐ Ce qui est MESURÉ — la mémoire libérée part sur le réseau

Ce n'est plus une lecture du code. **Trois `CALAOS_DISCOVER` envoyés dos à dos** — une seule lecture
en rafale de libuv en avale jusqu'à **32**, donc les trois réponses sont postées dans le même tour
de boucle et les deux dernières partent en file :

- la **1ʳᵉ** réponse est correcte ;
- les **2ᵉ et 3ᵉ** sont **19 octets de tas libéré**, émis **au correspondant** — relevés
  `e28d1eb1ba5500004050…`, et non le `CALAOS_IP <adresse>` attendu.

⚠️ **Sans ASan** : le défaut ne demande aucun outil pour se produire, seulement pour être nommé.
⭐ **À l'identique sur `master`** ⇒ **préexistant**, [`T3.135`](T3.135.md) ne l'introduit pas et n'y
change rien : la mise en file existait déjà, `T3.135` la rend seulement observable.

⛔ **La gravité monte, et pas d'un cran de forme.** Ce n'est pas un plantage possible : c'est une
**divulgation de mémoire du serveur vers un pair du réseau local non authentifié**. Le déclencheur
est la **découverte UDP**, c'est-à-dire le seul verbe que le serveur sert **sans authentification**
— n'importe quoi sur le LAN peut le demander, et le répéter. Ce que les 19 octets contiennent
dépend de ce que l'allocateur vient de libérer ; rien ne le borne.

## 3. Ce qu'il faudra mesurer et trancher

1. ✅ **Fait** : la lecture après libération est reproduite, et son contenu part au correspondant
   (§2). Reste à la **rejouer sous ASan** pour la nommer `heap-use-after-free` dans un cas.
2. Le recensement des autres appelants du même `send(…, char *, …)` de l'arbre.
3. L'arbitrage : copier dans la surcharge `unique_ptr<char[]>` de uvw (qui, elle, possède), ou
   garder le tampon vivant côté `UDPServer` jusqu'à l'événement terminal — la file `pendingSends`
   de [`T3.135`](T3.135.md) est déjà exactement cette durée de vie.
4. ⚠️ **Le cas qui le tient doit poster TROIS réponses**, pas deux : la première part
   immédiatement, ce sont les suivantes qui sont mises en file.
