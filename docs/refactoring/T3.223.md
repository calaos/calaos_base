# T3.223 — `smtpsocket.c` écrit sans `MSG_NOSIGNAL`, et seul le `SIG_IGN` du serveur le couvre

**Statut** : 📋 · **Type** : fix (robustesse) · **Phase** : 3
**Origine** : recensement des sites d'envoi fait par [`T3.167`](T3.167.md).
**Dépend de** : —

---

## 1. Ce qui a été relevé

`src/lib/libquickmail/smtpsocket.c:94` :

```c
while (len > 0 && (l = send(sock, buf, len, 0)) < len) {
```

C'est le **dernier** des **huit** appels bruts de la famille `send` de l'arbre (hors `llhttp` vendu,
qui n'en fait aucun) sans `MSG_NOSIGNAL` : les cinq de `src/lib/tcpsocket.cpp` (`:204`, `:238`,
`:252`, `:317`, `:319` — ces deux derniers par la variable `flags`, posée en `:312` et `:314`) et
celui de `src/bin/calaos_server/IO/Wago/libmbus/mbus_sock.c:293` l'arment tous, et
`ExternProc.cpp:866` vient de l'armer.

## 2. ⚠️ Pourquoi ce n'est PAS chaud — et ⛔ pourquoi le motif d'origine était FAUX

La fiche disait : « ce code ne tourne que dans `calaos_server`, que le `signal(SIGPIPE, SIG_IGN)` de
`main.cpp:69` protège ». ⛔ **Faux.** `smtpsocket.c` n'est **compilé nulle part** : il n'apparaît que
dans `libquickmaillight_la_SOURCES` (`src/lib/libquickmail/Makefile.am:20`), et cette bibliothèque
n'est bâtie par personne — `configure.ac` ne contient **aucune** occurrence de `libquickmail`,
`src/lib/Makefile.am:1` ne liste que `calaos-python` en `SUBDIRS`, et le répertoire n'est cité qu'en
`VENDORED_DIST_TREES` (`src/lib/Makefile.am:212`), c'est-à-dire pour la distribution des sources.
Aucun `.o` n'existe dans l'arbre bâti.

L'envoi de courriel **vivant** est ailleurs : `libquickmail/quickmail.c` (`src/lib/Makefile.am:93`,
la variante **curl**), appelée par **`calaos_mail`** (`src/bin/tools/Makefile.am:43`), qui est un
**processus ENFANT** lancé par `NotifManager.cpp:106` — et qui ne contient **aucun** `SIGPIPE` : le
`SIG_IGN` du serveur ne l'aurait de toute façon jamais protégé, exactement comme `T3.167` l'a mesuré
pour les sidecars (`uv_spawn` remet toute disposition à `SIG_DFL` dans l'enfant).

⭐ **La conclusion « pas chaud » tient donc toujours, mais pour une raison plus forte** : la ligne
**ne tourne pas**. ⛔ Ce qui reste fragile est le code **vendu** que personne ne relit : le jour où
un `SUBDIRS` reprend `libquickmaillight`, le défaut arrive nu dans un processus qui n'ignore rien.

## 3. Ce qu'il faut faire

Armer le drapeau au site d'envoi, comme les sept autres. ⚠️ **À arbitrer d'abord** : un fichier que
rien ne compile se supprime peut-être plutôt qu'il ne se corrige. ⚠️ **Le cas est le point dur** : cette
bibliothèque n'est exercée par aucune suite, et un cas qui vérifierait la seule **présence** du
drapeau dans le source serait un capteur à nom connu d'avance. Ce qui se mesure est le
comportement : un pair qui cesse de lire — `shutdown(SHUT_RD)`, jamais `close()`, voir le §5.1 de
[`T3.167`](T3.167.md) pour pourquoi — et un envoi qui rend `EPIPE` au lieu de tuer, dans un
processus qui **n'ignore pas** `SIGPIPE`.

## 4. ⛔ Nu

- ⛔ **Rien n'a été joué** : le relevé est une lecture du source et des fichiers de bâtiment, pas une
  exécution. L'absence de `.o` a été vérifiée sur **cet** arbre bâti, pas sur toutes les
  configurations de `configure`.
- ⛔ **`calaos_mail` n'a pas été joué non plus** : que `libcurl` arme ou non `MSG_NOSIGNAL` pour son
  compte n'a pas été mesuré, seulement que `calaos_mail` n'installe aucun gestionnaire.
