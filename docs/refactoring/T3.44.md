## 1. Le défaut

`tests/run-python-tests.sh:50-60` (état `b7a4c63d`) :

```sh
if "$PYTHON" -m pytest --version >/dev/null 2>&1; then
    exec "$PYTHON" -m pytest -q -p no:cacheprovider "$pydir"
fi
echo "  skipping pytest-only suites (test_auth.py, test_extern_proc.py, test_logger.py)"
exec "$PYTHON" -m unittest discover -v -s "$pydir" -p 'test_t116_*.py'
```

Le motif `test_t116_*.py` ramasse **3** des **6** suites. Les trois autres disparaissent, le script
sort **0**, automake écrit **PASS** dans le `.trs`, et la seule trace est une ligne dans un `.log`
que personne ne lit.

⭐ **Le point décisif : ce n'est PAS un `SKIP` automake.** Un `SKIP` (code 77) est compté dans la
colonne **visible** `# SKIP:` du *Testsuite summary*. Ici c'est un **`PASS`**, indiscernable du
`PASS` d'une suite qui a réellement tourné.

⚠️ **Et c'est conditionnel à l'environnement.** Sur une machine qui a `pytest` **et** les modules
que les suites importent, tout tourne. Sur l'image de build, non. ⇒ **le vert ment ici et dit vrai
ailleurs**, ce qui est pire qu'un mensonge constant : **personne ne peut savoir, en lisant `89/89`,
si les tests Python ont tourné.**

## 3. Le mécanisme exact du `PASS` silencieux — **mesuré à chaque maillon**

1. `tests/Makefile.am:26` met `run-python-tests.sh` dans `TESTS` **hors** du bloc `if HAVE_GTEST`.
2. Le script teste `"$PYTHON" -m pytest --version`. Sur l'image de build :
   `/usr/bin/python3: No module named pytest`.
3. Il **retombe** sur `unittest discover -p 'test_t116_*.py'`, qui rend **0** (23 cas verts).
4. `exec` propage ce **0**. Le protocole de test simple d'automake lit **0 = PASS** et écrit
   `:test-result: PASS` dans `run-python-tests.sh.trs`.
5. Le *Testsuite summary* compte donc **1 PASS de plus** et **0 SKIP**.

⚠️ **Le suspect « `exit 0` sur `command -v pytest` absent » est presque juste et rate l'essentiel** :
il n'y a **pas** d'`exit 0` explicite. Le `0` est celui d'`unittest discover`, qui a **vraiment**
réussi — sur un sous-ensemble que personne n'a déclaré. C'est pour cela qu'aucun garde-fou de
lien, de mutation ou de code de sortie ne le voit : **tout ce qui a tourné est vert ; ce qui manque,
c'est ce qui n'a pas tourné.**

⭐ **Et une deuxième couche, que le finding ne voyait pas** : installer `pytest` **ne suffirait
pas**. `test_auth.py` fait `pytest.importorskip("fastapi")` et `importorskip("httpx")`,
`test_extern_proc.py` et `test_logger.py` font `importorskip("colorama")`. Aucun de ces quatre
modules n'est dans l'image de build (mesuré). Avec `pytest` seul, les 19 cas seraient **`skipped`
par pytest**, pytest sortirait **0**, et le `PASS` silencieux reviendrait **une couche plus bas**.
⇒ **Il faut compter les CAS, pas les dépendances.**

## 6. La voie choisie, et pourquoi pas les deux autres

⚠️ **Le principe** : *un test qui ne peut pas s'exécuter doit ÉCHOUER ou être VISIBLEMENT sauté,
jamais passer.* Le piège est qu'un **échec franc** casserait le build de tout développeur sans
`pytest` — **le nôtre compris** — et serait contourné dans l'heure ; on aurait échangé un faux vert
contre un `TESTS` amputé, c'est-à-dire le même silence sous un autre nom.

**Voie retenue : `SKIP` automake réel (`exit 77`) + comptabilité publiée.**

- Le lanceur **compte les cas déclarés** par les sources (`ast`), **compte ceux qu'il a exécutés**,
  et **publie les deux** sur une ligne lisible par machine :
  `run-python-tests: suites=3/6 cases=23/42`.
- Verdict, dans cet ordre : **un cas rouge ⇒ 1 (FAIL)** · **un cas déclaré non exécuté ⇒ 77
  (SKIP)** · **tout exécuté et vert ⇒ 0 (PASS)**.
- ⇒ **`make check` ne peut plus imprimer `95/95 PASS` sans que la colonne `# SKIP:` ne dise que le
  Python n'a pas été mesuré.** C'est exactement la cible : *rendre impossible la lecture de « vert »
  sans savoir.*
- `configure.ac` gagne `PYTEST_INFO`, **de la même forme que `GTEST_INFO`** (la convention du
  dépôt : `HAVE_GTEST`, `have_owcapi`, `have_libola`, `have_libknx`, `have_mosquitto`,
  `have_python_mcp` sont tous des `yes/no` sondés puis **affichés** au résumé). L'information
  remonte donc **deux fois** : à la configuration et au `make check`.

**Écartées, explicitement** :
- **Échec franc** — casse le build de quiconque n'a pas `pytest` ; contourné dans l'heure.
- **Rendre la dépendance obligatoire dans `configure.ac`** — déplace l'échec du test vers la
  configuration, et pour une dépendance **de test seulement**. Le dépôt ne le fait pour **aucune**
  dépendance optionnelle (gtest inclus : sans lui, `make check` reste vert avec 3 tests). S'aligner
  sur la convention plutôt que d'inventer.

⇒ Arbitrage consigné dans `DECISIONS.md`.

1. ⭐ **L'oracle avait été trompé.** Le relecteur a posé dans la fixture un `test_mask.py` =

   **ENSEMBLES DE NOMS** — les `<testcase name=…>` du junit, suffixe `[…]` de paramétrisation
   retiré, contre les noms pointés lus à l'`ast`. **Rejoué sur la fixture exacte du relecteur** :
   `suites=6/7 cases=43/44` + `NOT RUN: test_mask.py (1 of 2 …; missing:

   « un `parametrize` futur pourrait masquer un cas manquant » : il n'était pas futur.
2. ⭐ **L'invariant « sauté de l'INTÉRIEUR ⇒ NON exécuté » n'était épinglé par aucun cas** — c'est la
   **seconde couche** du défaut (§3), celle qui fait qu'installer `pytest` seul ne suffirait pas — et
   deux mutations y survivaient. `C5` la ferme, **sur les deux back-ends**.

⚠️ **Contre le piège de la « fixture pauvre »** : `C2` **fabrique le monde** « la suite ne tourne
pas » au lieu de l'attendre — un module fantôme `pytest.py` pousse une machine qui a `pytest` et une
machine qui ne l'a pas dans le **même état**. `C5` va plus loin et fabrique **l'arbre source
entier**, deux cas déclarés dont un qui ne peut pas tourner : il ne dit donc **rien** de ce que
`tests/python/` contient aujourd'hui et ne peut pas pourrir quand la fixture bouge.

⭐ **`C2` a été rendu insensible à la composition de la fixture** (autre réserve de revue) : il
épinglait **en dur** que la fixture garde des suites *pytest-only*, si bien que **porter
`tests/python/` en `unittest` — un progrès souhaitable — aurait cassé `make check`** (mesuré :
supprimer les 3 suites pytest rendait `C2` rouge alors que le lanceur était parfaitement honnête).
Il n'asserte plus que deux choses vraies dans tous les mondes : la ligne existe et est cohérente,
et **retirer une dépendance ne peut pas faire tourner PLUS de cas**.

⚠️ **Pourquoi `C5d`/`C5e` ont l'air tirés par les cheveux, et pourquoi ils restent.** Renommer une
méthode à l'import n'est pas quelque chose que `tests/python/` fait ni devrait faire. C'est la
**seule** forme qui sépare les deux comptabilités, et la séparation est **mesurée, pas imaginée** :
avec `C5a`/`C5b`/`C5c` seuls, la mutation qui **remet le `got >= want` par fichier** — la régression

#### ⚪ `MU_C` est un **mutant équivalent** — la preuve, pas l'affirmation

`re.sub(r"\[.*\]$", "", s)` et `re.sub(r"\[.*?\]$", "", s)` rendent **la même chaîne pour toute
entrée**. **Raison** : l'ancre `$` cloue le `]` fermant à la **fin de la chaîne** ; à partir du même
`[` le plus à gauche, les deux expressions doivent donc consommer **exactement le même segment**,
greedy ou lazy. **Mesuré, pas raisonné seulement** :

- **exhaustif** sur l'alphabet `{'[', ']', 'a', '\n'}`, longueurs 0 à 8 : **87 381 chaînes,
  0 différence** ;
- **aléatoire** sur `{'[', ']', 'a', 'b', 'c', '_', '0'…'3', '.', '\n'}`, longueurs 0 à 40 :
  **400 000 chaînes, 0 différence**.

⭐ **La variante du regex qui n'est PAS équivalente est celle qui retire l'ancre** — `MU_I` :
`test_p[a]b]` rend `test_p` avec l'ancre et `test_pb]` sans. Elle est **tuée par `C5c`**, mais
**seulement depuis que les trois `id` de son `parametrize` portent un `]`** : ⚠️ avec des `id`
entiers, ou même avec **un seul `id` sage parmi trois**, une instance retombait sur le nom déclaré
et **payait pour les deux autres** — mesuré, `MU_I` survivait.

### 12.1 ⛔ `R1` — le faux vert silencieux, **reproduit sur l'arbre RÉEL**

**Fixture du relecteur** : un cas de `tests/python/test_logger.py` marqué `@pytest.mark.skip`, plus
un paquet `tests/python/regress/` (`__init__.py`) contenant un `test_logger.py` **de même basename**
déclarant un cas **du même nom pointé**. **Mesuré, image de dev + les quatre paquets Debian, arbre
complet** :

| | avant | ⭐ après |
|---|---|---|
| sortie de `pytest` | `42 passed, 1 skipped` | `42 passed, 1 skipped` |
| ligne publiée | ⛔ **`suites=6/6 cases=42/42`** | ✅ **`suites=6/7 cases=42/43`** |
| note | ⛔ **aucune** — ni `NOT RUN`, ni `UNDECLARED` | ✅ `NOT RUN: test_logger.py (3 of 4 …; missing: test_default_level_4_logs_debug)` |
| verdict | ⛔ **`PASS`, RC 0** | ✅ **`SKIP`, RC 77** |

**La cause, maillon par maillon** :
1. la **déclaration** lisait un `os.listdir` **PLAT** ⇒ `regress/test_logger.py` n'existait pour
   personne ;
2. l'**exécution** classait par **`os.path.basename`** ⇒ **une seule clé** pour deux fichiers ;
3. ⭐ **et — mesure qui a corrigé la correction** — la famille junit **par défaut n'écrit pas

   mais le repli qui prenait la **première** composante « module » du `classname`. ⚠️ **Le premier
   jet de ce correctif a réparé la mauvaise moitié** : le mutant `MU_D` — clé par basename dans le
   lecteur de `file=` — **a survécu à toute la campagne**, faute d'être atteignable. C'est
   exactement la faute **M-7** (« un remède correct, appliqué à côté de la cause »).

**Le remède** : clé par **chemin relatif à `tests/python/`**, déclaration **récursive** (`os.walk` +
la liste `norecursedirs` de pytest), résolution du `classname` par **le plus long préfixe pointé qui
existe sur disque**, repli par basename **seulement s'il est unique** parmi les suites déclarées
(deux candidats ⇒ on rend « inconnu » plutôt que de choisir), `--rootdir` passé à `pytest`, et repli
sur le chemin **brut** — jamais le basename — quand rien ne se résout.

⭐ **Pourquoi rien ne l'avait vu — la leçon transportable** : les **cinq** arbres fabriqués de
l'oracle étaient **TOUS PLATS**. *Un oracle dont toutes les fixtures ont un seul répertoire ne peut
pas rougir sur une collision de chemin.* ⇒ **`C5f`/`C5g`/`C5m` posent un arbre NON PLAT.**
⚠️ **Et il a fallu qu'il soit ASYMÉTRIQUE** : la première version (2 cas + 1) donnait, sous la clé
par basename, **exactement les deux mêmes nombres** que la comptabilité honnête — le mutant
survivait encore. Rendue asymétrique (2 + 2, dont un cas que **seul** le sous-répertoire déclare) :
honnête **3/4**, basename **2/4**. ⇒ **une fixture de collision se construit pour que les DEUX
comptabilités DIVERGENT NUMÉRIQUEMENT, pas seulement conceptuellement.**

### 12.5 ⭐ Le fait qui remet le reste en perspective

**`run_with_pytest` est du CODE MORT partout dans ce dépôt aujourd'hui** : **aucune** des deux images
n'a `pytest` (dev : `ModuleNotFoundError` ; CI : **aucun `python3`**). Il devient **le seul chemin**
le jour où `T3.47` atterrit. ⇒ **c'est pourquoi `R1`–`R3` sont bloquantes pour `T3.47` et non pour ce
merge**, et c'est écrit **en tête de `T3.47`** (§0) : celui qui la prendra **active un chemin non
éprouvé**, et `R1`–`R3` sont **sa dette d'entrée**.
⚠️ **Corollaire de méthode** : *un correctif dont le chemin principal n'est exécuté par aucune
machine du dépôt n'est pas « vérifié parce que la suite est verte ».* Il n'est vérifié que par ce
qui **fabrique** ce chemin — ici l'oracle et sa campagne.
