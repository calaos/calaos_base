## Findings

### M1 — major: multi-input condition reduced to the last input
`ConditionStd::Evaluate` (`ConditionStd.cpp:59-186`) **assigns** `ret` on each iteration of the input loop (`ret = eval(...)` at `:103,139,169`). For a condition with several `<calaos:input>`, only the **last** input decides the result; the earlier truth values are computed and discarded. `LoadFromXml` explicitly supports N inputs (sibling loop from `:321`) → a real logic bug.

**Fix:** accumulate as a conjunction — seed `ret = true`, then `ret = ret && eval(...)`. (Confirm the intended semantics: logical AND of all inputs.)

### M7 — major: ConditionStd / ConditionOutput duplication + uninitialized temporaries
The three `eval(bool/double/string)` overloads of `ConditionStd.cpp` (at `:202,229,282`, ending `:307`) and `ConditionOutput.cpp` (at `:157,184,237`) are near-identical, as are the TBOOL/TINT/TSTRING branches of their `Evaluate`. An existing divergence: `ConditionOutput` leaves `bval/dval` **uninitialized** (`ConditionOutput.cpp:39-40`) while `ConditionStd` initializes them (`:62-63`).

**Fix:** extract a shared operator-evaluation helper (free function or common base), and always initialize the temporaries — fixing the uninitialized-read bug in passing.
