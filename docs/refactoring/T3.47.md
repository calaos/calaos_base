**ce qu'il faut re-vérifier une fois `pytest` réellement installé en CI**, où le chemin cessera

## 1. Le fait, mesuré

`T3.44` a réparé le **rapport** : `tests/run-python-tests.sh` ne dit plus `PASS` sur des suites qui
n'ont pas tourné, il publie `run-python-tests: suites=N/M cases=N/M` et sort **77** (`SKIP` visible)
quand un cas déclaré n'a pas été exécuté. ⚠️ **Il n'a rien réparé du fond** : les **42 cas** de
`tests/python/` ne sont exécutés **sur aucune machine de CI**, et le journal d'un `push` vert ne
permet toujours pas de le savoir.

**Balayage des cinq jobs de `.github/workflows/ci.yml`** (mesuré, `python3` sur le fichier) :

| job | installe `python3` ? | lance `make check` ? | conséquence |
|---|---|---|---|
| `build-and-test` | ⛔ **non** | ✅ oui | `AM_PATH_PYTHON` pose `PYTHON=:` ⇒ **77**, `SKIP`, **0 cas exécuté** |
| `coverage` | ⛔ **non** | ✅ oui | idem, **0 cas exécuté** |
| `format-check` | non | non | hors sujet |
| ⭐ `mcp-sidecar-deps` | ✅ **oui** (`python3 python3-pip`, puis les deps de `pyproject.toml`) | ⛔ **non** | la **seule** machine outillée est celle qui **ne lance pas les tests** |
| `push` | — | — | déclencheur |

⭐ **C'est l'asymétrie qu'il faut retenir** : les deux jobs qui exécutent `make check` n'ont **aucun
`python3`** ; le seul job qui a `python3` **et** les modules du sidecar ne lance **jamais**
`make check`. Personne n'a construit ça ; c'est le résultat de deux ajouts indépendants.

⚠️ **Et le journal ne le dit pas.** Trois raisons cumulées, chacune vérifiée :
1. `PYTHON=:` **court-circuite dans `run-python-tests.sh` AVANT le runner** ⇒ la ligne de
   comptabilité `suites=N/M cases=N/M` **n'est jamais produite** en CI ;
2. le protocole de test simple d'automake n'écrit sur la console que `PASS:` / `SKIP:` — **la sortie
   du test part dans `tests/run-python-tests.sh.log`**, pas dans le journal du job ;
3. l'étape qui dumpe ces `.log` est **`if: failure()`** (`ci.yml:39`) ⇒ **sur un build vert,
   personne ne les lit**.

⇒ ⚠️ **Le `SKIP: run-python-tests.sh` était déjà là avant `T3.44`** (même branche `PYTHON=:` dans
l'ancien script) : **ce n'est pas un gain**, et `T3.44` ne le revendique pas.

## 5. Livraison (branche `fix/t3.47`, non mergée)

### 5.1 ⭐ La cause du `SKIP` n'est PAS la même sur les deux images — mesuré

Le §2 supposait une cause unique. Il y en a **deux**, et le correctif diffère :

| image | `python3` ? | `pytest`/`fastapi`/`httpx` ? | verdict mesuré | cause |
|---|---|---|---|---|
| CI `debian:12` (`build-and-test`, `coverage`) | ⛔ **non** | — | `SKIP: no python3 interpreter detected at configure time`, **0/42** | le harnais court-circuite avant le runner (`PYTHON=:`) |
| image de dev (devcontainer publiée) | ✅ oui | ⛔ **non** (`colorama` seul est là) | `suites=3/6 cases=23/42`, RC 77 | le harnais est **bien câblé** ; ce sont les **modules** qui manquent |

⇒ **le harnais n'est pas en cause dans un seul des deux cas.** En CI c'est l'absence
d'interpréteur ; dans l'image de dev c'est l'absence des modules, et le runner le dit déjà
correctement, nommant les 19 cas non exécutés.

⚠️ **L'image de dev publiée est en retard sur son propre `.devcontainer/Dockerfile`** : celui-ci
installe le jeu `pyproject.toml` depuis `T3.23`, l'image montée n'a **ni `mcp`, ni `fastapi`, ni
`uvicorn`, ni `pydantic`, ni `starlette`**. Consigné en `F-PYIMG-1`.

### 5.2 Ce qui a été fait

- **`src/bin/calaos_mcp/pyproject.toml`** : nouveau `[project.optional-dependencies] test =
  pytest==9.1.1, httpx==0.28.1, colorama==0.4.6`. ⭐ **La source de vérité reste unique** : aucune
  liste de dépendances Python n'est écrite à la main ailleurs.
- **`scripts/pyproject-requirements.py`** : `--extra NAME` (répétable). Un extra inconnu est une
  **erreur**, pas une liste vide.
- **`.github/workflows/ci.yml`** (`build-and-test`) : `python3 python3-pip` dans l'`apt`, une étape
  d'installation depuis `pyproject.toml --extra test`, `make check` sous
  `CALAOS_PYTHON_TESTS_REQUIRED=1`, et une étape **`if: always()`** qui imprime la ligne de
  comptabilité — §2.3 fermé.
- **`tests/run-python-tests.sh`** : `CALAOS_PYTHON_TESTS_REQUIRED=1` transforme **tous** les 77 en
  **1**. ⚠️ **Contredit le §4 « rien dans `tests/` »** : la mesure a dit autre chose. Un `SKIP`
  reste invisible sur un build vert ; sur une machine dont c'est le métier d'exécuter ces 42 cas,
  « je n'ai pas pu » est une erreur de build. **Éteint par défaut** (arbitrage `DECISIONS.md` du
  2026-08-25 sur les dépendances optionnelles).
- **`tests/check-python-tests-reporting.sh`** : `C6a`–`C6d` épinglent le mode strict, et le script
  **désarme** la variable pour ses propres sous-invocations (voir 5.4).
- **`.devcontainer/Dockerfile`** : `--extra test`, pour que `make check` exécute vraiment les 42.
- **Lest `jansson`** retiré des trois images (`Dockerfile` ×2, `.devcontainer`, `ci.yml` ×2) :
  aucun `#include <jansson.h>`, aucun `-ljansson`, rien dans `configure.ac` — les seules
  occurrences restantes sont des commentaires d'époque. Prouvé par une compilation complète dans
  un `debian:12` **sans** `libjansson-dev`.

### 5.4 ⭐ Ce que la mutation a trouvé et que personne n'avait vu

La première `make check` en mode strict a rendu **`FAIL: check-python-tests-reporting.sh`, 13
checks rouges**. Ce n'était pas une régression : **`CALAOS_PYTHON_TESTS_REQUIRED` fuit du
`make check` vers les sous-invocations du méta-oracle**, dont **treize** fabriquent un arbre dont
le verdict honnête est précisément 77 et l'assertent. Une variable d'environnement globale traverse
un oracle qui teste un script. **Le script la désarme désormais explicitement en tête**, et `C6`
la ré-exporte dans son propre sous-shell.

⚠️ **C'est le genre de couplage qu'aucune relecture n'attrape** : sans le passage effectif en mode
strict, la variable aurait été posée en CI et le premier `push` aurait rougi sur un test **sans
rapport** avec le sujet.
