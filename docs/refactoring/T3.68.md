# T3.68 — `remote_ui_get_config` reste sans réponse, et le journal accuse le parseur JSON

## Le défaut

`RemoteUI::getRemoteUIConfigMessage()` (`src/bin/calaos_server/IO/RemoteUI/RemoteUI.cpp:496-497`)
lit `brightness` et `timeout` par un **`std::stoi` nu** :

```cpp
config["brightness"] = std::stoi(get_param("brightness"));
config["timeout"]    = std::stoi(get_param("timeout"));
```

`IOBase::get_param()` rend `""` pour un param absent et `std::stoi("")` lève
`std::invalid_argument`. L'appelant est `RemoteUIWebSocketHandler::handleGetConfig()`, appelé
**depuis l'intérieur du `try` de `processApi()`** — un `try` écrit pour les erreurs de parse. Donc,
sur tout écran dont l'`io.xml` ne porte pas les deux params :

1. l'écran ne reçoit **rien** en réponse à `remote_ui_get_config` ;
2. le serveur journalise `RemoteUIWebSocketHandler: JSON parse error: stoi` — **sur une trame
   parfaitement valide** ;
3. la trame part ensuite au parent, qui ne connaît pas ce `msg` et ne répond pas non plus.

⚠️ **Le message de journal désigne la mauvaise cause.** Il envoie chercher le défaut dans le
parseur JSON alors que la trame est correcte et que le problème est un param manquant.

## Ce qui le rend atteignable

Aucun chemin d'écriture n'oblige un `RemoteUI` à porter `brightness` ou `timeout` : ils viennent de
l'`io.xml`, et `setBrightness()` n'est appelé que si quelqu'un règle la luminosité. Un écran
provisionné et jamais réglé est donc dans cet état — c'est un appareil physique légitime.

## Ce qui reste à faire

Le jumeau `RemoteUI::getBrightness()` (`:522`) fait déjà la bonne chose depuis
[T3.25](T3.25.md) — `Utils::from_string_or_keep()` sur un défaut de 100 — et `sendConfigUpdate()`
passe par `parseGridDimension()` pour exactement la même raison. Correctif :

1. lire les deux params par `from_string_or_keep()` avec les défauts de `getBrightness()` ;
2. poser un cas qui exerce `remote_ui_get_config` sur un IO **sans** les deux params — la fixture de
   `RemoteUiConfigProjectionTest` (`tests/core/JsonApiStateWireBytes_test.cpp`) les pose
   aujourd'hui **pour contourner ce défaut**, et le commentaire le dit ;
3. ⚠️ regarder le `catch` du handler pendant qu'on y est : il nomme « JSON parse error » tout ce qui
   remonte de la branche locale, y compris ce qui n'a rien à voir avec un parse.
