# T3.68 — `remote_ui_get_config` reste sans réponse, et le journal accuse le parseur JSON

> **État : ✅ LIVRÉE** (branche `fix/t3.68`, 3 commits : caractérisation **zéro ligne de `src/`**,
> correctif, doc ; **non poussée, non mergée**). Ouverte au merge de [T3.62](T3.62.md) sur
> `F-REMOTEUI-1` de [`FINDINGS.md`](FINDINGS.md).

## Le défaut

`RemoteUI::getRemoteUIConfigMessage()` (`src/bin/calaos_server/IO/RemoteUI/RemoteUI.cpp:496-497`)
lisait `brightness` et `timeout` par un **`std::stoi` nu**. `IOBase::get_param()` rend `""` pour un
param absent, `std::stoi("")` lève `std::invalid_argument`, et l'appelant
`RemoteUIWebSocketHandler::handleGetConfig()` tourne **dans le `try` de `processApi()`** — un `try`
écrit pour les erreurs de parse. Sur tout écran dont l'`io.xml` ne porte pas les deux params :

1. l'écran ne recevait **rien** ;
2. le serveur journalisait `RemoteUIWebSocketHandler: JSON parse error: stoi` — **sur une trame
   parfaitement valide**.

**Mesuré, pas raisonné.** Le commit de caractérisation rougit sur les deux symptômes, verbatim :

```
the screen received nothing at all
a well formed frame was reported as a parse failure:
  [WRN] remote_ui (RemoteUIWebSocketHandler.cpp:160)
  RemoteUIWebSocketHandler: JSON parse error: stoi
```

## Les valeurs par défaut, et d'où elles viennent

| Param | Défaut | Source |
|---|---|---|
| `brightness` | `100` | `RemoteUI::getBrightness()`, qui le porte depuis [T3.25](T3.25.md). Le correctif **appelle cette fonction**, il ne recopie pas la valeur. |
| `timeout` | `30` | ⚠️ **Aucun défaut établi dans le code.** Aucun chemin d'écriture ne pose ce param (`set_param("timeout")` : **0 site**), et `ioDoc` ne le déclare pas. `30` est la seule valeur que l'arbre énonce : **tous** les exemples de `src/bin/calaos_server/RemoteUI/remote-ui.md` — modèle d'`io.xml`, réponse de provisioning, réponse REST — la portent. Retenue et **déclarée comme telle**, faute de mieux. |

`getTimeout()` est écrit comme le jumeau de `getBrightness()` : `Utils::from_string_or_keep()`, non
lançant, un défaut nommé. C'est la convention du fichier, pas une convention neuve.

## Le `try` du handler

Le `try` de `processApi()` est **coupé en deux**. Le parse garde son nom ; le service du message a
le sien (`unhandled failure while serving <msg>`). ⚠️ **Ce `try` ne masquait pas que le `stoi`** :
il couvre aussi les **écritures d'état déclenchées par une trame `remote_ui_relay_state`**
(`handleRelayState()` → `RemoteUIOutputRelay::updateStateFromDevice()`, donc le moteur de règles)
et la **sérialisation de la réponse** dans `sendJson()`. Tout cela était imputé au parseur ; c'est
désormais nommé « unhandled ». **La chute vers le parent est inchangée** — aucun changement de wire.

## Le motif, balayé

`std::stoi(get_param(...))` nu : **2 sites**, les deux corrigés ici. Élargi à toute conversion
lançante de `src/` hors bibliothèques tierces (`src/lib/cpptui`, `src/lib/exprtk`) : **5 sites**,
dont **4 déjà gardés** (`RemoteUI.cpp:332`, `OtaFirmwareManager.cpp:81`, `IOBase.cpp:226`,
`JsonApi.cpp:435`). **Il en reste UN, non gardé** : `RemoteUI.cpp:213`, `std::stoi(attr_value)` sur
les attributs `x`/`y` d'un widget dans `LoadFromXml()`, qui n'est protégé par aucun `try`. **Non
corrigé ici** : le mode d'échec est le **chargement de la configuration**, pas la réponse à un
appareil, et le remède demande de trancher entre « widget ignoré » et « position à 0 ».
⇒ ticket [`T3.70`](T3.70.md), `F-REMOTEUI-3`.
