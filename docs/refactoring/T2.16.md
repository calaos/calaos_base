# T2.16 — HttpClient : fuite des headers entre requêtes keep-alive

**Type** : fix (sec)
**Phase** : 2

## Contexte

Confirmé par revue (FINDINGS wave 5) : `_parser_begin` (`HttpClient.cpp:118-133`) remet à
zéro les flags de parsing entre deux requêtes d'une même connexion keep-alive
(`parse_done`, `has_field`, `has_value`, `hfield`, `hvalue`, `bodymessage`, `parse_url`,
`headersSize`) mais **pas `request_headers`** : les en-têtes de la requête N fuient dans la
requête N+1. Conséquence concrète : un `Origin` périmé continue de déclencher la logique
CORS sur une requête qui n'en envoyait pas ; idem pour tout header à sémantique
par-requête (`X-Forwarded-For` → identité client du cap T2.11, auth, etc.). Un header envoyé
une fois « colle » à toute la connexion.

## Travail

Fichiers : `src/bin/calaos_server/HttpClient.{cpp,h}`, `tests/TransportHardening_test.cpp`.

1. Vider `request_headers` dans `_parser_begin` avec les autres résets (et vérifier qu'aucun
   autre état par-requête n'est oublié au même endroit — balayer les membres de `HttpClient`
   remplis par les callbacks llhttp).
2. Vérifier que rien ne dépend légitimement de la persistance inter-requêtes (le keep-alive
   ne doit conserver que l'état de **connexion**, pas de requête).
3. Test de régression dans `TransportHardening_test.cpp` (binaire existant, T2.11) : deux
   requêtes pipelinées sur la même connexion, la première avec `Origin:`/header témoin, la
   seconde sans → la seconde ne doit plus voir le header de la première.

## Acceptation

- Build docker + `make check` verts (test keep-alive nouveau inclus).
- Requête N+1 sans `Origin` sur une connexion keep-alive → aucun traitement CORS déclenché.
