**Type** : epic (doc) · **Phase** : 4 · **Dépend de** : rien de bloquant — mais chaque sous-ticket
doit être écrit **contre le code et les goldens**, jamais contre l'ancienne doc.
**Origine** : demande utilisateur (2026-08-17), après ~230 commits de refactoring.

## ⚠️ La leçon d'E4.0f — à lire avant d'écrire une ligne

E4.0f a réécrit deux de ces documents **contre le code**. Ce qu'il y a trouvé n'était pas de
l'obsolescence, c'était de la **fausseté** :
- `08_http_api.md` décrivait une **enveloppe d'event que le code n'émet pas**, listait un type
  **fantôme** (`push_notification`, le code dit `push_notif`) et **omettait 9 types sur 23** ;
- `10_events_notifications.md` était **factuellement faux sur la configuration mail** (les vraies
  clés sont `notif/mail_sender`, `notif/mail_recipients`, `smtp_debug`, consommées par le binaire
  hors-processus `calaos_mail`) et son **exemple XML d'`ActionPush` était inventé**.

Sa revue a échantillonné ~50 affirmations et en a **revérifié 29 au source** : les 4 défauts
trouvés étaient **tous des goldens cités infidèlement** — dont un qui enseignait
`len(steps) == steps_count` alors que le code garantit **`+1`**, ce qui **tronque** le tableau
d'un client qui suit la doc.

**Règle de la série, non négociable** : *la documentation n'est testée par rien. Une erreur y est
permanente, et elle est reprise de bonne foi par tous ceux qui la lisent.* On écrit **contre le
code observé et contre les goldens**, jamais contre le document existant.

## Sources d'autorité, dans cet ordre

1. **`tests/core/golden/*.json` — 145 fichiers.** C'est le comportement réel de l'API, **généré par
   le code**. Tout extrait cité doit être **fidèle** ; marquer explicitement `intégral` ou `extrait`.
2. **`docs/refactoring/RELEASE_NOTES.md`** — 297 lignes, 19 sections. C'est la liste des
   comportements **qui ont changé pour l'utilisateur**, donc la table des matières de ce qui doit
   bouger dans la doc.
3. **`docs/refactoring/FINDINGS.md`** — porte de nombreux écarts doc/code déjà mesurés par les
   agents, avec leurs sites. **À dépouiller avant de commencer.**
4. **`docs/refactoring/DECISIONS.md`** — les choix utilisateur et leur raison (option `insecure`,
   règle désactivée, scénario désactivé, clés JSON triées…).
5. Le code.

## Invariants

- **Aucune ligne de `src/`, aucun test, aucun golden.** C'est de la documentation pure.
- **Ne pas anticiper E4.1** : la migration JSON **n'est pas faite**. Toute mention de jansson qui
  décrit l'état actuel est **juste** ; ne la corrige pas au futur.
- **Marquer la provenance** de chaque exemple : `(capturé, <golden>)` ou `(dérivé, Fichier.cpp:L-L)`.
  E4.0f a établi cette convention, elle a permis à sa revue de vérifier 29 affirmations.
- Chaque document reste **dans sa langue d'origine**.

## Acceptation

Pour chaque sous-ticket : toute affirmation nouvelle ou modifiée est **adossée** soit à un golden
cité fidèlement, soit à une référence `Fichier.cpp:ligne` **vérifiée**. Les écarts trouvés et
**non corrigés** (hors périmètre) partent dans `FINDINGS.md` plutôt que d'être passés sous silence.

⚠️ **Revue exigée**, comme pour le code : la revue d'E4.0f a trouvé 4 citations de goldens
infidèles qu'une relecture d'auteur n'avait pas vues. **Échantillonner et revérifier au source**
est le seul contrôle qui marche sur de la doc — il n'y a pas de `make check` pour ça.
