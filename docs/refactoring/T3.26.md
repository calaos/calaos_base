# T3.26 — OTA : « version différente » = « mise à jour disponible », donc le downgrade est proposé au parc

**Statut** : 📋 · **Type** : fix (comportement) · **Phase** : 3 · **Dépend de** : —
**Décision utilisateur requise** — voir §4. **Ne pas implémenter avant.**
**Origine** : `FINDINGS.md` § *E4.5e*, :2601-2610 (`[COMPORTEMENT, plus grave qu'il n'y paraît]`).

---

## 1. Le constat, revérifié au source (2026-08-25)

`RemoteUI/OtaFirmwareManager.cpp:247-253` — **la référence de `FINDINGS.md` est exacte** :

```cpp
    // Simple string comparison: if versions differ, offer update
    // This allows switching between dev and release branches
    if (firmware->getVersion() == currentVersion)
    {
        cDebugDom(TAG) << "Device " << hardwareId << " is up to date (v" << currentVersion << ")";
        return false;
    }
```

Il n'y a **aucun ordre**. Ce n'est même pas « une comparaison textuelle qui n'ordonne pas
correctement `1.10.0` et `1.9.0` » (formulation de `FINDINGS.md:2608`, qui laisse croire à une
comparaison relationnelle) : c'est une **égalité**. Toute version *différente* — plus ancienne
comprise — traverse le test et déclenche la notification `remote_ui_fw_update_available`
(`:255-273`).

⭐ **Et le comportement est DÉLIBÉRÉ, écrit dans le commentaire** : *« This allows switching
between dev et release branches »*. `FINDINGS.md` ne le mentionnait pas. **Ce ticket n'est donc
pas un correctif de bug évident, c'est une demande d'arbitrage** — d'où le blocage sur décision
utilisateur.

### La chaîne complète, et qui peut la déclencher

| Étage | Site | Ce qui se passe |
|---|---|---|
| Dépôt | `/usr/share/calaos/firmwares/<hardware_id>/manifest.json` (`:36`, surchargeable par l'option `ota_firmware_path`, `:65`) | un répertoire du **système de fichiers** |
| Scan | `scanDirectory()` `:143-217` | **écrase** l'entrée du cache par le manifeste trouvé ; **un seul firmware par `hardware_id`**, le dernier scanné gagne |
| Déclencheurs | `init()` `:95`, minuterie périodique `:101-116` (défaut **60 min**), et `POST /api/v3/ota/rescan` — **localhost uniquement** (`OtaHttpHandler.cpp:68`) | |
| Diffusion | `rescan()` `:140` → `notifyAllDevices()` `:279-289` → `RemoteUIManager::notifyOtaUpdates()` | **tous** les appareils RemoteUI connectés |

**Gravité réelle, dite honnêtement.** ⛔ **Ce n'est PAS un vecteur d'attaque à distance.** Il
n'existe **aucun endpoint d'envoi** de firmware : `OtaHttpHandler` n'expose que
`GET …/firmware/{hardware_id}/download` et `POST …/ota/rescan` (localhost). Déposer un fichier
demande un **accès en écriture au système de fichiers du serveur** — c'est-à-dire déjà la partie.

**Ce qui reste réel, et suffit à justifier le ticket** : une **erreur d'exploitation ordinaire**
— restaurer une sauvegarde du répertoire de firmwares, revenir sur une release, un paquet qui
réinstalle une version antérieure — **propose silencieusement un downgrade à tout le parc** de
ce `hardware_id`, sans qu'aucune ligne de journal ne dise « c'est un retour en arrière ». Le
journal dit l'inverse : `Firmware update available for … device has vX, available vY` (`:255`),
**sans comparer X et Y**.

⚠️ **Non vérifié, et ce n'est pas dans ce dépôt** : ce que fait l'appareil de la notification —
téléchargement automatique ou confirmation. Le firmware RemoteUI est un **autre dépôt**. Si
l'appareil installe sans confirmer, le downgrade est **effectif**, pas seulement *proposé*.
**À établir avant de trancher §4.**

## 2. Les garde-fous déjà en place (à ne pas casser)

- Le nom du répertoire doit **égaler** `hardware_id` du manifeste (`:195-201`) ;
- le **checksum SHA-256** du fichier est vérifié à chaque scan (`:204-208`) ;
- le manifeste doit être `isValid()` (`:188`).

⇒ le défaut n'est **pas** un défaut d'intégrité. Le fichier proposé est bien celui annoncé. Il est
simplement **plus vieux**, et personne ne le dit.

## 3. Le travail

1. Une **comparaison sémantique** de versions, dans `src/lib` et **testée seule** — pas une
   lambda enfouie dans `OtaFirmwareManager`. Forme minimale suffisante : découpage sur `.`,
   comparaison numérique composante par composante, **suffixe de pré-release traité
   explicitement** (`4.4.3-dev.11` existe dans l'arbre, c'est la version courante).
2. `checkDeviceForUpdate()` ne notifie que si la version du dépôt est **strictement supérieure**.
3. **Le cas non ordonnable doit être un cas**, pas un trou : deux versions dont l'une ne se parse
   pas (`main`, `custom-build`) — comportement à choisir en §4, mais **journalisé en `cWarning`**,
   jamais silencieux.
4. Le journal `:255` dit désormais **le sens** de la transition.

## 4. ⚠️ Décision utilisateur — trois options, à porter dans `DECISIONS.md`

| Option | Effet | Ce qu'on perd |
|---|---|---|
| **A** — strictement supérieur, point | plus aucun downgrade proposé | **le cas d'usage écrit dans le commentaire** : basculer dev ↔ release ne marche plus dans le sens descendant |
| **B** — strictement supérieur **par défaut**, downgrade **opt-in** par une clé du manifeste (`allow_downgrade: true`) ou une option de configuration | garde le cas d'usage, le rend explicite | une clé de plus dans le format de manifeste, donc un accord avec le firmware |
| **C** — statu quo, mais **journal explicite** `cWarning` « proposing a DOWNGRADE from X to Y » | zéro risque de régression | le défaut reste, on l'a seulement rendu visible |

**Recommandation** : **B**. Elle est la seule qui referme le défaut *et* préserve la raison pour
laquelle il a été écrit. **A** casserait un usage documenté dans le code même.
⚠️ **Ne pas trancher sans avoir répondu à la question du §1** (l'appareil installe-t-il seul ?) :
si oui, **C est insuffisante**.

## 5. Les tests

**Commit de caractérisation d'abord — tests seuls, zéro ligne de `src/`.**

Suite neuve `tests/core/OtaVersionOrder_test`, plus des cas sur `checkDeviceForUpdate()`.
⚠️ `OtaFirmwareManager` est un **singleton** (`_instance`, `:33`) qui lit le système de fichiers et
`RemoteUIManager` : le filet doit viser **la fonction de comparaison extraite**, appelée par la
production **et** par le test — c'est le remède à 10 lignes du test-miroir d'E4.1e, pas une
duplication de la logique dans le test.

| Cas | Ce qu'il fige |
|---|---|
| `AnOlderFirmwareIsNotOfferedAsAnUpdate` | ⭐ **le défaut** — `1.9.0` proposé à un appareil en `1.10.0` ⇒ 🔴 puis 🟢 |
| `TenIsGreaterThanNine` | l'ordre numérique, **pas** lexicographique |
| `AnIdenticalVersionIsNotOffered` | **acquis** — le seul comportement correct d'aujourd'hui |
| `ANewerFirmwareIsStillOffered` | **acquis** — le chemin nominal ne régresse pas |
| `APrereleaseSortsBeforeItsRelease` | `4.4.3-dev.11` < `4.4.3` |
| `AnUnparsableVersionIsRefusedAndLogged` | le trou nommé au §3.3 |

### ⚠️ Fixture pauvre — la forme qu'elle prendrait ici

Tester avec `1.0.0` / `2.0.0` **ne prouve rien** : lexicographique et numérique donnent la même
réponse. **La paire qui mord est `1.9.0` / `1.10.0`** — c'est la seule où les deux ordres
divergent. Un fixture qui ne la contient pas laisse la mutation « revenir à `<` sur les chaînes »
**verte**. (9ᵉ récidive de la série, **toutes** trouvées par les relecteurs.)

### Contre-mutation par échange
Échanger `firmware->getVersion()` et `currentVersion` dans l'appel de comparaison ⇒ les cas
« plus ancien » et « plus récent » doivent rougir **en deux ensembles distincts**, témoin 0 rouge.
Effacer le `.o` **et** le binaire, exiger la ligne `CXXLD` **et** le code de sortie.
