# T3.243 — `WAGO_DALI_GET ERR <reason>`, la réponse d'erreur de la 4.0, est lue comme « allumé »

**Statut** : ✅ livrée (3 commits) · **Type** : fix · **Phase** : 3
**Origine** : spécification `docs/PROTOCOL_WAGO_V4.0.md`, en cours d'écriture par l'utilisateur, § *Error
replies — new in 4.0*, puis relecture du chemin de lecture DALI de `calaos_server`.
⭐ **Même forme que le bug rapporté par l'utilisateur** et instruit en [T3.156](T3.156.md) : la
« Lumiere SAS » affichée allumée alors qu'elle est éteinte.

---

## 0. Ce qui a été LIVRÉ, et ce que le correctif MESURE

**L'arbitrage est tranché par l'utilisateur : PAS de verrou de version.** `ERR` n'est un niveau DALI
sous **aucune** version, donc le lire comme « allumé » est faux en 2.3 comme en 4.0 ; le test protège
aussi un automate intermédiaire ou tiers qui émettrait cette forme. ⛔ **Aucune constante de seuil,
aucune branche de version n'a été ajoutée** — vérifié : `plcDaliGetCarriesGroup()` n'est pas appelée
sur ce chemin et aucun `DALI_ERROR_*_MAJOR` n'existe.

Un seul prédicat partagé, `Calaos::daliReplyIsError()` / `daliReplyErrorReason()`
(`WagoMap.h`, `WagoMap.cpp`), et les **deux** consommateurs le consultent **avant** de lire un
niveau :

| chemin | avant, MESURÉ sur l'arbre non corrigé | après, MESURÉ |
|---|---|---|
| `WODali` | `value = 100` ⇒ état publié **« allumé, 100 % »** | état publié identique à celui d'une **expiration**, et le jeton `StartReadRules` rendu **exactement une fois** |
| `WODaliRVB` | `from_string("GROUP_UNSUPPORTED", red)` écrit **0** (`StringUtils.h:251-262` publie `T{}` sur un jeton illisible), le `-1` « pas encore lu » est détruit, `checkReadState()` publie une couleur ⇒ `get_command_string()` vaut `"set 0"` | rien n'est publié, `get_command_string()` reste **vide**, et les **trois** jetons sont rendus |

**La raison est journalisée sur les deux chemins**, relevé au journal d'exécution des suites :

```
[INF] output (WODali.cpp) dali_v25: PLC refused the DALI read 'WAGO_DALI_GET 1 77': GROUP_UNSUPPORTED
[INF] output (WODaliRVB.cpp) dali_rgb_refused: PLC refused the DALI read 'WAGO_DALI_GET 1 71 0' for the red channel: GROUP_UNSUPPORTED
```

⭐ **Le plafond est celui qui existait déjà, et aucun chemin de journal neuf n'a été créé.** La ligne
est écrite sur la branche d'échec qui journalisait **déjà** (`WODali.cpp:95-101`), et le nombre de
lignes ne se négocie pas sur le réseau : `udpRequest_cb()` dépile **une** commande par réponse et
sort immédiatement sur file vide (`WagoMap.cpp:578-579`), or les lectures DALI sont émises **une fois
par IO au chargement** (`WODali.cpp:71`, `WODaliRVB.cpp:86-91`, seuls appelants de
`SendDaliGetCommand()`). ⇒ le plafond est le **nombre d'IO DALI de la configuration**, pas le débit
d'un pair. C'est pourquoi la rampe par doublement de [T3.152](T3.152.md)/[T3.212](T3.212.md) et la
fenêtre de [T3.240](T3.240.md) ne sont **pas** reprises ici : elles bornent des lignes dont la cadence
est décidée **dehors**, ce qui n'est pas le cas de celle-ci. ⛔ `UDPServer.cpp` n'est pas touché.

**Suites neuves : +2** (`core/WagoDaliErrorReply_test`, 7 cas ; `core/WagoDaliAddressRange_test`,
2 cas, pour [T3.244](T3.244.md)).

### Contre-mutation — ensembles rouges par les NOMS

Témoin `CM0` : **0 rouge** sur l'arbre livré. Chaque tour efface **les objets et les binaires** avant
`make -C src` puis `make -C tests <cibles>` (14ᵉ piège), et lit un oracle d'**exécution** (`N tests
from 1 test suite ran`, `[  PASSED  ]`) et non le seul `CXXLD`.

| mutant | rouges |
|---|---|
| `CM1` le test retiré de `WODali` | `AnErrorReplyLeavesTheBallastWhereATimeoutLeavesIt`, `TheRefusalIsReadAtTheLevelPositionAndNowhereElse`, `OnlyTheWordErrIsARefusal`, `AnErrorReplyIsRefusedWhateverVersionWasAnnounced` |
| `CM2` le test retiré des **trois** canaux de `WODaliRVB` | `ARefusedChannelPublishesNoColour` |
| `CM3` le test déplacé **après** la conversion | **identique à `CM1`** |
| `CM4` `"ERR"` → `"ERROR"` | `CM1` ∪ `CM2` |
| `CM5` `tokens[1]` → `tokens[2]` | **identique à `CM4`** |
| `CM6` `ioRead()` retiré de la branche d'erreur | `AnErrorReplyGivesBackExactlyOneStartReadToken`, `AnErrorReplyIsRefusedWhateverVersionWasAnnounced` |
| `CM7` « tout champ illisible est un refus » | `OnlyTheWordErrIsARefusal` (⊂ `CM1`) |

⚠️ **Deux égalités : `CM1` ≡ `CM3` et `CM4` ≡ `CM5`.** Deux mutations au même ensemble ne sont pas
deux preuves ; ce sont quatre mutations et **deux** ensembles.

⛔ **Un cas n'est rouge sous aucun mutant, et c'est voulu** :
`AnErrorReplyIsDeliveredAndNotDroppedOnTheWay` ne mesure pas le correctif mais la **livraison** de la
trame — que le filtre de §2.1 ne la jette pas — en exigeant que la lecture ait été **dépilée**, face à
une trame qui, elle, est réellement jetée. C'est la fermeture du piège « un capteur qui ne mesure rien
passe pour un capteur qui ne trouve rien », pas un oracle du correctif.

## 1. Ce qui est MESURÉ

**Un automate 4.0 franchit bien le seuil de groupe — il n'y a pas de défaut de comparaison.**

`core/WagoDaliGetGroup_test`, cas `ThreeZeroIsTheFirstVersionToldTheGroup`
(`tests/core/WagoDaliGetGroup_test.cpp:565-589`), porte la ligne `{ "85", 4, 0, true }` dans son
tableau de versions. Binaire existant relancé sur ce seul cas : **PASSED**.

Ce que ce vert mesure vraiment : le helper `answerVersion()`
(`tests/core/WagoDaliGetGroup_test.cpp:184-188`) construit la **vraie chaîne**
`WAGO_GET_VERSION 4.0 750-849` et la fait entrer par `WagoMap::udpRequest_cb()`. L'analyse du champ
`<H>.<L>` (`WagoMap.cpp:516-536`) **et** la comparaison (`WagoMap.cpp:468-476`) sont donc toutes deux
exercées, pas court-circuitées. La comparaison est lexicographique sur deux entiers séparés et
traite le majeur d'abord :

```cpp
if (plc_version_major != DALI_GROUP_MAJOR)
    return plc_version_major > DALI_GROUP_MAJOR;   // WagoMap.cpp:473-474
return plc_version_minor >= DALI_GROUP_MINOR;
```

⇒ `4.0 ≥ 3.0` passe. ⛔ **Aucun ticket à ouvrir de ce côté.**

## 2. Ce qui est LU — le chemin, avec mes ancres revérifiées

### 2.1 Le filtre d'attribution est exactement celui que la spécification annonce

`udpReplyMisattributedToDaliGet()`, `WagoMap.cpp:49-58` :

```cpp
if (udpVerb(command) != "WAGO_DALI_GET")
    return false;
const string verb = udpVerb(reply);
if (verb.rfind("WAGO_", 0) != 0)
    return false;
return verb != "WAGO_DALI_GET";
```

Appelé en tête de `udpRequest_cb()` (`WagoMap.cpp:564-565`), avant la remise du jeton de délai.
`udpVerb()` (`WagoMap.cpp:34-38`) coupe à la **première espace**.

⇒ `WAGO_DALI_GET ERR GROUP_UNSUPPORTED` a pour verbe `WAGO_DALI_GET` : **il n'est pas jeté**, il est
livré à l'appelant. Et un `WAGO_DALI_GET_ERROR` **le serait**, jeté. La contrainte de forme retenue
côté automate — verbe conservé, `ERR` en **champ**, pas en verbe — est justifiée.

⚠️ **Deux précisions où le filtre est plus ÉTROIT que « il jette ce qu'il n'attend pas »** : il ne
garde **que** le cas où la tête de file est un `WAGO_DALI_GET`, et il laisse passer toute charge dont
le premier champ n'est **pas** un nom de commande (`rfind("WAGO_", 0) != 0` ⇒ `false`). Le commentaire
qui le précède (`WagoMap.cpp:40-48`) dit déjà les deux. Ça ne change rien pour `ERR`, qui arrive
derrière le bon verbe.

### 2.2 La conversion binaire, et ce que `ERR` produit aujourd'hui

`WODali::WagoUDPCommand_cb()`, `WODali.cpp:93-126`. Le nœud :

```cpp
if (tokens.size() >= 3)          // WODali.cpp:107
{
    //get the status of the ballast
    if (tokens[1] == "0")        // WODali.cpp:110
    { value = 0; old_value = 100; }
    else
    { value = 100; old_value = 0; }   // WODali.cpp:117-118
}
emitChange();                    // WODali.cpp:122
```

`split()` a pour délimiteur par défaut `" "` (`src/lib/StringUtils.h:44`) : la trame
`WAGO_DALI_GET ERR GROUP_UNSUPPORTED` donne **exactement trois** jetons, la garde `>= 3` passe.
`tokens[1]` vaut `"ERR"`, différent de `"0"`.

⇒ **`value = 100`, `old_value = 0`, `emitChange()`. L'état publié est « allumé, 100 % »** — `WODali`
dérive de `OutputLightDimmer` (`WODali.h:24,30`). Et `StartReadRules::ioRead()` (`WODali.cpp:125`)
rend son jeton comme si la lecture avait réussi : rien, nulle part, ne dit que l'état est inconnu.

⚠️ **Deux corrections à apporter au § *What `calaos_server` needs to implement* de la spécification**,
qui ne changent pas la conduite mais changent le geste :

- le champ testé n'est pas « le premier champ » mais **`tokens[1]`**, le premier **après le verbe** ;
- il n'y a **aucune conversion numérique** sur ce chemin : c'est une comparaison de chaînes contre
  `"0"`. « Tester avant toute conversion numérique » décrit une conversion qui n'existe pas ; ce
  qu'il faut, c'est un test **avant** cette comparaison-là.

### 2.3 Un second consommateur, plus discret

`WODaliRVB::WagoUDPCommandRed_cb()` / `Green_cb` / `Blue_cb` (`WODaliRVB.cpp:104-165`) lisent
`tokens[2]` — donc **la raison** — par `from_string()`, puis appellent `checkReadState()`. Un
`<reason>` n'est pas un nombre ; la couleur est publiée quand même. ⛔ Ce que `from_string()` laisse
dans `red`/`green`/`blue` sur un jeton non numérique n'est **pas mesuré**.
(`WODaliRVB::WagoUDPCommand_cb()`, `WODaliRVB.cpp:178-186`, ne lit rien du tout en cas de succès : ce
n'est pas un chemin de lecture d'état.)

## 3. Ce qui est DÉDUIT

- **La chaîne `ERR` → 100 → « allumé » est une déduction de trois lignes**, pas une mesure : aucun cas
  du dépôt ne fait entrer une réponse `ERR`. Elle est courte et sans branche cachée, mais elle reste
  une lecture.
- ⭐ **Le lien avec la « Lumiere SAS ».** [T3.156](T3.156.md) §3 posait déjà l'ancre sur cette même
  ligne — « `WODali.cpp` ne lit **jamais un niveau** […] tout ce qui n'est pas exactement `"0"`
  devient allumé à 100 % ». (Son ancre `WODali.cpp:100-107` a dérivé : elle est aujourd'hui
  `:107-119`.) `T3.156` a supprimé **une** façon de rendre la valeur fausse — le drapeau de groupe
  perdu ; elle n'a pas touché la lecture qui transforme tout non-`"0"` en 100. La 4.0 introduit un
  **second producteur de la même forme** : une réponse hors du domaine des valeurs, lue comme un état.
  Troisième passage sur la même arête après `-1` et `0`.

## 4. Ce qu'un correctif doit faire — et ce qu'il ne doit pas faire

1. Dans `WODali::WagoUDPCommand_cb()`, tester `tokens[1] == "ERR"` **avant** la comparaison à `"0"`,
   et rejoindre la branche d'échec existante (`WODali.cpp:95-101`) : journaliser la raison
   (`tokens[2]`), rendre le jeton `StartReadRules`, et ⛔ **ne pas** appeler `emitChange()`. Un état
   inconnu doit rester l'état précédent, pas devenir un état.
2. `WODaliRVB` doit être traité dans le même geste, sinon il gardera silencieusement son canal.
3. ⭐ **Le verrou de version : TRANCHÉ par l'utilisateur, il n'y en a pas.** `ERR` n'appartient au
   domaine de valeurs d'**aucune** version, donc le lire comme un niveau est faux partout, et un
   verrou aurait laissé passer un automate intermédiaire ou tiers émettant la même forme.
   `plcDaliGetCarriesGroup()` répond de toute façon à une autre question (seuil 3.0) et n'est pas
   réemployée. Le cas `AnErrorReplyIsRefusedWhateverVersionWasAnnounced` épingle l'absence de verrou
   en jouant 2.3, 3.0, 4.0 et un automate qui n'a **rien** annoncé.
4. ⛔ **Ne pas ajouter de verbe dédié côté automate** sans lever d'abord le filtre de §2.1 — vérifié,
   la spécification a raison sur ce point.

## 5. Ce qu'un cas devra PROUVER, et les façons dont il pourrait mentir

**À prouver** : une réponse `WAGO_DALI_GET ERR GROUP_UNSUPPORTED`, entrée par le vrai chemin
(`WagoMap::udpRequest_cb(true, …)`, comme le fait déjà le harnais de `WagoDaliGetGroup_test`), laisse
l'IO dans **le même état publié** qu'une expiration, et rend **exactement un** jeton `StartReadRules`.

Les mensonges à fermer nommément :

- ⭐⭐ **Un capteur qui ne mesure rien passe pour un capteur qui ne trouve rien.** Si la trame est
  jetée en amont — par le filtre de §2.1, ou parce qu'elle ne satisfait pas la garde `tokens.size()
  >= 3` — rien n'atteint la comparaison et le cas est vert **pour la mauvaise raison**. Le cas doit
  d'abord prouver que la réponse **est arrivée** : exiger le rouge sur le code non corrigé, ou
  asséner la ligne de journal qui **nomme la raison**.
- **Asséner sur `value` seul.** `value` part à 0 : un cas qui attend `0` passe aussi sur un IO qui n'a
  jamais reçu sa réponse. Il faut une trace **positive** (raison journalisée, jeton consommé), pas
  seulement l'absence de 100.
- **Écrire la trame attendue à la main** au lieu de laisser le code la construire : cela prouve la
  chaîne du test, pas celle du serveur.
- **Un verrou de version non épinglé.** Si le verrou de §4.3 est retenu, le cas doit fixer la version
  annoncée et avoir un jumeau à 3.0 ; sans cela il est vert quelle que soit la version.
- **Mutants qui doivent rougir** : le test déplacé **après** la comparaison à `"0"` ; `"ERR"` remplacé
  par `"ERROR"` ; le `emitChange()` laissé en place dans la branche d'erreur.

## 6. ⛔ LE NU

- ⛔⭐ **Aucun automate n'émettra jamais cette réponse ici.** Les `.pro` de `calaos_wago` sont des
  **binaires CoDeSys** et **personne dans ce dépôt ne peut exécuter un automate**. Que le programme
  4.0 renvoie effectivement `WAGO_DALI_GET ERR GROUP_UNSUPPORTED`, sur ce bus, dans cette situation,
  est **la parole de l'utilisateur et de sa spécification** — ce n'est pas vérifiable ici et ne le
  sera jamais. Tout cas injectera la trame lui-même.
- ✅ **MESURÉE depuis** : la chaîne `ERR` → 100 → « allumé » est rouge sous `CM1` et sous `CM3` (§0),
  donc l'arbre non corrigé publie bien cet état. Ce n'est plus une lecture.
- ⛔ **`GROUP_UNSUPPORTED` est la seule raison connue.** Rien ne borne celles à venir ; un test sur
  `tokens[1]` les accepte toutes, ce qui est l'intention, mais aucun cas ne peut les énumérer.
- ✅ **MESURÉ depuis** : `from_string()` publie **0** dans le canal sur un jeton non numérique, ce qui
  détruit le `-1` « pas encore lu » et fait publier à `checkReadState()` une couleur d'état **faux**
  (§0). Ce n'est plus du Nu.
- ⛔ **L'installation réelle n'est pas atteignable.** Que la « Lumiere SAS » et ce chemin soient le
  même défaut est une inférence **de forme**, pas une reproduction.
- ✅ **L'arbitrage du verrou de version est tranché** : il n'y en a pas (§0, §4.3).
- ⛔ **Un refus SANS raison** (`WAGO_DALI_GET ERR`, deux champs) est bien refusé par le code livré,
  mais **aucun oracle de cet arbre ne le sépare** de l'ancien comportement : la garde `>= 3`
  laissait déjà le luminaire tranquille sur une trame à deux champs. Le cas est **absent** plutôt
  que vert pour la mauvaise raison.

## 7. Ce que la sérialisation garantit — l'argument de conception, vérifié

La spécification s'appuie sur deux affirmations pour dire qu'une erreur coûte moins cher qu'un
silence. Les deux tiennent, avec une nuance :

- `WagoMap::UDPCommand_cb()` (`WagoMap.cpp:602-628`) sort immédiatement si la tête de file est
  `inProgress` (`:604`), pose `inProgress` avant d'émettre (`:617`), et `udpRequest_cb()` ne dépile
  que sur réponse ou expiration (`WagoMap.cpp:592`). ⇒ **une seule commande en attente de réponse à la
  fois.**
- ⚠️ **Nuance** : une commande `no_callback` — les `WAGO_DALI_SET`, le battement — est dépilée **dès
  l'envoi** (`WagoMap.cpp:627-628`) et **n'arme aucun délai** (`:621`). La sérialisation vaut donc pour
  les commandes **qui attendent une réponse**, pas pour toutes.
- Le délai est `Timer(2.0, …UDPCommandTimeout_cb)` (`WagoMap.cpp:622`), et l'expiration rejoue
  `udpRequest_cb(false, "")` (`WagoMap.cpp:595-600`). ⇒ **une lecture sans réponse bloque la file 2 s**,
  confirmé. Répondre une erreur est bien strictement moins cher que se taire.
