# T3.81 — deux secrets journalisés **hors de l'argv de lancement**, dont un au niveau imprimé par défaut

**Statut** : 📋 · **Type** : fix (sécurité, hygiène de journal) · **Phase** : 3 · **Dépend de** : —
**Origine** : trouvés en mesurant [`T3.79`](T3.79.md) §4, en balayant l'arbre pour la question
« y a-t-il d'autres endroits où la même configuration est journalisée ? ». **Fichés, PAS corrigés** :
ni l'un ni l'autre n'est sur le chemin de lancement d'un sidecar, qui était le périmètre de T3.79.

---

## 1. ⭐ `Audio/AVRRose.cpp:126` — un jeton d'appareil, **au niveau imprimé par défaut**

```cpp
cInfoDom("hifirose") << "Registered with device, roseToken: " << roseToken;
```

`roseToken` est le jeton d'authentification que l'amplificateur Hifi Rose rend à l'enregistrement
(`AVRRose.cpp:123-124`) et que toutes les requêtes ultérieures portent
(`Audio/hifi_rose_API.md:82,141,293`). **Même gravité que le défaut fermé par T3.79** : `cInfoDom`
et `debug_level` à `4` par défaut (`src/lib/ConfigOptions.cpp:608`) ⇒ **la ligne part sur une
installation de série**, sans que personne ait rien allumé, et à **chaque** enregistrement.

⚠️ Contrairement au mot de passe MQTT, ce jeton n'est **pas** dans la configuration : il est obtenu
au vol. Le supprimer de la ligne ne coûte donc **aucun** diagnostic de configuration — savoir que
l'enregistrement a réussi suffit.

## 2. ⚠️ `IO/ExternProc.cpp`, `sendMessage()` — la charge utile sortante entière, à DEBUG

```cpp
cDebugDom("process") << "client writing data: " << data;
```

`data` est le message applicatif, quel qu'il soit. Pour Reolink, c'est le message
d'enregistrement de caméra, qui porte `username` et `password` **en clair**
(`IO/Reolink/ReolinkWire.h:85`).

⭐ **Ce qui rend ce site intéressant, c'est que les deux extrémités croient déjà le protéger** :
l'en-tête de `ReolinkWire.h` écrit « Never log the message itself », `ReolinkCtrl.cpp` répète
« camera password IN CLEAR: never log it, here or anywhere downstream », et le sidecar Python
**caviarde** vraiment (`IO/Reolink/ExternProcReolink_main.py:1606-1608`,
`"<redacted>" if k in ("username", "password")`). ⇒ **La consigne est écrite trois fois et le
transport générique la contredit**, parce qu'il ne sait pas ce qu'il transporte.

Niveau DEBUG, donc **pas** imprimé par défaut — mais c'est exactement l'objection que T3.79 §3.1
a tranchée par la mesure : DEBUG est ce qu'un utilisateur allume avant de coller son journal dans
un rapport de bogue public.

⚠️ **Site voisin, même famille** : `ExternProc.cpp` journalise aussi la charge utile **entrante**
(`cDebugDom("process") << "Got a new frame : " << currentFrame.getPayload()`), à DEBUG.

## 3. Ce qu'il faudrait épingler

- Aucun des deux ne peut être fermé « à la liste de noms sensibles » : c'est la mesure de
  [`T3.79`](T3.79.md) §2, et elle vaut ici aussi — le transport ne voit que des `std::string`.
  Pour le site 2, la forme qui reste vraie est celle de T3.79 : journaliser **la taille** de la
  charge utile, pas son contenu. `processData()` le fait déjà
  (`cDebugDom("process") << "Processing frame data " << data.size()`), ce qui est un précédent
  **dans le même fichier**.
- Le site 1 se ferme en retirant la valeur de la ligne.
- ⚠️ **Anti-vacuité obligatoire** dans les deux cas : le cas doit asserter d'abord que le domaine
  n'est pas muet au niveau visé, sinon un environnement plus silencieux le rendrait vert sans rien
  mesurer. Forme éprouvée : `ExternProcLogSecretTest.TheMqttBrokerPasswordNeverReachesTheLog`,
  qui exige de voir **au moins une ligne** avant de conclure qu'aucun secret n'y est — et dont la
  contre-mutation **M2** de T3.79 montre que cette garde mord.
- ⛔ Le harnais existe : `core/ExternProcLogSecret_test.cpp` capture `std::cout` autour d'un vrai
  contrôleur. Un `ReolinkCtrl` s'y construirait de la même façon ; `AVRRose` demande une réponse
  HTTP bouchonnée, ce qui est un travail distinct.
