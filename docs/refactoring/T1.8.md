## Findings

### F5 — major: rate-limit/ban bypassable via `X-Forwarded-For`
`auth.py::_source_ip` (`auth.py:34-38`) uses the client `X-Forwarded-For` header as the bucket key for the sliding-window rate-limiter and the ban-list. An attacker rotates `XFF` per request to evade both. Worse: the sidecar is only reachable through the C++ Unix-socket proxy (which does not forward a trustworthy IP) → without `XFF`, all requests share a single global bucket. The `_req_counts`/`_ban_until` dicts grow unbounded per (spoofable) IP. The bearer-token check is solid (`hmac.compare_digest`, `auth.py:81`) — only the throttling key is broken. **Fix:** do not trust `XFF` here; or have the C++ proxy inject a trusted client-IP header validated at the proxy hop. Bound the dicts.

### `extern_proc.py` quality
- `stop()` (`:115-116`) is **dead**: it sets `self._running = False` but the `run()` loop (`:89-114`) tests a local `quit_loop`, never `self._running` (uninitialized). The external process cannot be stopped cleanly.
- `:123` uses `sockfd.send()` instead of `sendall()` → partial writes silently truncate frames under load.

### `logger.py` quality
`CalaosLogger.should_log()` (`:62-64`) and `DOMAIN_LEVELS`/`DEFAULT_LEVEL` are defined but **never wired** — the root logger is forced to `DEBUG` (`:103`), so domain filtering (`CALAOS_LOG_DOMAINS`) is inert. Unit mismatch: `get_debug_level()` (Calaos level 1-4) compared to Python logging levels (10-50).

### Dependency pinning
`calaos_mcp` has **no** `requirements.txt`/`pyproject.toml`/`setup.py` despite importing `websockets`, `mcp`, `fastapi`, `uvicorn`. `calaos-python/setup.py` pins only `colorama>=0.4.4` (open). **Fix:** add `src/bin/calaos_mcp/pyproject.toml` with pinned deps.

> The MCP **client** (`client.py`) and tool argument validation (`tools/*.py`) are owned by **T1.16**, not here.

## Acceptance

- `stop()` works (loop tests the right flag); `sendall()` used.
- Domain filtering effective, or the dead code removed.
- `pyproject.toml` present with pinned versions.
