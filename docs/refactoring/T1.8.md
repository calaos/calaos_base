## Constats

### F5 — majeur : rate-limit/ban contournable via `X-Forwarded-For`
`auth.py:_source_ip` (`auth.py:34-38`) prend le header client `X-Forwarded-For` comme clé de bucket pour le rate-limiter à fenêtre glissante et la ban-list. Un attaquant fait tourner `XFF` par requête pour échapper aux deux. Pire : le sidecar n'est atteint que via le proxy C++ Unix-socket (qui ne transmet pas d'IP fiable) → sans `XFF`, toutes les requêtes partagent un seul bucket (global). Les dicts `_req_counts`/`_ban_until` croissent sans borne par IP (spoofable).
Le check du bearer-token est solide (`hmac.compare_digest`, `auth.py:81`) — seule la clé de throttling est cassée.
**Remédiation** : ne pas truster `XFF` ici ; ou faire injecter par le proxy C++ un header d'IP client de confiance validé au hop proxy. Borner les dicts.

### Qualité `extern_proc.py`
- `stop()` (`:115-116`) est **mort** : il pose `self._running = False` mais la boucle `run()` (`:89-114`) teste une locale `quit_loop`, jamais `self._running` (non initialisé). Le process externe ne peut pas être arrêté proprement.
- `:123` utilise `sockfd.send()` au lieu de `sendall()` → writes partiels tronquent silencieusement les frames sous charge.

### Qualité `logger.py`
`CalaosLogger.should_log()` (`:62-64`) et `DOMAIN_LEVELS`/`DEFAULT_LEVEL` sont définis mais **jamais câblés** — le root logger est forcé à `DEBUG` (`:103`), donc le filtrage par domaine (`CALAOS_LOG_DOMAINS`) est inerte. Mismatch d'unités : `get_debug_level()` (niveau Calaos 1-4) comparé à des niveaux logging Python (10-50).

### Pinning des dépendances
`calaos_mcp` n'a **aucun** `requirements.txt`/`pyproject.toml`/`setup.py` malgré l'import de `websockets`, `mcp`, `fastapi`, `uvicorn`. `calaos-python/setup.py` ne pin que `colorama>=0.4.4` (ouvert).
**Remédiation** : ajouter `src/bin/calaos_mcp/pyproject.toml` avec deps pinnées.
