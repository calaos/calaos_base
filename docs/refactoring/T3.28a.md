# T3.28a — un `host` Roon contenant un **espace** met le sidecar en boucle de relance à 100 ms

**Statut** : 📋 · **Type** : fix (robustesse) · **Phase** : 3 · **Dépend de** : —
**Origine** : trouvé par la **revue de T3.28** (2026-08-25) en relisant `RoonArgs::buildArgs()`.
⚠️ **Pré-existant. Ni introduit ni aggravé par T3.28** — le ticket n'a fait que *déplacer* la
concaténation fautive, ce qui la rend pour la première fois testable.
**Fiché, pas corrigé** : hors périmètre de T3.28, qui traitait le port et le respawn.

---

## 1. Le défaut, mesuré

`Audio/RoonArgs.h` assemble la ligne de commande par concaténation **sans protéger `host`** :

```cpp
return " --host " + host + " --port " + Utils::to_string(port);
```

`ExternProcServer::startProcess()` (`IO/ExternProc.cpp:184`) recompose une chaîne unique puis la
**redécoupe sur l'espace** :

```cpp
string cmd = process + " --socket " + sockpath + " --namespace " + name + " " + args;
...
Utils::CStrArray arr(cmd);                       // StringUtils.cpp:379-383 : split(str, m_strings, " ")
process_exe->spawn(arr.at(0), arr.data(), env.data());
```

Il n'y a **ni quoting, ni échappement, ni `execv` sur un vecteur construit d'avance** : tout
espace présent dans `host` devient une **frontière d'argument**.

Un `host` valant `mon core` (une faute de frappe suffit) produit donc :

```
calaos_roon --socket … --namespace roon --host mon core --port 9330
                                                    ^^^^ argv en trop
```

`ExternProcRoon_main.py:36-45` appelle `parser.parse_args()` sans `parse_known_args()` :
`argparse` répond `error: unrecognized arguments: core` et **sort en `SystemExit(2)`**
(reproduit : `rc = 2`).

## 2. Pourquoi c'est une boucle et pas une simple panne

`ExternProc.cpp:187-199` : l'`ExitEvent` **comme** l'`ErrorEvent` réarment le lancement par

```cpp
Timer::singleShot(0.1, [this]() { processExited.emit(); });
```

et `RoonCtrl` relance sans aucun **backoff** — le trou déjà recensé sur **sept contrôleurs sur
huit** (`FINDINGS.md`, E4.5d, « Sept contrôleurs sur huit respawnent leur sous-processus sans
aucun délai »). Le sidecar meurt en quelques millisecondes, est relancé 100 ms
plus tard, remeurt : `calaos_server` enchaîne **~10 `fork`/`exec` par seconde**, indéfiniment,
tant que la configuration reste en place. Chacun écrit une ligne de log.

## 3. Portée, et ce que ce n'est pas

- **Ce n'est pas une escalade de privilèges.** Le champ vient de `calaos_installer`, donc d'un
  compte qui peut déjà écrire `io.xml` — c'est-à-dire déjà tout faire.
- **C'est un déni de service par faute de frappe**, et c'est ce qui le rend digne d'un ticket :
  la configuration est acceptée sans un mot, l'installateur n'affiche aucune erreur, et le
  symptôme observé est « Roon ne marche pas » avec un log qui défile.
- **Aucune injection d'option n'est atteignable au-delà de `calaos_roon` lui-même** : les argv
  supplémentaires sont refusés par `argparse` avant toute action. Un `host` valant
  `1.2.3.4 --list` ferait cependant démarrer le sidecar dans un **mode différent** de celui
  demandé — `--list` est accepté (`:41`), mais `:52-53` le refuse en présence de `--socket`, donc
  ce chemin retombe lui aussi sur `SystemExit(2)`. Non exploitable **aujourd'hui** ; ce qui tient
  cette conclusion est la table d'options du sidecar, pas le C++.

## 4. Les trois corrections possibles, et laquelle est la bonne

| # | Où | Ce que ça fait | Verdict |
|---|---|---|---|
| 1 | `RoonArgs::buildArgs()` | refuser un `host` contenant un blanc (retour vide ⇒ autodétection) + log | ⭐ **le moins cher, testable immédiatement** par `tests/core/RoonArgs_test.cpp` |
| 2 | `RoonPlayer` / ioDoc | valider le champ à la lecture de la configuration, remonter l'erreur | complémentaire, plus visible pour l'utilisateur |
| 3 | `ExternProcServer` | passer un `vector<string>` d'arguments au lieu d'une chaîne à redécouper | ⭐⭐ **la vraie correction**, mais elle touche **les six** sidecars et mérite son propre ticket |

⚠️ **(1) et (3) ne s'excluent pas et (1) n'est pas un substitut.** `buildArgs()` n'est qu'un
émetteur parmi d'autres : le même défaut de conception attend dans chaque `startProcess()` de
l'arbre dont un argument vient de la configuration. Corriger (1) ferme **ce** chemin ; seul (3)
ferme la classe.

## 5. Ce qu'il faudra épingler

- `buildArgs("mon core", 9330)` → **pas** de `--host` coupé en deux (forme exacte à décider avec
  la correction retenue).
- Le cas nominal `buildArgs("192.168.7.42", 9331)` doit rester **byte pour byte** celui que
  `AStaticHostCarriesBothFlags` fige déjà.
- ⛔ **Rien de tout cela n'a été essayé sur un core Roon réel**, comme pour T3.28.
