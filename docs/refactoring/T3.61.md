## Le défaut, tel qu'il était

Le marqueur qui décidait qu'un IO scénario **est** un auto-scénario était l'ancien
`auto_scenario`, pas l'uid :

- `IO/Scenario.cpp:60` — `if (get_param("auto_scenario") != "")` construisait l'`AutoScenario` ;
- `Calaos::get_new_scenario_id()` (`Calaos.cpp:48`) survivait avec son **unique** appelant
  `JsonApi.cpp:2450`, qui frappait `auto_scenario` sur un scénario neuf.

Conséquence : les 4 anciens scénarios de `configs/raoulh` restaient des auto-scénarios et
apparaissaient dans `autoscenario list`. L'affirmation de §1.1 d'`E4.6.md` — « les anciens
scénarios cessent d'être reconnus » — n'était vraie qu'après ce ticket.

## Ce qui a été fait

| | |
|---|---|
| `IO/Scenario.cpp` | le marqueur est `AutoScenarioDef::KEY_UID`, et rien d'autre — **aucun repli** sur la clé historique |
| `Scenario/AutoScenario.cpp` | `scenario_id` est lu au même param ⇒ les ids de machinerie deviennent `<uid>_step` & co. |
| `JsonApi.cpp` | `buildAutoscenarioCreate()` alloue l'uid directement (`AutoScenarioDef::newUid()`) |
| `Calaos.{h,cpp}` | `get_new_scenario_id()` **supprimé**, son unique appelant n'existe plus |
| ioDoc | le param documenté par l'IO scénario est `autoscenario_uid` |

**Hors périmètre déclaré** : `Scenario/AutoScenario.{h,cpp}` et `Calaos.{h,cpp}`. Le premier parce
que `scenario_id` y est lu et qu'il est le **préfixe des ids dérivés** — re-cléer l'un sans l'autre
laisse un scénario dont la machinerie est nommée d'après rien ; le second parce que
`get_new_scenario_id()` y vit.

⛔ **Délibérément NON re-clé** : `AutoScenario::createInput()` frappe toujours la machinerie avec
`auto_scenario`. Personne ne le lit, c'est ce que §5.3 décrit comme l'état de production, et le
déplacer dans le namespace publié le mettrait sur le fil (`buildJsonIO()` publie `KEY_UID`) et
ferait bouger les goldens `get_home`/`get_io` pour rien.
