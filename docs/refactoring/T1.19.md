## Findings

### Major — error-handling: `MySensorsController::sendMessage` dereferences a possibly-null handle
`MySensorsController.cpp:482` — `sendMessage()` writes to the serial/TCP handle without checking it is non-null; during reconnect (or before the transport is established) the handle can still be null → crash. **Fix:** null-check the handle and drop/queue the message when the transport is down.

### Major — lifetime: inverted fd-close guard leaks the GPIO value fd
`GpioCtrl.cpp:46` — `if (fd == -1) close(fd); fd = -1;` — `close()` runs only when `fd` is already `-1` (a no-op `close(-1)`); a valid open fd is **never** closed → leak. **Fix:** invert to `if (fd != -1) close(fd);`.

### Minor — edge-case: `WebCtrl::getValueText` indexes `tokens[0]` without a non-empty check
`WebCtrl.cpp:289` — `Utils::split(path, tokens, "/"); Utils::from_string(tokens[0], line_nb);` — `split` with `max=0` does not pad, so an empty/delimiter-only `path` yields an empty vector and `tokens[0]` is out of range. **Fix:** return early (or log) when `tokens.empty()` before indexing `tokens[0]`.

## Acceptance
- MySensors `sendMessage` during reconnect (null handle) → no crash.
- A GPIO controller destructor actually closes the value fd (no fd leak).
- Empty/malformed Web path → handled, no OOB access.
