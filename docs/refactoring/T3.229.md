# T3.229 — un transfert avorté est remis à l'appelant comme un succès HTTP 200

**Statut** : 📋 · **Type** : fix · **Phase** : 3
**Origine** : [T3.174](T3.174.md) — mesuré en vérifiant que la borne de stagnation mord.

---

## 1. Le fait, mesuré

Le relais de flux joué par `TheSameCorridorStillCutsOffATransferThatAskedForNoExemption` est
**coupé à 36,3 s** par la borne de stagnation, avec une seule des deux trames reçues. Une
assertion `EXPECT_NE(200, rep.status)` posée sur ce cas **rougit** : ce que l'appelant reçoit est

```
m_signalCompleteData(<corps tronqué>, 200)
```

**Pourquoi** : `UrlDownloaderCurlManager` lit le `CURLcode` du transfert, s'en sert pour écrire
`Transfer failed for …` (`src/lib/UrlDownloader.cpp:333-344`) — **puis le jette**. Ce qui est passé
à `transferDone()` (`:349`) est seulement `CURLINFO_RESPONSE_CODE`. `transferDone()` préfère le
code de la ligne de statut réellement parsée (`:777-779`), et `completeCb()` émet le couple
`(corps, statusCode)` (`:801`) **exactement de la même façon** qu'après un transfert entier.

⇒ Le `CURLcode` **n'atteint jamais l'appelant**. L'échec ne vit que dans le journal.

## 2. Pourquoi ça compte, et pourquoi maintenant

Les vingt appelants de `UrlDownloader` décident sur ce couple. Un instantané de caméra tronqué, un
JSON d'ampli coupé au milieu, une réponse InfluxDB partielle **arrivent avec `200`** et sont
traités comme des réponses. Un parseur JSON refusera le tronçon, mais une image ne le fera pas, et
`ActionCameraDownload` écrit dans un **fichier**.

⚠️ **Ce n'est pas un défaut de `T3.174`**, il préexiste. Mais avant `T3.174` un transfert avorté
était **rare** (il fallait une erreur de transport franche) ; depuis, **toute** stagnation de plus
de trente secondes produit ce chemin. Le défaut est passé d'improbable à **atteignable**.

## 3. Ce qui est demandé

Faire remonter l'échec. La **mécanique** est petite : porter le `CURLcode` (ou un simple booléen)
jusqu'à `transferDone()` et l'exposer. ⛔ **La décision ne l'est pas**, et c'est pourquoi ce ticket
n'est pas un nettoyage :

- que doit valoir `statusCode` quand les en-têtes disaient `200` et que le corps est tronqué ?
  `0` casse les appelants qui testent `== 200` ; `200` est le défaut actuel et mensonger ;
- faut-il **livrer** un corps tronqué du tout ?
- les **vingt** appelants doivent ensuite être relus un par un ; aucun ne sait aujourd'hui poser la
  question.

⇒ **Non trivial**, non par volume de code mais par nombre de décisions et d'appelants à revoir.

## 4. Le Nu

⛔ **Aucune conséquence réelle n'a été observée** : aucun instantané corrompu, aucun fichier
tronqué sur une installation. Ce qui est mesuré, c'est le **couple remis à l'appelant**, pas ce
qu'un appelant en fait.
⛔ **Un seul appelant a été joué** : la fixture de la suite. Les dix-neuf autres n'ont pas été
relus pour savoir lesquels sont réellement trompés.
⛔ **Le chemin `downloadToFile`** (`m_signalComplete` seul, sans corps) n'a pas été mesuré ; il
porte la même ambiguïté de statut.
