## Fichiers possédés
- `lib/UrlDownloader.{cpp,h}`

## Constat
`lib/UrlDownloader.cpp` **fork le binaire `curl`** au lieu d'utiliser libcurl : `:80` pousse `"curl"` dans un argv et `:203` `exeCurl->spawn(arr.at(0), arr.data())` via `uvw::ProcessHandle`. C'est async (non bloquant) mais :
- crée une **dépendance runtime au binaire `curl`** dans le PATH ;
- alors que `configure.ac:52` exige `libcurl >= 7.20.0` comme dépendance de link **que le code applicatif n'appelle jamais** (seul `lib/libquickmail/` utilise libcurl directement).

Ce chemin couvre tout HTTP (snapshots IPCam, contrôle Foscam/Hue, firmware). Autres points :
- `:83` ajoute **toujours** `--insecure` (pas de vérif TLS) → tout téléchargement HTTPS est MITM-able (justifié pour caméras auto-signées, mais appliqué globalement).
- `:129-134` passe `--user u:pass` → credentials visibles via `ps`/`/proc`.

## Remédiation
- Migrer vers **libcurl-multi** (async, intégrable à la loop libuv) — libcurl est déjà lié.
- `--insecure` → opt-in par caméra/hôte (défaut = vérif TLS activée).
- Credentials via l'API libcurl (`CURLOPT_USERPWD`), pas en argv.
- Alternative si libcurl-multi jugé trop lourd : documenter/isoler explicitement le contrat « binaire curl » et supprimer la dépendance libcurl inutile du link applicatif.

## Acceptance
- Téléchargement caméra/firmware fonctionnel **sans** dépendance au binaire `curl`.
- TLS vérifié par défaut ; insecure opt-in explicite.
- Credentials hors ligne de commande.

## Vérification
Test de download (snapshot caméra HTTP + HTTPS auto-signée avec opt-in) ; `ps` ne montre plus de credentials ; retirer le binaire `curl` du PATH de test et confirmer que les downloads marchent toujours.
