## 1. Les deux défauts, revérifiés au source (2026-08-25)

### ⚠️ Deux numéros de ligne de `FINDINGS.md` ont dérivé

`FINDINGS.md:2456` cite `RoonPlayer.cpp:174` pour le `paramAdd`, et `:2458` cite `:179` pour le
`from_string`. **Sur master (`db6770a7`) c'est `:180` et `:185`** — décalage de **+6**, dû au bloc
de commentaire de six lignes qu'E4.1g a inséré à `:159-164`. Corrigé dans `FINDINGS.md` par ce
ticket. Le reste des références (`IODoc.h:46`, `RoonPlayer.cpp:43`, `:46-48`, `:39-50`) est
**exact**.

### (a) `port` : un entier dans le paramètre `bool`

`IO/IODoc.h:46` :
```cpp
void paramAdd(const string &name, const string &description, ParamType type, bool mandatory,
              const string defaultval = string(), bool readonly = false);
```

`Audio/RoonPlayer.cpp:180` :
```cpp
ioDoc->paramAdd("port", _("Static Roon server port, empty to autodetect on network"),
                IODoc::TYPE_INT, 9330);
```

`9330` occupe la place de **`mandatory`** ⇒ conversion implicite vers `true`, **sans un seul
avertissement**, et `defaultval` reste **`""`**. Le port est donc déclaré **obligatoire et sans
défaut** dans l'ioDoc — c'est-à-dire dans ce que `calaos_installer` affiche à l'utilisateur.

Puis `:185` :
```cpp
Utils::from_string(param["port"], port);
```

⛔ **Et ici `FINDINGS.md:2458-2459` se trompe** : elle écrit « `Utils::from_string("")` laisse
`port` à **0** ». **Non.** `RoonPlayer.h:214` déclare `int port;` — **sans initialiseur en-classe**,
et la liste d'initialisation du constructeur (`:172-173`) ne porte que `AudioPlayer(p)`. Sur une
chaîne vide, `from_string` **n'écrit rien** (voir **T3.25**) : `port` est **indéterminé**, pas nul.

⇒ `RoonCtrl::Instance(host, port)` (`:194`) reçoit une valeur arbitraire, et `RoonCtrl` la
recopie dans les arguments (`:46-48`) :
```cpp
    string args;
    if (!host.empty())
        args += " --host " + host + " --port " + Utils::to_string(port);
```

**Le `--port` transmis au sidecar est du bruit mémoire.** Le défaut `9330` n'existe que côté
Python, **et seulement quand le drapeau est absent** — ce qui n'arrive jamais dès que `host` est
renseigné.

### (b) Le respawn perd tous les arguments

`Audio/RoonPlayer.cpp:39-50` :
```cpp
    process->processExited.connect([=]()
    {
        cWarningDom("roon") << "process exited, restarting...";
        process->startProcess(exe, "roon");        // ← :43, SANS args
    });

    string args;
    if (!host.empty())
        args += " --host " + host + " --port " + Utils::to_string(port);

    process->startProcess(exe, "roon", args);      // ← :50, AVEC args
```

Le lambda ne capture pas `args` (il est construit **après**), et le `startProcess` du handler ne
le repasse pas. **Dès le premier redémarrage**, le sidecar retombe sur la découverte automatique
`RoonDiscovery` (`ExternProcRoon_main.py:75-83`) au lieu du core configuré.

## 2. ⚠️ « Roon est inutilisable » — l'affirmation est FORTE, et la mesure la NUANCE

`FINDINGS.md:2466-2467` écrit : « **il est probable que l'intégration Roon soit inutilisable en
configuration à hôte statique aujourd'hui** ». **Vérifié au source, voici le partage exact :**

| Configuration | Ce qui se passe |
|---|---|
| **`host` vide** (autodétection — le cas par défaut annoncé par la description du paramètre) | `args` reste **vide**, aucun `--port` n'est passé, le sidecar autodétecte. ⇒ **Roon fonctionne.** (b) est même **inoffensif** : relancer sans args = relancer avec les mêmes args. |
| **`host` renseigné** (hôte statique) | `--port <indéterminé>` au 1ᵉʳ lancement ⇒ la connexion au core échoue presque sûrement ; puis (b) fait retomber le respawn en autodétection ⇒ **peut se rattraper tout seul**, sur un core éventuellement différent de celui configuré |

⇒ **la formule juste est : « l'hôte statique ne marche pas comme configuré »**, pas « Roon ne
fonctionne pas ». Le mode par défaut est intact. ⚠️ Et **`port` indéterminé** rend le
comportement **non reproductible** : rien n'interdit qu'il vaille accidentellement 9330.
**Aucun test sur matériel réel n'a été fait** — ni ici, ni dans les deux tickets d'origine.
`FINDINGS.md` annoté en conséquence.

**Lien avec T3.25** : (a) est un **exemplaire** du piège général `from_string`. Le corriger ici
ne dispense pas de T3.25 ; T3.25 ne dispense pas de corriger l'argument mal placé.
Les deux tickets sont **indépendants** et peuvent avancer en parallèle — `RoonPlayer.cpp` n'est
dans aucun lot de T3.25 §3(c).
