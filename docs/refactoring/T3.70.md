# T3.70 — `std::stoi` nu sur les attributs `x`/`y` d'un widget RemoteUI

> **État : ✅ LIVRÉE** (branche `fix/t3.70`, 3 commits : caractérisation **zéro ligne de `src/`**,
> correctif, doc ; **non poussée, non mergée**). Ouverte au merge de [T3.68](T3.68.md) sur
> `F-REMOTEUI-3` de [`FINDINGS.md`](FINDINGS.md).

## Le défaut

`RemoteUI::LoadFromXml()` (`src/bin/calaos_server/IO/RemoteUI/RemoteUI.cpp:213`) :

```cpp
if (attr_name == "x" || attr_name == "y")
    widget[attr_name] = std::stoi(attr_value);
```

## ⭐ Le mode d'échec, MESURÉ — ce n'est pas le widget qui tombe, c'est le serveur

La fiche d'ouverture parlait d'une exception « dans le chargement de la configuration ». Le chemin
a été suivi jusqu'au bout, et il n'y a **aucun `catch` nulle part dessus** :

| Maillon | `try` ? |
|---|---|
| `RemoteUI::LoadFromXml()` | non |
| `IOFactory::CreateIO(node)` (`IOFactory.cpp:65`) | non — un `unique_ptr` **détruit l'IO** au passage de l'exception |
| `Room::LoadFromXml()` (`Room.cpp:174`) | non |
| `Config::LoadConfigIO()` (`CalaosConfig.cpp:310`) | non |
| `main()` (`main.cpp:150`) | non — **`grep -c try main.cpp` = 0** |

⇒ `std::invalid_argument` sort de `main()`, `std::terminate()`, **le serveur n'atteint jamais sa
boucle d'événements**. Un `x=""` ou un `x="haut"` dans l'`io.xml` **met toute l'installation par
terre** : pas un écran, pas un widget — le domotique entier, chauffage et volets compris.

**Reproduit avant toute ligne de `src/`**, sur le vrai chemin (`Config::LoadConfigIO`, `Room`,
`IOFactory`), commit `baeb917a` :

```
Expected: loadIo(configWithBadX("haut")) doesn't throw an exception.
  Actual: it throws std::invalid_argument with description "stoi".
Expected: (remoteUi(DEV_BAD)) != (nullptr), actual: NULL
the screen holding the misspelled widget was lost whole
Expected: (remoteUi(DEV_AFTER)) != (nullptr), actual: NULL
the screen of the NEXT ROOM was lost too: the load stopped there
```

Les deux dernières lignes sont ce que les `EXPECT_NO_THROW` (et non `ASSERT_`) permettent de
mesurer : la victime n'est pas le widget, c'est **tout ce qui est déclaré après lui**.

## Le comportement retenu, et d'où il vient

**Le widget est écarté, et lui seul.** Ce n'est pas une convention neuve : c'est **celle du bloc
qui suit immédiatement**, écrit avant ce ticket —

```cpp
//Only add widget if it has a type and x/y positions
if (widget.contains("type") && widget.contains("x") && widget.contains("y"))
    widgets.push_back(widget);
else
    cWarningDom(TAG) << "... Ignoring widget with missing required attributes";
```

Le correctif se contente de **laisser l'attribut absent** quand la valeur n'est pas un entier
entier, ce qui fait tomber le widget dans ce chemin existant. `Utils::from_string_or_keep()` — le
même non-lançant que `getBrightness()`/`getTimeout()` de [T3.68](T3.68.md) — n'écrit la coordonnée
que si **toute** la chaîne se lit comme un entier.

Et c'est bien la convention de tout le chargement, pas d'un seul bloc : `IOFactory::CreateIO()`
avertit et ne crée rien sur un `type` inconnu, `Room::LoadFromXml()` ignore tout élément dont il ne
connaît pas le nom, `RulesFactory` laisse tomber une condition ou une action mal formée. **Élément
fautif écarté, le reste chargé.**

### L'alternative « position à 0 », écartée explicitement

Poser 0 ferait apparaître le widget **empilé sur le coin haut-gauche**, à un endroit que personne
n'a demandé, en recouvrant peut-être un autre widget — et sans rien pour distinguer ce 0 inventé
d'un `x="0"` légitime, qui est une position parfaitement valable (`JsonApiStateWireBytes_test:822`
en pose deux, et son golden les épingle). Un widget invisible qui se dit à sa place est pire qu'un
widget absent qui se dit absent.

### ⛔ Et surtout pas « garder la chaîne brute »

Mettre `attr_value` tel quel satisferait le `widget.contains("x")` du bloc voisin, et l'appareil
recevrait `"x": "haut"` là où il attend un nombre. **Changement de wire déguisé** : écarté.

## ⭐ Un widget écarté ne l'est plus en silence

Un widget écarté **ne revient pas** : le `SaveConfigIO()` suivant réécrit la page sans lui, et
l'`io.xml` de l'utilisateur perd la ligne. Le `cWarningDom` d'avant ne suffit pas — personne ne lit
le journal d'un serveur qui a démarré.

Le chargement de configuration a déjà un canal pour ça, celui de `loadXmlDocument()` (fichier
corrompu, E4.6f) et des règles désactivées faute d'IO (E4.6h) : `Config::reportConfigAlert()`,
qui diffère un mail + une notification push jusqu'à ce que la boucle tourne. Un `RemoteUI` qui
perd des widgets y dépose **un** message, nommant l'écran, la page et chaque widget :

```
Screen 't370_screen_bad' lost 1 widget(s) whose io.xml declaration is incomplete. They are
gone from the screen and will be gone from io.xml at the next save:
- widget 'thermostat' on io t370_io_broken of page 'Home'
```

⚠️ **Le cas préexistant en profite aussi** : un widget sans `type`, ou sans `x`/`y` du tout, était
déjà écarté — silencieusement depuis toujours. Après ce ticket il déclenche la même alerte. C'est
un élargissement assumé : les deux catégories partagent désormais le même chemin, et les
distinguer n'aurait servi qu'à garder un silence.

## Ce sur quoi le ticket reste nu

- ⚠️ **Le widget disparaît définitivement de l'`io.xml` au premier enregistrement**, comme le
  faisait déjà un widget sans `type`. L'alerte prévient, elle ne restaure pas. Conserver la ligne
  fautive telle quelle demanderait un modèle « attributs bruts non interprétés » que ce loader n'a
  pas, et le premier `SaveToXml()` la mangerait quand même.
- ⚠️ **`w`/`h` ne sont pas convertis** — ils restent des chaînes, comme avant. Le wire les porte
  donc en chaînes ; ce ticket ne le change pas (`SaveToXml()` les réécrit tels quels, et un
  micrologiciel déployé les lit ainsi).
- **Aucun `io.xml` réel porteur du défaut n'a été observé.** Le cas part d'un fichier construit
  pour, comme le demandait la fiche d'ouverture.
