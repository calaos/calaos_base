# T3.19 — `audio_db` : déréférencement de `nullptr`, plantage à distance

**Type** : fix (sec) · **Phase** : 3 · **Dépend de** : T3.17c (possède `JsonApi.cpp`)
**Origine** : heurté par T3.17b en écrivant son fake, caractérisé précisément par T3.17c.
**Préexistant** — introduit par aucun ticket de ce refactoring.

## Le bug

`AudioPlayer::database` est initialisé à **`nullptr`** (`AudioPlayer.cpp:28`) et `get_database()`
(`AudioPlayer.h:105`) le rend **brut, sans garde**.

`JsonApi.cpp:966` (`audioGetDbStats`) **et les 15 méthodes `audioDbGet*`** font
`player->get_database()->getXxx(...)` **sans aucun contrôle de nullité**.

`canDatabase()` apparaît **0 fois** dans `JsonApiHandlerHttp.cpp` et **0 fois** dans
`JsonApiHandlerWS.cpp` : aucun des deux transports ne filtre. Son unique occurrence
(`JsonApi.cpp:406`) se contente de **publier la capacité** dans `get_home` — l'information existe
donc, elle n'est simplement jamais consultée avant l'appel.

`Squeezebox.cpp:81` est le **seul endroit de tout l'arbre** qui assigne `database`.

## Le chemin d'exploitation — client authentifié, les deux transports

```json
{"msg":"audio_db","data":{"id":"<id d'un RoonPlayer>","audio_action":"get_artists",
                          "from":"0","count":"10"}}
```

`RoonPlayer::canDatabase()` est **faux** et son `database` est **nul** → **SIGSEGV de
`calaos_server`**. **Les 16 actions `audio_db` sont affectées.**

Ce n'est pas une entrée malformée : c'est un appel d'API **parfaitement légitime** sur un lecteur
qui n'a pas de base musicale. N'importe quelle UI qui propose la navigation musicale sans vérifier
`canDatabase()` au préalable fait tomber le serveur.

## Travail (fichier : `src/bin/calaos_server/JsonApi.cpp`)

Garder les 16 sites. **Décider et documenter la réponse** quand la base est absente — et prendre
la décision explicitement plutôt que par défaut :
- un `{"success":"false"}` (le vocabulaire déjà utilisé par le point d'entrée pour un id inconnu,
  cf. T3.17a), ou
- une réponse vide typée cohérente avec le contrat de liste existant.

⚠️ **Ne pas répondre une donnée mutilée**, et **ne pas** inventer une forme d'erreur nouvelle :
la série T3.17 a établi qu'on réutilise le vocabulaire existant.

⚠️ **Contrat de payload gelé** : E4.0f et T3.17c ont caractérisé ces réponses. Toute forme nouvelle
doit être répercutée dans leurs goldens **dans le même diff**, et signalée.

## Question ouverte à trancher dans le ticket

Faut-il **aussi** filtrer côté handlers sur `canDatabase()` ? Avantage : refus net et précoce,
symétrique de la capacité déjà publiée. Inconvénient : touche `JsonApiHandlerHttp.cpp` **et**
`JsonApiHandlerWS.cpp`, et ajoute deux chemins d'erreur que E4.0e a gelés. **Mesurer avant de
décider** ; la garde dans `JsonApi.cpp` seule suffit à supprimer le plantage.

## Extension (2026-08-17) — un SECOND plantage distant, même famille, même fichier

Découvert par E4.0e, confirmé par sa revue et par T3.17f, qui l'ont tous deux **délibérément évité**
en test (le signal tuerait le binaire). **À traiter dans ce ticket** : même fichier, même classe de
défaut — une entrée client non validée qui tue le serveur.

### Le bug

`JsonApi.cpp` (`buildJsonEventLog`) initialise `perPage = 100` puis appelle `Utils::from_string()`
**dont le code de retour est ignoré** (`StringUtils.h:105-111`). Sémantique C++11 d'`operator>>`,
**vérifiée empiriquement par deux agents indépendants** :

| `per_page` reçu | effet |
|---|---|
| **absent ou vide** | le sentry du flux échoue **avant** `num_get` → rien n'est écrit → **100 survit** (inoffensif) |
| **non vide et non numérique** (`"abc"`, `"1,5"`, `"true"`) | `num_get` s'exécute, échoue, et **écrit 0** |
| **`"0"`** | **écrit 0** |
| **très grand** (`"99999999999"`) | **sature à `INT_MAX`** (inoffensif) |

`HistLogger::getEvents()` ne clampe pas, et `HistLogger.cpp:269` calcule
`int start = ac->page * ac->per_page` puis `HistLogger.cpp:268` fait `rowcount / ac->per_page`
**dans le thread worker sqlite** → **division entière par zéro, SIGFPE, processus mort**.

⚠️ Le `try` de `HistLogger.cpp:257` **n'attrape rien** : un signal n'est pas une exception.

**Chemin d'exploitation** : `?action=eventlog&per_page=0` (ou `per_page=abc`) depuis n'importe quel
client **authentifié**, **sur les deux transports**. Contre-intuitif et c'est pourquoi personne ne
l'avait vu : une valeur **énorme** est inoffensive, une valeur **absurde** est fatale.

### Travail

Clamper `perPage` (et vérifier `page`) **avant** de le passer à `HistLogger`. Décider explicitement
de la réponse sur valeur invalide — et **réutiliser le vocabulaire existant**, ne pas inventer une
forme d'erreur nouvelle.

⚠️ **Contrat de payload gelé** : E4.0e (`JsonApiSession_test`) et T3.17f (`JsonApiEventLog_test`)
caractérisent ces réponses. Toute forme nouvelle doit être répercutée dans leurs goldens **dans le
même diff**, et signalée.

⚠️ **Le mécanisme est déjà épinglé** par `FromStringWritesZeroOnFailureWhichIsWhyEventLogCanDivideByZero`
(E4.0e) : si `from_string` cesse d'écrire 0, ce cas rougit et la prémisse est invalidée. **Ne le
casse pas** — adapte-le si ton correctif change la donne, en le disant.

### Preuve

Le crash **ne peut pas être exercé tel quel** : le SIGFPE tuerait le binaire de test. Deux voies
recevables — un test qui prouve le **clamp** (la valeur invalide n'atteint jamais `HistLogger` avec
0), ou un `EXPECT_EXIT`/sous-processus si tu démontres qu'il est fiable dans un fixture qui possède
un thread sqlite vivant. **Dis franchement laquelle tu retiens et pourquoi.**
