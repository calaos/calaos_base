## 2. Pourquoi ça compte pour les tripwires

T3.28 §6 justifie ses **deux tripwires de source** (`CALAOS_TOP_SRCDIR`, mécanisme de

laissait passer l'échange du 3ᵉ argument ; compter `int port =` laissait passer `int port = 0;`).

d'exécution.**

## 2. Les deux tripwires, instruites SÉPARÉMENT

**Vérifié par mutation, pas par lecture** : `int port = RoonArgs::DefaultPort;` ⇄ `int port = 0;`

découverte du §1 de cette fiche, et la tripwire reste le **seul** oracle possible de cette
propriété. Elle est conservée telle quelle.

### (b) ⭐⭐ `tests/core/RoonSpawnViaPlayer_test.cpp` — **LE SECOND BINAIRE**, 1 cas

**La revue a trouvé une mutation qui SURVIVAIT, et c'est le bug de terrain de `T3.28` déplacé d'un
site.** Sur le code **livré** :

```
RoonPlayer.cpp:227   RoonCtrl::Instance(host, port);
             ->      RoonCtrl::Instance(host, RoonArgs::DefaultPort);
```

⇒ `core/RoonArgs_test` restait à **14/14, sortie 0**. Un core statiquement configuré sur 9331
aurait été cherché sur **9330**, en silence, et tous les oracles de l'arbre auraient dit que le
ticket était fait.

**La cause est exactement celle que la première fiche invoquait pour ne pas le couvrir** :
`RoonCtrl::Instance()` est un **static de fonction** (`RoonPlayer.cpp:86`). Le **premier** appel
d'un processus gagne, les suivants rendent le même objet et **jettent leurs arguments**. Un
processus n'a donc **qu'une seule** occasion d'observer une configuration de lancement, et les deux
façons de la dépenser s'excluent :

| Forme | Ce qu'elle observe | Ce qui lui reste aveugle |
|---|---|---|
| appeler `Instance()` depuis le test | le constructeur de `RoonCtrl` et le **respawn** | `RoonPlayer.cpp:227` |
| construire un vrai `RoonPlayer` | **`RoonPlayer.cpp:227`**, le report de la configuration | rien du respawn n'est perdu : il tourne aussi |

⭐ **La fiche précédente en concluait « les deux formes s'excluent, j'ai gardé la plus sûre ». La
conclusion était fausse pour la même raison que celle de `T3.28` : un binaire de test EST un
processus.** `tests/Makefile.am` en compte 87 autres. Un second binaire donne au singleton un
processus **neuf** ; les deux formes sont couvertes **sans `fork`, sans couture, sans crochet de
test dans `src/`**. C'est la forme ordinaire de l'arbre, pas un dispositif.

- **Un seul cas, délibérément.** Un second cas voulant un contrôleur configuré autrement dans le
  même processus ramènerait le problème.
- Le `RoonPlayer` est **fuité exprès** : son constructeur arme `Timer::singleShot(10, [this]…)`
  (`:230-233`) — une **lambda**, donc `sigc::trackable` ne la déconnecte pas (`FINDINGS.md`, la
  distinction lambda / `mem_fun`). Le détruire pendant que la boucle peut encore la lancer est un
  use-after-free.
- **Mesuré : `MR4` rougit, et elle SEULE** (§5).
