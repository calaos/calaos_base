### 5.5 ⚠️ Ce que M1 et M5 ont appris, et qui contredit la première rédaction

**M1 dit que le `try` porte davantage que prévu.** Avec la garde déplacée *après* `erase`/`pop_back`,
le processus **survit** au `[` isolé : `ALonePathBracketDoesNotKillTheProcess` reste **vert**, seul
le message est faux. C'est que `Utils::from_string` **copie** `val` dans un `istringstream` — c'est
précisément là que naissait le `std::bad_alloc`, et le `try` le rattrape. Le commentaire de la
première rédaction (« *from_string ne peut pas lever pour un `int`* ») était **faux** et a été
corrigé dans le code.

**M5 dit qu'il est malgré tout redondant *étant donné la garde*** : ressorti du `try`, garde
conservée, la suite reste à **0 rouge**. C'est un **mutant équivalent, pas un trou de filet** — il
est donc **annoté dans le code plutôt que retiré** : il ferme la famille (tout ce qui touche à
l'index échoue désormais par l'unique chemin d'erreur de la branche).

⛔ **CORRECTION (T3.35b)** : le long commentaire qui portait cette explication dans les deux
parseurs a été **remplacé**, pas supprimé. La garde étant désormais une garde de **forme**, `val`
ne peut plus arriver avec une longueur sous-fluée : la parenthèse `try` couvre toujours **tout ce
qui touche à l'index** (analyse du jeton **et** `parent.at(idx)`), mais elle n'est plus la ligne de
défense contre le `bad_alloc` — la garde l'est, et de manière prouvée. La lecture de M5 reste
juste, sa conclusion aussi ; c'est sa **portée** qui change.

### 6.1 ⭐ Le problème déplacé — reproduit, pas repris sur parole

`MqttCtrl::getValue()` posait **`err = false` inconditionnellement** avant `getValueJson()`, qui
rend une chaîne vide sur **chacun** de ses échecs. Conséquence directe du correctif §3 : le
`battery_path` valant `[` ne tue plus le serveur, il **franchit** le `if (!err)` de l'appelant avec
`v == ""` et alimente

```c++
double rawValue;                                    // MqttCtrl.cpp, 3 sites
Utils::from_string(v, rawValue);                    // n'écrit RIEN sur une chaîne blanche
io->setStatusInfo(IOBase::StatusType::BatteryLevel, rawValue);
```

**Mesuré**, pas déduit. Deux mesures, toutes deux reproductibles :

1. `Utils::from_string("", d)` **laisse `d` intact** *et* **renvoie `true`** — le sentry du flux
   échoue avant `num_get`, mais le flux a bien atteint sa fin, donc `iss.eof()` est vrai. Le code de
   retour ne permet **pas** de détecter le cas. Contraste : `from_string("zz", i)` renvoie `false`
   **et écrit 0** (C++11, `num_get` stocke zéro à l'échec). C'est cette **asymétrie** qui est le
   piège, et elle est désormais un cas : `UtilsFromString.ABlankStringNeitherWritesTheDestinationNorReportsIt`.
2. La même forme de code, compilée avec **`-ftrivial-auto-var-init=pattern`** — l'instrumentation de
   GCC, donc déterministe, pas un pari sur la pile — publie un niveau de batterie de
   **≈ −5,3·10³⁰⁷ %**. Recette exacte, rejouable :
   `g++ -O2 -std=c++17 -ftrivial-auto-var-init=pattern repro.cpp`, où `repro.cpp` reproduit
   `from_string()` et le bloc batterie **à l'identique**.

⚠️ **Tel quel, c'était un troc défavorable.** Un plantage est visible, daté, diagnosticable. Un
niveau de batterie, un RSSI ou un uptime **inventés** ne le sont pas : ils remontent dans
l'interface et **les règles de l'utilisateur agissent dessus**. Le ticket échangeait un défaut
bruyant contre un défaut silencieux.

le dos du comportement gelé. Le refus se fait un cran plus loin, sur « est-ce un **nombre** ».

### 6.3 ⭐ `getValueColor()` — le site que T3.25 ne couvre pas, avec ou sans elle

```c++
double x, y; int b;          // non initialisés
err = true;
value = getValue(params, err, "topic_sub", "path_x");
if (…) { Utils::from_string(value, x); err = false; }   // ← efface err
```

`err` était le **OU** des trois lectures. `path_x` cassé + `path_y` bon ⇒ `err` faux ⇒
`fromXYBrightness()` reçoit un `x` **jamais écrit**. **Aucune réparation de `Utils::from_string()`
n'atteint ce site** : sur le chemin fautif, `from_string` n'est **même pas appelée**. Corrigé ici,
et seulement ici : `x`, `y`, `b` initialisés ; `err` devient le **ET** des trois (les trois
paramètres sont déclarés **obligatoires** dans l'ioDoc de `MqttOutputLightRGB`) ; et chaque valeur
doit être un **nombre**, pas seulement avoir été lue.

annonçait **4** :

|---|---|---|

### 6.4 ⭐ La garde vérifiait une **longueur**, le message annonçait une **forme**

`if (val.size() < 2)` + *« an array index must be written [n] »* ne sont pas la même phrase, et
`erase(0,1)` / `pop_back()` retirent le premier **et le dernier** caractère sans rien demander.
**Mesure sur `3db14a92`**, journal capturé :

| chemin | valeur rendue | journal |
|---|---|---|
| `weather/[/description` | `""` | *malformed array index [* |
| `weather/[5/description` | **`clear sky`** (élément 0) | **rien** |
| `weather/[12/description` | **`light rain`** (élément 1) | **rien** |
| `weather/[zz]/description` | `clear sky` | **rien** |
| `weather/[]/description` | `clear sky` | **rien** |

**Tranché : durcir la garde**, pas corriger le message — un message juste sur un code faux
laisserait la lecture fausse en place. La garde devient **`val.size() < 2 || val.back() != ']'`**,
c'est-à-dire la forme que le message promet. ⇒ **il ne reste pas de trou à ficher** (le renvoi
`T3.25`/`T3.37` envisagé est sans objet).

Et l'index est **décidé sur les deux branches** au lieu d'être laissé à ce que `from_string()`
abandonne. Les deux formes illisibles — `[]` (chaîne blanche, destination **non écrite**) et `[zz]`
(`num_get` écrit 0) — s'accordent désormais **délibérément** sur l'élément 0, valeur que T3.29 a
figée et sur laquelle une configuration réelle peut s'appuyer ; ce qui part, c'est le **silence**.

### 6.5 ⭐ Fixture pauvre : l'indication n'était assertée nulle part

`EXPECT_TRUE(logContains(log, "weather[0]"))` était satisfait par la **PREMIÈRE** ligne du
scénario — `subpath not found weather[0]`, imprimée juste au-dessus de l'indication. Supprimer
`suggestion.insert(...)` faisait donc proposer *« did you mean **weather[0]** ? »*, c'est-à-dire
**exactement le chemin fautif que l'utilisateur vient de taper** — et la suite restait à **0 rouge**.
Motif « fixture pauvre » de la série : **une assertion satisfaite par autre chose que ce qu'elle
prétend vérifier**.

L'aiguille devient **`"did you mean weather/[0]"`** : le `/` **est** tout le contenu du conseil.
Mutation **R2** rejouée après correction ⇒ **2 rouges** (`AGluedIndexIsAnsweredWithAHint`, une par
parseur), là où elle en donnait **0**.

**Balayage `python3` des autres assertions de la suite, sur les journaux RÉELLEMENT capturés** (11
scénarios instrumentés) :

- **un seul scénario de toute la suite émet plus d'une ligne de journal** — `weather[0]/description`
  (le « subpath not found » puis l'indication). ⇒ **aucune autre assertion ne PEUT être satisfaite
  par une ligne antérieure : le compte est 2**, les deux corrigées ci-dessus.
- famille voisine, distincte, **4 assertions** satisfaites par une **autre partie de la même
  ligne** — l'écho du `path` plutôt que le jeton : `"array index"` dans
  `ALonePathBracketIsLoggedAsAnError` (×2, **corrigée** en `"malformed array index ["`) et
  `"nosuchobject"` dans `APlainMissingKeyGetsNoHint` (×2, **laissée** : son objet réel est la paire
  d'`EXPECT_FALSE`, et là le chemin et le jeton sont le même texte).

### 6.6 ⭐ `int idx = 0` n'était retenu par aucun test — et ne peut pas l'être

Mutation **R1** du relecteur (`int idx = 0` → `int idx;`, **les deux fichiers**) : rejouée après
correctif, elle donne toujours **0 rouge, `exit 0`**. **Et c'est désormais correct** : l'index est
assigné sur **toutes** les branches, donc l'initialiseur est **mort**. R1 est un **mutant équivalent
par construction**, dit comme tel — et non plus une ligne présentée dans la fiche comme « une
correction mesurée » alors que rien ne l'épinglait.

Ce qui était censé être protégé — *« un index illisible lit l'élément 0, et le dit »* — est
maintenant épinglé par deux mutations qui **rougissent** :

- **R1v** (`idx = 0` → `idx = 1` dans la branche illisible, les deux fichiers) ⇒ **7 rouges**, dont
  `ANonNumericIndexSilentlyReadsElementZero`, l'acquis T3.29 que rien ne tenait déterministe avant ;
- **R1w** (l'avertissement supprimé) ⇒ **4 rouges**.

⚠️ **Un test ne peut pas détecter une lecture non initialisée de façon portable** ; la sortie n'est
pas d'écrire un test qui parie sur la pile, c'est de **rendre le code déterministe** et d'épingler
**ce qu'il décide**.
