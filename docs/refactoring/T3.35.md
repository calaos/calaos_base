## 1. Le plantage — mesuré, sur les deux parseurs

Un `path` de configuration valant exactement `[` (une faute de frappe) suffit :

| Étape | MQTT | Web |
|---|---|---|
| jeton reconnu comme index | `if (val[0] == '[')` | idem |
| `val.erase(0, 1)` | `val` devient **vide** | idem |
| `val.pop_back()` | **sous-flue le `size_t`** | idem |
| `Utils::from_string(val, idx)` | **`MqttCtrl.cpp:132` — HORS du `try`** | **`WebCtrl.cpp:202`** |

⇒ `std::bad_alloc` **s'échappe de `getValueJson()`**. Aucun `catch` sur toute la chaîne
(`getValue` → l'IO Mqtt → `main.cpp`) ⇒ **`std::terminate()`**.

⭐ **Ce n'est pas « de l'UB théorique », c'est un plantage déterministe**, reproduit sur les deux
pilotes. La première rédaction du finding disait « UB » et **sous-vendait gravement le défaut** ;
c'est corrigé dans `FINDINGS.md`.

⛔ **Aucun vecteur distant** : le `path` n'est jamais écrit par un client, seulement par
`calaos_installer`. Le déclencheur réaliste est **une faute de frappe dans un paramètre**.

## 2. Le message d'échec — l'« option C » de T3.29, instruite et décidée

T3.29 a tranché : **la doc avait tort, pas le code** — accepter aussi `weather[0]/description`
casserait les charges dont une clé s'**appelle** `action[0]`, ce qui existe (Zigbee2MQTT, mesuré).
Reste que l'utilisateur qui a copié l'ancienne syntaxe n'a **aucun moyen de comprendre**.

**Décision utilisateur (2026-08-25) : améliorer le message, dans le même ticket et le même
`catch`** — `MqttCtrl.cpp:151-155` et `WebCtrl.cpp:221-225`, 3-4 lignes chacun. Quand la recherche
de clé échoue sur un jeton qui **contient** `[`, journaliser en clair
*« did you mean `a/[0]/b` ? array indices are their own path segment »*.

⭐ **Le faux positif est IMPOSSIBLE PAR CONSTRUCTION, et c'est ce qui sépare l'option C de
l'option B** : on n'entre dans ce `catch` que si `parent.at(val)` a **déjà** échoué. Une charge
dont la clé s'appelle vraiment `action[0]` **n'y passe jamais** — elle a résolu. L'option C donne
l'aide sans rien casser, là où l'option B cassait en silence.

### 5.1 ⭐ Épingler un plantage sans figer d'UB

Le problème : lire une chaîne dont la longueur a sous-flué **est** de l'UB, et T3.29 avait raison de
refuser de le figer. La sortie est de **ne pas caractériser le comportement actuel** mais le
**chemin d'erreur qui devrait exister** — valeur vide, aucune exception, un avertissement qui nomme
le jeton, c'est-à-dire **exactement le contrat que tous les autres échecs de ce parseur honorent
déjà** (clé inconnue, index hors bornes, charge malformée). C'est une affirmation sur le
comportement voulu, pas sur le comportement observé : un rouge-avant-vert légitime.

**Le signal, mesuré sur le commit de caractérisation** (`3685dc7b`, build complet dans le conteneur) :

```
[  FAILED  ] MqttJsonPathTest.ALonePathBracketDoesNotKillTheProcess
[  FAILED  ] MqttJsonPathTest.ALonePathBracketIsLoggedAsAnError
[  FAILED  ] MqttJsonPathTest.AGluedIndexIsAnsweredWithAHint
[  FAILED  ] WebJsonPathTest.ALonePathBracketDoesNotKillTheProcess
[  FAILED  ] WebJsonPathTest.ALonePathBracketIsLoggedAsAnError
[  FAILED  ] WebJsonPathTest.AGluedIndexIsAnsweredWithAHint
FAIL JsonPathSyntax_test (exit status: 1)      <- 83 TESTS, 82 PASS, 1 FAIL
```

avec, en clair dans le journal : `Actual: it throws std::bad_alloc with description
"std::bad_alloc"`, **sur les deux parseurs**. ⚠️ **Ici gtest a rattrapé le `bad_alloc`** et a donc
produit des lignes `FAILED` ; ce n'est pas garanti — un binaire qui meurt n'en produit aucune. Le
signal exigé à chaque tour est donc le **code de sortie du binaire de test** (`exit status: 1`
avant, `exit status: 0` après), jamais l'absence de lignes rouges.

⚠️ **Ce qui n'est pas figé, et pourquoi** : le jeton `[]` (et non `[`) continue de lire l'**élément
0**. La garde le laisse passer volontairement pour que
`ANonNumericIndexSilentlyReadsElementZero` (acquis T3.29) tienne. Il n'est **pas** couvert par un
cas neuf : sur `master` son résultat dépendait d'un `int` **non initialisé**, donc indéterminé, et
un test l'aurait figé au hasard de la pile. Le correctif le rend **défini** (`int idx = 0`) sans
changer la valeur attendue ; le figer appartient à T3.25/T3.37.

### 5.2 ⭐ `AKeyReallySpelledThatWayGetsNoHint` — ce qu'il garde

Charge `kZigbeePayload`, calquée sur un vrai bouton Zigbee2MQTT : une **clé littéralement
nommée** `action[0]`, **et à côté un vrai tableau** `action`, plus un entier, un second entier et un
objet imbriqué.

- `action[0]` **résout** → `"single"`. `parent.at()` ne lève pas, le `catch` porteur de
  l'indication **n'est jamais atteint**, et le cas exige `EXPECT_EQ("", log)` : **rien du tout**
  n'est journalisé. Le faux positif n'est pas « improbable », il est **impossible par
  construction**.
- Sous **option B** (découper le jeton collé), `action[0]` rendrait `"hold"` — l'élément 0 du
  tableau voisin — **en silence**. La mutation **M4** le mesure : le cas rougit.

Il est doublé de `APlainMissingKeyGetsNoHint` : une clé absente **sans crochet** ne doit pas
recevoir d'indication, sinon celle-ci devient du bruit sur chaque faute de frappe et cesse d'être
lue.

**La diversité des CHAMPS est le filet**, pas la longueur du tableau : `battery` (entier),
`device/friendlyName` (objet imbriqué), `action/[0]` et `action/[1]` (deux éléments **non
substituables**) rendent visible une recherche qui atterrit à côté.

### 5.5 ⚠️ Ce que M1 et M5 ont appris, et qui contredit la première rédaction

**M1 dit que le `try` porte davantage que prévu.** Avec la garde déplacée *après* `erase`/`pop_back`,
le processus **survit** au `[` isolé : `ALonePathBracketDoesNotKillTheProcess` reste **vert**, seul
le message est faux. C'est que `Utils::from_string` **copie** `val` dans un `istringstream` — c'est
précisément là que naissait le `std::bad_alloc`, et le `try` le rattrape. Le commentaire de la
première rédaction (« *from_string ne peut pas lever pour un `int`* ») était **faux** et a été
corrigé dans le code.

**M5 dit qu'il est malgré tout redondant *étant donné la garde*** : ressorti du `try`, garde
conservée, la suite reste à **0 rouge**. C'est un **mutant équivalent, pas un trou de filet** — il
est donc **annoté dans le code plutôt que retiré** : il ferme la famille (tout ce qui touche à
l'index échoue désormais par l'unique chemin d'erreur de la branche).

### 5.6 Interaction avec **T3.25** (en revue, non mergé) — vérifiée

⚠️ **T3.25 ne corrige pas ce plantage.** Le plantage naît du `pop_back()` sur une chaîne vidée,
**avant** que `from_string` ne soit appelée ; T3.25 change ce que `from_string` **écrit**, pas ce
qu'elle **reçoit**. Les deux tickets touchent des fichiers disjoints (`StringUtils.h` d'un côté,
les deux parseurs de l'autre) : **aucun conflit de merge attendu**, dans les deux ordres.

Ce que T3.25 change **après** ce correctif :

1. **Le jeton `[]`** — `val` devient `""`, `from_string("")` échoue. Sur `master` la destination
   restait **intacte** et `int idx;` était **non initialisé** : lecture indéterminée. Ce correctif
   pose `int idx = 0` ⇒ élément **0**, défini. T3.25 fait écrire `T{}` ⇒ élément **0** aussi.
   **Les deux convergent sur la même valeur** ; `int idx = 0` reste correct avec ou sans T3.25, et
   le restera si T3.25 est reverté.
2. **Le jeton `[zz]`** — inchangé des deux côtés (le sentry passe, `num_get` échoue, C++11 écrit 0) :
   `ANonNumericIndexSilentlyReadsElementZero` reste vert dans les deux ordres de merge.
3. **Le chemin d'erreur du `[` isolé** — jamais atteint par `from_string` après ce correctif :
   T3.25 n'a **rien** à y changer.

⛔ **Ce que T3.25 ne rend pas caduc** : la garde. Sans elle, `pop_back()` sous-flue toujours, et
c'est le `try` — pas `from_string` — qui décide si le processus vit (mesure M1).

### 5.8 ⚠️ Ne pas survendre l'indication

`cWarning()` **n'est pas** un domaine filtré : la ligne part dans le log de `calaos_server`
**par défaut**, et c'était déjà le cas de l'avertissement `subpath not found` (correction §5.9 de
T3.29). Ce que le ticket améliore est donc **le contenu du message, pas sa portée** : la personne
qui commet la faute est dans **`calaos_installer`**, et le message atterrit dans le journal de
**`calaos_server`**. Amélioration réelle mais **faible** ; la vraie réponse serait de remonter le
diagnostic jusqu'à l'installeur, ce qui n'est pas ce ticket.
