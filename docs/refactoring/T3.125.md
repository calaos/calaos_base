## 1. L'état exact AVANT

**Ce qui publie** — `.github/workflows/docker-publish-dev.yml`, `name: Build and Publish dev docker
image` :

| | avant |
|---|---|
| déclencheur | `on: push: branches: [ master ]` |
| jobs | un seul, `build-and-push-docker-image`, **ni `needs:` ni `if:`** |
| version | `calaos/action-bump-version@2`, fragment `prerelease` |
| étiquette git | `negz/create-tag@v1` sur la version bumpée |
| image | `ghcr.io/calaos/calaos_base:dev` **et** `:<version>` |
| paquet | `peter-evans/repository-dispatch@v1` → `calaos/pkgdebs`, `build_deb`, `prerelease: true` |

**Ce qui teste** — `.github/workflows/ci.yml`, dont le `name:` est exactement :

> ### `Build and Test`

C'est cette chaîne, au caractère près, que le conditionnement cite. `on: push:` **sans aucun filtre**
de branche ni de chemin, plus `pull_request:`.

Les deux fichiers partaient donc du **même** événement, **en parallèle** : tout merge dans `master`
incrémentait la version, créait le tag, poussait l'image et dispatchait le paquet, que
`build-and-test` soit vert, rouge ou encore en cours. Le troisième fichier,
`docker-publish.yml` (`name: Build and Publish docker image`), est un `workflow_dispatch` manuel :
**hors périmètre de ce ticket, et non modifié**.

## 2. L'état exact APRÈS

`docker-publish-dev.yml` — trois changements, aucun ailleurs dans ses étapes :

1. le déclencheur devient
   `on: workflow_run: workflows: [ "Build and Test" ], types: [ completed ], branches: [ master ]` ;
2. le job porte
   `if: conclusion == 'success' && event == 'push' && head_sha == github.sha` ;
3. `actions/checkout@v3` reçoit `ref: ${{ github.event.workflow_run.head_sha }}`.

`ci.yml` gagne **un** job, `workflow-gating`, qui exécute le contrôle mécanique du §6.
`docker-publish.yml` est **inchangé, octet pour octet**.

## 3. ⭐ Ce que devient le contexte d'exécution

C'est le piège central de la forme retenue : `workflow_run` **change l'événement**, donc le contexte.

**`ref` / `sha`.** Un `workflow_run` s'exécute avec le fichier de workflow de la **branche par
défaut** (ici `master`, vérifié : `refs/remotes/origin/HEAD` → `refs/heads/master`), `github.ref` vaut
`refs/heads/master`, et `github.sha` est documenté comme **le dernier commit de la branche par
défaut** — *pas* le commit dont les tests viennent de passer. Deux merges rapprochés suffisent à les
séparer. D'où les deux parades :
- `actions/checkout` est **épinglé** sur `workflow_run.head_sha`, donc le `context: .` du
  `docker/build-push-action` est bien l'arbre testé ;
- ⭐ le job **refuse de tourner** quand `head_sha != github.sha`. La raison est
  `negz/create-tag@v1` : son code crée l'objet de tag sur `github.context.sha` et **n'offre aucune
  entrée pour le remplacer** (lu dans `negz/create-tag@v1:src/main.ts`, `object: github.context.sha`).
  Sans cette garde, l'étiquette pourrait se poser sur un commit plus récent et non testé — publier la
  mauvaise chose est pire que publier trop tôt. Quand la garde saute, `master` a déjà avancé, et
  c'est le commit suivant qui publiera par **sa** propre exécution : rien n'est perdu.
  ⚠️ La garde est écrite pour être correcte **dans les deux cas** : si GitHub résout en fait
  `github.sha` sur le commit déclencheur, l'égalité est simplement toujours vraie.

**Secrets.** Inchangés : un `workflow_run` s'exécute dans le contexte du dépôt de base, avec
`secrets.GITHUB_TOKEN` (login `ghcr.io`) et `secrets.ACTION_DISPATCH` (tag + dispatch `pkgdebs`)
lisibles. Aucun bloc `permissions:` n'existait, aucun n'a été ajouté : les permissions par défaut du
dépôt continuent de s'appliquer.
⛔ **Et c'est précisément le risque neuf** : `ci.yml` tourne aussi `on: pull_request`, **y compris
depuis un fork**, et la complétion d'une telle exécution lève un `workflow_run` sur le dépôt de
base — **avec les secrets**. `branches: [ master ]` ne suffit pas : une PR ouverte depuis la branche
`master` d'un fork porte `head_branch == 'master'`. C'est
`github.event.workflow_run.event == 'push'` qui porte ce refus, et l'égalité des sha le double.

**Version.** ⭐ **Aucun effet.** `calaos/action-bump-version@2` fait `git fetch --tags` puis dérive
la version du **dernier tag** (`get-last-version.py`, puis `bump.py <tag> prerelease`) : elle ne lit
ni la branche, ni le fichier `version` de l'arbre, ni `configure.ac`. Le changement de déclencheur ne
peut donc pas la déplacer. Les deux étiquettes d'image (`:dev` et `:<version>`) viennent de `env:` et
de cette sortie, également inchangées. `docker/metadata-action` reste calculé et **jamais utilisé** —
c'était déjà le cas.

## 4. Le cas « la CI ne tourne pas du tout »

`workflow_run` **ne se met pas en attente** : c'est un événement, pas une dépendance. S'il n'y a pas
d'exécution de `Build and Test`, il n'y a pas d'événement, et **la publication n'a pas lieu** —
silencieusement, sans erreur ni job en échec. Le comportement est donc *fail-closed* : jamais de
publication sans un succès explicite. C'est le bon comportement pour une garde ; son prix est le
silence — une chaîne arrêtée ressemble à une semaine calme.

Les cas, et ce qu'ils donnent :

| situation | résultat |
|---|---|
| `Build and Test` rouge / annulée | l'événement arrive, `conclusion != 'success'` ⇒ job **skipped**, rien n'est publié |
| `Build and Test` filtrée par `paths:` | **aucune exécution, aucun événement, aucune publication** — et rien ne le dit |
| `ci.yml` désactivé dans l'interface | idem, silencieux |
| nom cité erroné d'un caractère | idem, silencieux — c'est le mode d'échec le plus probable |
| poussée de tag (la publication en crée un) | `ci.yml` **re-tourne** (son `on: push:` n'a pas de filtre) ; le `workflow_run` qui suit porte le nom du tag en `head_branch` et est écarté par `branches: [ master ]` |

Aujourd'hui `ci.yml` n'a **ni `branches:` ni `paths:`**, donc l'événement existe toujours sur un push
vers `master`. Les trois premières lignes silencieuses sont exactement ce que le contrôle du §6
refuse en statique.

## 5. ⭐ Ce que le vert couvre, et ce qu'il ne couvre pas

Conditionner n'a de sens que si le vert veut dire quelque chose. Franchement :

**Ce qui bloque la publication** (jobs de `Build and Test` dont l'échec rend l'exécution rouge) :

| job | ce qu'il lance |
|---|---|
| `build-and-test` | debian:12, **pugixml système 1.13** (jamais le vendored 1.14 des builds locaux), `./autogen.sh && ./configure && make -j$(nproc)`, puis `make check` avec `CALAOS_PYTHON_TESTS_REQUIRED=1` **et** `CALAOS_PYDEPS_STRICT=1` — soit les 147 suites, sondes statiques et suites Python comprises |
| `mcp-sidecar-deps` | installe le jeu déclaré par `pyproject.toml` et importe l'API réelle du sidecar, `_session_manager` compris |
| `dependabot-config` | chaque répertoire surveillé porte bien un manifeste |
| `workflow-gating` *(neuf)* | le contrôle du §6 |

**Ce que le vert ne dit RIEN de :**

- ⛔ **aucun `Dockerfile` n'est construit par la CI.** Le seul build d'image du dépôt est l'étape de
  publication elle-même. Un vert ne promet pas que l'image se construit ;
- ⛔ **ni `make dist` ni `make distcheck`** — la distribution n'est jamais éprouvée ;
- ⛔ **pas d'ASan** : `--enable-asan` n'est câblé dans aucun job ;
- ⛔ **`make check-docs` n'est nulle part** — hors de `make check` par décision de `T3.32`, et absent
  de la CI ;
- ⚠️ **`format-check` est `if: github.event_name == 'pull_request'`** : sur un push vers `master` il
  est **sauté**, et un job sauté laisse l'exécution en `success`. Le style ne fait donc pas partie du
  vert qui garde la publication ;
- ⚠️ **`coverage` est `continue-on-error: true`** : son échec ne rougit pas l'exécution, par décision
  déjà écrite dans le fichier ;
- ⚠️ `check-ccache-honesty.sh` est le `SKIP` structurel des 147 : il l'est aussi en CI ;
- ⚠️ une seule architecture : QEMU et buildx sont installés mais `platforms:` n'est jamais passé.

⇒ le vert couvre **la compilation et la suite de tests sur debian:12**, plus trois contrôles
statiques. Il ne couvre ni l'emballage, ni l'image, ni la distribution. La garde est réelle, elle
n'est pas totale — et elle vaut exactement ce que valent les 147.

## 6. ⭐ Le contrôle mécanique et son auto-test

`.github/check-workflow-gating.py`, exécuté par le job `workflow-gating` de `Build and Test`. Il
**refuse trois formes silencieuses** :

1. un `workflow_run` citant un nom qu'**aucun** fichier de `.github/workflows/` ne déclare en `name:`
   (faute de frappe, citation du **nom de fichier** au lieu du `name:`, casse différente, workflow
   cité **sans** `name:`) ;
2. le workflow cité filtré par `paths:` / `paths-ignore:` — un commit écarté ne déclenche rien, donc
   ne publie jamais ;
3. un job conditionné dont l'`if:` ne mentionne pas `workflow_run.conclusion` — `types: [completed]`
   se déclenche **aussi sur un échec**, donc sans ce test la garde ne garde rien.

Plus la validité YAML de chaque fichier, la présence d'un `on:` et d'un `jobs:`.

**Auto-test** — la norme des trois sondes du dépôt qui en portent un (`check-echo-ceilings.sh`,
`check-order-sentinels.sh`, `check-docs.py`) : **10 jeux refusés, 5 acceptés**, passés à la **même**
fonction `scan()` que le balayage réel, **avant** lui ; un échec de l'auto-test rend **rc 2** et le
balayage n'a pas lieu — une sonde cassée n'accuse jamais l'arbre.

⚠️ Il était mesuré à la revue de `T3.22` qu'un contrôle sans auto-test accepte cinq configurations
invalides. Ici, **cinq mutations du contrôle lui-même** (jamais de la règle qu'il énonce, là où un
auto-test ne regarde pas) sont toutes attrapées :

| mutation du contrôle | résultat |
|---|---|
| `ON_KEYS` privé de `True` (en YAML 1.1 la clef nue `on` **est** le booléen) | rc 2, 3 refus faussés |
| `declared_name()` rendant un nom au lieu du chemin quand `name:` manque | rc 2 |
| le test `paths` / `paths-ignore` changé en conjonction | rc 2, 2 refus perdus |
| `workflow_run.conclusion` affaibli en `workflow_run` | rc 2 |
| les noms de fichiers ajoutés à la table des noms | rc 2 |

**Dans aucun de ces cinq cas l'arbre n'est accusé** (`tree-complaints = 0`) : le balayage n'est pas
atteint.

## 8. ⛔ Nu — ce qui n'est PAS vérifié

**⛔ EN TÊTE : CE QUI NE SERA VÉRIFIÉ QU'AU PREMIER `push`.** Aucune exécution GitHub Actions n'a eu
lieu, ni ici ni de toute la série. Tout ce qui suit est **déduit de la documentation et du code des
actions lues**, jamais observé :

1. **que le `workflow_run` se déclenche du tout.** Un déclencheur `workflow_run` n'est honoré que
   depuis la branche par défaut ; le premier push est celui qui l'y installe ;
2. **ce que vaut réellement `github.sha` sous `workflow_run`.** La garde est écrite pour être juste
   dans les deux résolutions possibles, mais laquelle se produit ne s'observe que là-bas. ⚠️ Si
   c'était une troisième valeur, **plus rien ne publierait** — et cela ressemblerait à une semaine
   calme ;
3. **que `head_branch` porte bien le nom du tag** pour la poussée de tag que la publication crée
   elle-même, donc que la boucle est bien coupée par `branches: [ master ]` ;
4. **que `secrets.ACTION_DISPATCH` reste lisible** sous ce déclencheur (il doit l'être : contexte du
   dépôt de base) ;
5. **que le job `workflow-gating` s'installe** : `python3-yaml` de debian:12, jamais joué ;
6. **le câblage `CALAOS_PYDEPS_STRICT: "1"` de [`T3.67`](T3.67.md)** — point ouvert depuis, non
   refermé par ce ticket ;
7. ⚠️ **les 12 dépréciations de runner** relevées par actionlint. Elles sont **antérieures** à ce
   ticket et il n'y touche pas, mais si elles font échouer le job de publication, c'est maintenant
   dans une chaîne où plus rien d'autre ne publie.

**Et ce que ce ticket ne fait pas :**

- ⛔ **la protection de branche (issue C) reste à poser, à la main de l'utilisateur.** Elle est plus
  forte — elle empêche un rouge d'**entrer** au lieu de l'empêcher de publier — mais c'est un réglage
  d'interface, invisible dans le dépôt, qu'un agent ne peut pas poser. Écartée comme *seule* réponse,
  disponible en complément ;
- ⛔ **le contrôle du §6 ne tourne pas dans `make check`.** L'image de développement n'a **pas**
  PyYAML (mesuré : `ModuleNotFoundError: No module named 'yaml'`), et `tests/` appartenait à un autre
  agent pendant ce ticket. Il vit donc dans la CI, comme `dependabot-config` — même compromis, même
  limite : il ne se joue pas sur le poste du développeur ⇒ [`T3.132`](T3.132.md) ;
- ⛔ **il se garde lui-même de l'intérieur.** Le contrôle qui protège la garde est un job de la CI
  qu'il garde : qui retire le job **et** casse le nom cité ne rencontre rien ;
- ⛔ **`docker-publish.yml` porte toujours le commentaire faux** (`F-DEP-10`) que `T3.22` avait corrigé dans
  l'autre fichier (`# run only when code is compiling and tests are passing`, ligne 25), alors qu'il
  n'y a là non plus **aucune** garde ; il publie `:latest` et un paquet **non** prerelease sur simple
  `workflow_dispatch`. Hors périmètre — laissé intact pour que la vérification (c) reste probante ;
- ⛔ **la publication n'est pas éprouvée par la CI** : ni le build du `Dockerfile`, ni le bump, ni le
  tag, ni le dispatch `pkgdebs` ne sont exercés par un job de test. Le vert ne dit rien d'eux (§5) ;
- ⚠️ **chaque publication relance la CI complète** : le tag créé est un `push`, et le `on: push:` de
  `ci.yml` n'a pas de filtre de ref. Coût préexistant, désormais aussi une source de déclenchement
  qu'il faut écarter.
