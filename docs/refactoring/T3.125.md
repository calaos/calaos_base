# T3.125 — La publication ne dépend d'aucun test, et le fichier prétend le contraire

**Type** : infra / décision · **Phase** : 3
**Origine** : mesure de [`T3.22`](T3.22.md) §1. **Statut** : 📋 backlog — **décision utilisateur**.
**Finding** : `F-DEP-8` (moitié « publication »).

## Le fait

`.github/workflows/docker-publish-dev.yml:3-5` déclare `on: push: branches: [master]`. Son unique
job, `build-and-push-docker-image`, n'a **ni `needs:`, ni `if:`**, et l'arbre ne porte **aucun**
déclencheur `workflow_run`. Les tests vivent dans un **autre** fichier de workflow (`ci.yml`), donc
hors de portée d'un `needs:`. Les deux partent du **même** événement, **en parallèle**.

⇒ **tout merge dans `master` incrémente la version, crée un tag git, publie
`ghcr.io/calaos/calaos_base:dev` et le tag versionné, puis dispatche un `build_deb` vers
`calaos/pkgdebs` — que `build-and-test` soit vert, rouge, ou encore en cours.**

⚠️ **Et `docker-publish-dev.yml:16` porte le commentaire
`# run only when code is compiling and tests are passing`.** Il énonce une garantie que le fichier
n'implémente pas. Un lecteur qui s'y fie merge en croyant qu'un rouge le retiendra.

## Les issues

1. ✅ **A — corriger le commentaire seul. FAIT à la revue de merge de [`T3.22`](T3.22.md).** Le
   fichier dit désormais pourquoi rien ne garde ce job. Changement de **texte seul** : les deux
   versions donnent des documents YAML **égaux** une fois parsés. La livraison reste non gardée.
2. **B — `workflow_run`.** `docker-publish-dev.yml` se déclenche sur la **complétion réussie** de
   `Build and Test` au lieu du `push`. ⚠️ Deux effets à connaître : un `workflow_run` s'exécute avec
   le workflow de la branche **par défaut**, et la publication devient dépendante d'une suite dont
   `core/MqttSidecarConfigWait_test` flanche par intermittence (`F-FLAKY-2` / [`T3.112`](T3.112.md))
   — donc **des livraisons manquées** tant que ce flottement n'est pas fermé.
3. **C — protection de branche sur `master`.** Hors dépôt (réglage GitHub), n'apparaît dans aucun
   fichier suivi, mais c'est le geste qui empêche un rouge d'**entrer** plutôt que de publier.

**A est fait. Restent B et C — après [`T3.112`](T3.112.md), jamais avant** : tant que
`core/MqttSidecarConfigWait_test` flanche, les poser ferait **manquer des livraisons**.

⛔ **Ce ticket ne se fait pas sans l'utilisateur** : B et C changent ce qui est livré et quand.
