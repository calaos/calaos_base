# T3.160 — le miroir serveur→dégradé de l'automate est faux depuis la 1.8, et il éteint les lumières

**Statut** : 📋 · **Type** : fix (dépôt `calaos_wago`) · **Phase** : 3
**Origine** : **bug rapporté par l'utilisateur** le 2026-09-07. Instruit par lecture du texte ST
extrait des huit versions de `calaos_wago/Wago_*`. ⛔ **Le correctif est dans l'autre dépôt.**

---

## 1. Le symptôme, observé par l'utilisateur

Au redémarrage de `calaos_server` — qui dure **plus de 30 s**, donc au-delà du `HEARTBEAT_TIMER` —
**les lumières s'éteignent**, puis l'état est restauré quand le serveur reprend la main. Deux
transitions observables là où il ne devrait n'y en avoir aucune.

## 2. Le miroir existe déjà, et il est faux de deux lignes

`PLC_PRG`, branche mode serveur (identique **octet pour octet de la 1.8 à la 3.0**) :

```pascal
ELSE
    j := 0;
    FOR i := 0 TO 14 DO
        valw := netOutStandard[j + 1];
        write_word(WORD_ADDRESS := i + start_addr_out / 16, VALUE := SHL(valw, 8) + netOutStandard[j]);
        j := j + 2;                                    (* incrémenté AVANT le miroir *)
        OutArrState[j]     := netOutStandard[j];       (* copie donc le mot SUIVANT *)
        OutArrState[j + 1] := netOutStandard[j + 1];
    END_FOR
```

Deux défauts distincts dans ces trois lignes :

1. ⛔ **`j := j + 2` s'exécute avant la recopie** ⇒ `OutArrState[0..1]` — **les 16 premières sorties
   digitales** — n'est **jamais** synchronisé, et chaque tour recopie le mot d'après celui qu'il
   vient d'écrire.
2. ⛔ **La recopie indexe `OutArrState` en RELATIF** (`j` de 0 à 31) alors que `SetOutput()` et la
   branche dégradée l'indexent en **ABSOLU** (`start_addr_out / 8 + …`). Dès que `start_addr_out ≠ 0`
   — un module analogique de sortie placé avant le premier digital suffit — **tout le rack est
   désaligné**, pas seulement les 16 premières.

⇒ Les sorties non synchronisées gardent **0** dans la table dégradée. À la bascule, ce `0` est écrit
sur les relais : **la lumière s'éteint**. C'est exactement le symptôme.

## 3. ⭐ C'est une RÉGRESSION, et la 1.7 était correcte

```pascal
(* Wago_1.7 — pleine largeur, absolu, et SYMÉTRIQUE *)
IF (HEARTBEAT = FALSE) THEN
    FOR i := start_addr_out / 8 TO 512 DO  byOutArr[i] := OutArrState[i];  END_FOR
ELSE
    FOR i := start_addr_out / 8 TO 512 DO  OutArrState[i] := byOutArr[i];  END_FOR
END_IF
```

La 1.7 disposait d'un miroir **bidirectionnel, pleine largeur et correctement basé** : une bascule
sans à-coup dans les deux sens. La **1.8** a déplacé l'image serveur de `%QB0` vers
`%IB512`/`netOutStandard` — la contrainte Modbus que décrit l'utilisateur — et **a cassé le miroir**
: l'aller est devenu décalé, mal basé et tronqué à 30 octets sur 512 ; **le retour a disparu**
(⇒ [T3.161](T3.161.md)).

## 4. Ce qui est dangereux, et ce qui ne l'est pas

⛔ **Le danger est un NIVEAU périmé rejoué, pas un front.** L'hypothèse du front parasite est
**réfutée** : `event[cpt](IN := GetInput(…))` vit dans `SendInput`, appelé **à chaque cycle dans les
deux modes**, donc les `R_TRIG`/`F_TRIG` ne gèlent jamais.

Le seul type dangereux est le **`VOLET` simple** : son `SetOutput(… MONTE/DESCENTE)` est **à
l'intérieur** du `IF (event[cpt].ON)`, donc les deux bits relais restent **latchés** entre deux
appuis. Un `TRUE` périmé est rejoué et **rien ne le fera retomber avant un appui** — le volet part
en butée. `VOLET_IMPULSE` est au contraire sûr : son `SetOutput` est hors du garde et tourne à
chaque cycle. Le télérupteur n'est pas dangereux : il n'agit que sur `event.ON`.

⭐ **Un volet occupe deux bits relais, tous deux à 0 au repos** : recopier une image au repos est
donc inoffensif. Le danger vient exclusivement d'un non-zéro périmé dans la table dégradée.

## 5. Correctif proposé

1. Déplacer `j := j + 2` **après** les deux lignes de recopie, et baser la recopie en absolu :
   `OutArrState[start_addr_out / 8 + j] := netOutStandard[j];`
2. Ensemencer l'état interne sur le **front descendant** de `HEARTBEAT` — `F_TRIG`, **jamais
   l'état** : ré-ensemencer à chaque cycle empêcherait le mode dégradé de piloter quoi que ce soit.
   Le point de pose est `PLC_PRG`, **entre `UDPServer;` et `IF (HEARTBEAT = FALSE) THEN
   ManageOutput`** — `HEARTBEAT` est affecté en fin de `UDPServer`, le front est disponible dans le
   même cycle.
3. ⚠️ `lights[]` **n'est pas un `memcpy`** : il est indexé par **id de règle**, pas par adresse de
   sortie. Il faut une boucle par règle allant chercher le bit `output_addr[tmp].ADDR1 +
   start_addr_out`. `volets[tmp].MONTE`/`.DESCENTE` sont des `VAR_OUTPUT` directement assignables et
   **entièrement reconstructibles depuis l'image** — le cas qui gêne l'utilisateur **est**
   ensemençable.

## 6. ⛔ Ce qui reste hors de portée

`mode` et `imp` de `VOLET_IMPULSE` **ne sont pas ensemençables** : « le volet est en train de
bouger » n'est pas dans l'image de sortie. Ce type s'auto-corrige, le coût est un premier appui qui
envoie un STOP au lieu d'un mouvement — nuisance, pas mouvement parasite. Les branches DALI et DMX
contournent l'image : ni ensemençables ni réversibles.

## 7. ⛔ Le nu

Rien n'a été compilé, exécuté ni mesuré sur automate. Tout est de la **lecture** de texte ST extrait
par `strings` d'un binaire CoDeSys : les faits porteurs reposent sur des corps de boucle et des
déclarations — lignes longues, non ambiguës — mais **l'imbrication des `IF` est lue, pas prouvée**.
La valeur réelle de `start_addr_out` sur les racks installés est **inconnue** : elle décide de
l'ampleur du désalignement, pas de son existence. L'impulsion d'un scan du `TP` de `VOLET_IMPULSE`
à la reprise n'est **pas bornée**.
