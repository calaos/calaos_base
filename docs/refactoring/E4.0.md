# E4.0 — Filet de caractérisation de l'API JSON (avant toute migration)

**Type** : test (caractérisation) · **Phase** : 4 · **Série** : E4.0 (parent, 6 sous-tickets)
**Dépend de** : rien · **Débloque** : **E4.1** (bibliothèque JSON unique / suppression de jansson)
**Décision utilisateur (2026-08-16, DECISIONS.md)** : on écrit d'abord les tests qui valident les
entrées/sorties de l'API JSON **actuelle**, on migre ensuite sous ce filet. Aucun sous-ticket E4.1
ne démarre tant que E4.0 n'est pas livré.

## Objectif
Geler le **comportement observable** de l'API JSON (port 5454) — commandes requête/réponse et
events temps réel — avant de toucher à la bibliothèque JSON. Sans comportement de référence
enregistré, un payload qui change après migration est indiscernable d'un payload qui a toujours
été comme ça : on ne saurait pas distinguer une régression d'un comportement d'origine.

Ce ticket **n'écrit aucune ligne de production**. Il ne corrige rien, il n'améliore rien : il
**enregistre l'existant tel quel**, bugs compris (voir « Invariants »).

> **Convention de comptage de la colonne « Union » — tranchée par E4.0f, ne pas recorriger.**
> Ce document a longtemps porté **57** feuilles et **37** sous-actions. Le bon chiffre est **56**
> et **36**. L'écart tient **entièrement** à la paire `get_albums` (HTTP, `JsonApiHandlerHttp.cpp:781`)
> / `get_album` (WS, `JsonApiHandlerWS.cpp:380`) : **deux noms de fil pour le même builder**
> `audioDbGetAlbums()`, comme le dit déjà la ligne « même builder, deux noms de fil » ci-dessous.
>
> **La colonne « Union » compte les opérations par identité de comportement, pas par orthographe
> de fil.** Une opération présente sur les deux transports y est comptée **une fois** — c'est déjà
> le traitement de la totalité des 17 commandes communes. Compter `get_albums`/`get_album` deux
> fois reviendrait à faire remonter dans l'union une **divergence d'orthographe entre transports**,
> alors que les colonnes HTTP (53) et WS (44) la portent déjà, chacune avec sa propre orthographe.
> Ce n'est donc **pas** une erreur de dénombrement corrigée mais une **convention explicitée** ;
> les colonnes par transport sont inchangées, seule l'union bouge. Les dénominateurs du reste de
> ce document (couverture, documentation, livraison de la série) suivent la même convention.
> `docs/08_http_api.md` et `docs/10_events_notifications.md` sont alignés sur **56/36**.

### Events temps réel

`src/bin/calaos_server/EventManager.h:37-71` : **24 constantes d'enum**, **23 types réels**
(hors `EventUnkown`, filtré à `EventManager.cpp:38-42`), **18 effectivement poussés** aux clients
(⚠️ ce document a longtemps porté **19** — corrigé par E4.0f, mesuré, voir ci-dessous).
3 types morts jamais émis : `EventRoomAdded`, `EventRoomDeleted`, `EventRoomPropertyDelete`.

Deux types de plus n'atteignent jamais un client par le canal temps réel, pour deux raisons
**différentes** — d'où 23 − 3 − 2 = **18** :

- `EventAudioPlaylistCleared` est **inatteignable**. Son site d'émission
  (`Audio/Squeezebox.cpp:306`/`:311`, `else if (p["2"] == "clear")`) est masqué par une chaîne
  `else if` **antérieure** : `Squeezebox.cpp:290` teste
  `p["2"] == "loadtracks" || p["2"] == "clear" || p["2"] == "play" || p["2"] == "load"` et émet
  `EventAudioPlaylistReload`. Toute commande `clear` produit donc `playlist_reload` ; la branche
  `:306` est **du code mort**. Le `type_str` `playlist_cleared` n'est jamais sur le fil.
- `EventPushNotification` ne passe **jamais** par `EventManager::create()`. `ActionPush.cpp:105`
  construit un `HistEvent` et l'écrit **directement en base** (`e.event_type = EventPushNotification`,
  `e.event_raw = data.dump()`, `:111-115`). Ce `type_str` est donc bien observable par un client,
  mais **uniquement via `eventlog`** — jamais via l'enveloppe WS `msg:"event"` ni via `poll_listen`.
  Nuance à conserver : ce n'est pas un « type mort », c'est un type **hors canal temps réel**.

Enveloppe WS (`JsonApiHandlerWS.cpp:53-73` + `EventManager.cpp:185-196`) :

```json
{"msg":"event","data":{"event_raw":"io_changed id:output_5 state:true",
                       "type":"3","type_str":"io_changed","data":{"id":"output_5","state":"true"}}}
```

Points de contrat : `data.data` imbriqué ; **toutes les valeurs sont des chaînes**, y compris
`type` qui est l'entier de l'enum **stringifié** ; `event_raw` est une chaîne plate url-encodée,
pas du JSON ; pas de `msg_id` (push non sollicité) ; rien n'est envoyé si `!loggedin`.

Équivalent HTTP : `poll_listen` (`JsonApiHandlerHttp.cpp:388-426`, `PollListenner.{h,cpp}`) —
même objet event, mais dans un tableau plat `{"success":"true","events":[…]}`, sans enveloppe
`msg`/`data`. Sous-actions `register` → `{"uuid":…}`, `get`, `unregister`.

### Contrats de payload particuliers

- **Tout est chaîne, sauf un endroit.** `JsonApi.cpp` : 32 `json_string`, **0** `json_real` /
  `json_integer` / `json_true`. Idem `Params::toJson()` (`src/lib/Params.cpp:134-147`).
  Seule exception : `buildJsonEventLog()` (`JsonApi.cpp:1955-1961`), déjà en **nlohmann**, émet
  `total_page` / `total_count` / `page` / `per_page` en **entiers JSON**. C'est le seul payload de
  l'API où un type non-chaîne est sur le fil.
- `buildJsonIO()` (`JsonApi.cpp:256-297`) : 16 clés candidates, **une clé absente du `Params` de
  l'IO n'est pas émise du tout** (`continue` l. 286) — absence, jamais `null`. Plus une clé
  `status_info` conditionnelle (`buildJsonStatusInfo()`, `:1997`).
- `getCameraList()` / `getAudioList()` : leur **type d'élément** est épinglé par `static_assert`
  depuis E4.2a (`tests/core/ListeRoomIdResolution_test.cpp:335-340`) précisément parce qu'il
  détermine les payloads de `buildJsonCameras()` (`JsonApi.cpp:359-387`) et `buildJsonAudio()`
  (`:389-419`). Ces deux builders filtrent par `dynamic_cast` (`IPCam*`, `AudioPlayer*`) : changer
  le type d'élément change **silencieusement le contenu du tableau**, pas seulement sa forme.
  Les goldens de E4.0b doivent contenir au moins une caméra et un player pour que ce filtre soit
  exercé, et au moins un IO qui **ne passe pas** le `dynamic_cast`.

  ✅ **Fait en E4.0a pour la partie faisable** : la maison de référence du harnais porte
  désormais **deux caméras réelles** (`StandardMjpeg`, les deux branches de la capacité `ptz`) et
  **un player réel** (`Roon`, avec un param `amp` pour exercer la clé optionnelle `avr`). Coût de
  link mesuré au `nm -Cu` : **zéro objet supplémentaire** — chacun ne réclame que sa classe de
  base, déjà fournie par `CORE_SERVER_OBJECTS` (`IPCam.o`, `Audio/AudioPlayer.o`). `Squeezebox` a
  été écarté : il traîne `SqueezeboxDB`, `UrlDownloader` et les neuf objets AVR, et linke
  `uv_tcp_connect`/`uv_write` (réseau réel dans un test unitaire). `RoonPlayer` est instancié avec
  un `zone_id` **vide**, ce qui le fait sortir de son constructeur avant `RoonCtrl::Instance()` —
  donc sans spawn de process ni timer : `make check` reste hermétique.

  ❌ **Correction : « au moins un IO qui ne passe pas le `dynamic_cast` » est INFAISABLE, et la
  demande est retirée.** Mesuré : `ListeRoom::addIOHash()` (`ListeRoom.cpp:80-85`) remplit
  `cameraCache`/`audioCache` uniquement sur `get_param("gui_type") == "camera"` / `"audio_player"`,
  et les **seuls** endroits qui posent ces deux valeurs sont les constructeurs d'`IPCam`
  (`IPCam.cpp`) et d'`AudioPlayer` (`Audio/AudioPlayer.cpp`) — qui appellent eux-mêmes
  `addIOHash()` dans la foulée. Toute autre classe d'IO écrase `gui_type` avec sa propre valeur
  (p. ex. `IO/IntValue.cpp:83-85` force `var_bool`/`var_int`/`var_string`), donc un attribut XML ne
  peut pas faire entrer un IO étranger dans l'un des deux caches. Le `dynamic_cast` de
  `buildJsonCameras()`/`buildJsonAudio()` est du **code défensif inatteignable** : il n'a pas de
  branche fausse joignable depuis une configuration. E4.0b ne doit pas dépenser d'effort à la
  couvrir.
- `buildJsonAudio()` n'émet `avr` que si le param `amp` existe → clé optionnelle.
- `buildJsonGetTimerange()` (`:1487-1522`) : `ranges` (tableau, `day` = index+1 via
  `TimeRange::toParams()`, `src/lib/TimeRange.cpp:429`) + `months` = bitset 12 bits **inversé**
  (`std::reverse`, l. 1518). Aller-retour non trivial.
- `Scenario::toJson()` (`IO/Scenario.cpp:81-140`) : `steps_count` stringifié, tableau `steps`
  + une **étape terminale synthétique** `step_type:"end"` ajoutée hors boucle.
  ⚠️ **`steps_count` n'est donc PAS la longueur du tableau `steps`.** `:95` compte
  `getRuleSteps().size()`, c'est-à-dire les seules étapes réelles ; l'étape `end` est ajoutée
  **hors de la boucle** (`:125-142`). **Invariant : `len(steps) == steps_count + 1`, toujours.**
- **4 opérations ne renvoient pas de JSON** mais des octets `image/jpeg` : `audio/get_cover`
  (sous-action), `camera/get_picture`, `camera/get_video`, `event_picture`.
  ⚠️ Ce document a longtemps porté **6** — corrigé par E4.0f, mesuré : `get_cover` **de premier
  niveau** et `get_camera_pic` ne renvoient **pas** d'octets bruts. Les deux finissent dans
  `JsonApiHandlerHttp::exeFinished()` (`JsonApiHandlerHttp.cpp:574-591`), qui répond un **objet
  JSON** `{"success":"true","contenttype":"image/jpeg","encoding":"base64","data":…}`. Elles ont
  donc bien un contrat de payload. Les 4 restantes n'en ont pas, seulement des chemins d'erreur.
- **`items[0]` n'est PAS toujours le marqueur `{"count":"N"}`.** `processDbResult()`
  (`JsonApi.cpp:984-1006`) ne réordonne **jamais** ce que lui donne la couche audio, et la couche
  audio place le marqueur où ça l'arrange : `SqueezeboxDB::getAlbums_cb()`
  (`Audio/SqueezeboxDB.cpp:66-73`) traite `count:` comme un **séparateur d'enregistrement** au même
  titre que `id:` (il peut donc tomber n'importe où), et `getRandoms()` (`:750-776`) l'ajoute
  **en dernier**. Ne pas réintroduire l'affirmation générale « le premier élément est le compte ».

## Verdict de faisabilité : **in-process, appel direct, ni serveur ni socket**

C'est la question qui conditionne tout le reste. Réponse : **oui, et à un coût bien plus faible
qu'attendu**, parce que trois éléments sont déjà en place.

1. **`JsonApi.o` est déjà linké dans tous les tests `core/`** (`tests/Makefile.am:127`, dans
   `CORE_SERVER_OBJECTS`). Appeler `buildJsonHome()`, `buildJsonCameras()`, `buildJsonGetTimerange()`…
   depuis un test GTest **ne demande aucun travail de build**. `JsonApi` a un constructeur par
   défaut (`JsonApi.h:89`) qui laisse `httpClient = nullptr`, et aucun builder ne s'en sert.

2. **`JsonApiHandlerWS` est instanciable avec un `HttpClient*` nul** — c'est le point clé, il donne
   le dispatch complet de bout en bout sans réseau :
   - `clientIp()` garde explicitement le cas (`JsonApiHandlerWS.cpp:45-51` → `"unknown"`),
   - les deux `sendJson()` (`:63-73` jansson, `:75-85` nlohmann) n'utilisent **que**
     `sendData.emit()`, jamais `httpClient`.

   Donc : `JsonApiHandlerWS h(nullptr); h.sendData.connect(capture); h.processApi(requeteJson, Params());`
   exerce le **parsing d'entrée, le dispatch, le gating `loggedin`, le `serviceScope`, l'enveloppe
   et le payload**, en mémoire, sans socket et **sans faire tourner la boucle**
   (`Utils::getMainLoopTime()` n'a besoin que de `uvw::Loop::getDefault()`, pas d'un `run()`).

   ⚠️ **Deux réserves mesurées, à traiter dans E4.0a** :
   - `JsonApiHandlerWS` **référence le symbole** `HttpClient::getClientIp()` même si l'appel est
     null-gardé. Il faut donc soit linker `HttpClient.o` et sa fermeture (lourde : `HttpServer`,
     `WebSocket`, `JsonApiHandlerHttp`, `McpProxyHandler`, `PollListenner`, `RemoteUI/*`), soit
     fournir un **stub** de ce seul symbole dans l'unité de test. `McpServerManager.o` reste
     nécessaire (`login_service`, `:531`) — objet autonome, sans fermeture.

     ✅ **TRANCHÉ EN E4.0a PAR LA MESURE : on linke la vraie fermeture, PAS de stub.** Cette
     section recommandait le stub ; la mesure a conclu l'inverse, et le point 3 ci-dessous se
     contredisait déjà lui-même en concédant qu'il faut un vrai `HttpClient`. Relevé exact
     (`nm -Cu`) : `JsonApiHandlerWS.o` ne réclame qu'**un** symbole `HttpClient`
     (`getClientIp()`) — le stub suffirait pour un binaire WS seul ; mais
     `JsonApiHandlerHttp.o` en réclame **trois** (`getClientIp`, `buildHttpResponse`,
     `buildHttpResponseFromFile`), et `buildHttpResponse()` **est** précisément la logique de
     production que E4.0e doit épingler (en-têtes, `Content-Length`, `conn_close`). La stubber
     reviendrait à caractériser le stub. Le bloc de link recopié de `core/RemoteUIDeviceInfo_test`
     a linké du premier coup et `make check` est vert. **Aucun stub dans le harnais.**
   - **Les events ne sont PAS livrés sans boucle qui tourne.** `EventManager` empile dans un
     **idler uvw** (`EventManager.cpp:46-54`) et `CalaosCoreFixture.h:77-97` documente
     explicitement que la file grandit sans jamais être dépilée dans les tests. E4.0d doit donc
     pomper la boucle (`uvw::Loop::getDefault()->run<uvw::Loop::Mode::NOWAIT>()`) après chaque
     `EventManager::create(...)` — ou tester `CalaosEvent::toJson()` en direct **et** le chemin
     `handleEvents()` avec pompage. **Les deux, la seconde étant la seule qui prouve l'enveloppe.**

3. **`JsonApiHandlerHttp` exige un vrai `HttpClient`, non-null, dès le premier échec d'auth** :
   `sendLoginFailed()` (`JsonApiHandlerHttp.cpp:63-71`) et `sendJson()` (`:232, 249`)
   déréférencent `httpClient` **sans garde**. Deux voies, à trancher **par la mesure** dans E4.0a :
   - `HttpClient(std::shared_ptr<uvw::TcpHandle>)` (`HttpClient.h:476`) sur un handle obtenu de
     `uvw::Loop::getDefault()->resource<uvw::TcpHandle>()` **sans connexion** ;
     `buildHttpResponse()` (`HttpClient.cpp:541+`) est du pur formatage de chaîne, rien de réseau,
     et `getClientIp()` est `try/catch` → `"unknown"`. Réserves : le constructeur alloue un
     `Timer` et un handle uv dans la boucle par défaut (`HttpClient.cpp:146-154`) → fuite de
     handles entre cas ; et `buildHttpResponse()` **mute** l'état de connexion (`resHeaders`,
     `conn_close`, `:552-566`) → **un `HttpClient` neuf par requête**, obligatoire.
   - Si ça ne tient pas : le **corps** de la réponse HTTP est, par construction, exactement le
     `json_dumps` du même objet que produisent les builders (`sendJson()`, `:221-251`). On
     caractérise alors le corps via `JsonApi::build*` et le dispatch via le WS ; il ne reste
     de spécifiquement HTTP que la table de dispatch et les en-têtes, couverts par E4.0e.
   Dans les deux cas, **exclure `get_camera_pic` / `get_cover`** de la caractérisation : ils
   spawnent `calaos_picture` via `uvw::ProcessHandle` (`:475, 526, 739`).

4. **Le précédent de link existe** : `core/RemoteUIDeviceInfo_test` (`tests/Makefile.am:987-1005`)
   linke déjà `JsonApiHandlerHttp.o`, `JsonApiHandlerWS.o`, `HttpClient.o`, `WebSocket.o`,
   `PollListenner.o`, `McpServerManager.o` par-dessus `CORE_TEST_LDADD`. Le bloc à recopier est
   écrit, testé et vert.

5. **Le harnais d'état existe** : `tests/core/CalaosCoreFixture.{h,cpp}` fournit config isolée,
   `loadConfig()/saveConfig()/reloadFromDisk()`, `addRoom()`, `createIO()`, `createInternalIO()`,
   `addSimpleRule()`, `clearCoreState()` — de quoi construire une maison déterministe et
   reproductible sans XML écrit à la main.

6. **Aucun harnais existant ne démarre un vrai serveur, et il n'en faut pas pour ce ticket** :
   `tests/run-python-tests.sh` (câblé dans `TESTS`, `tests/Makefile.am:26-27`) pilote les suites
   du sidecar MCP / extern-proc Python, **sans rapport avec le port 5454** ;
   `tests/websockets/` est la suite de conformité protocole Autobahn (`wstest`), lancée à la main,
   **absente de `TESTS` et d'`EXTRA_DIST`**, et qui ne teste que le framing.
   Un tel harnais serait pourtant **faisable sans patcher `src/`** : `main.cpp` accepte
   `--config`/`--cache` (l. 107-110, même `Utils::initConfigOptions()` que le fixture), le port
   vient de l'option de config `port_api` (l. 166-170), il n'y a **aucun `fork`/`daemon()`**, et
   `-noudp` (l. 156) neutralise les binds fixes 4545/4646. C'est noté ici pour mémoire — **hors
   périmètre E4.0** : la caractérisation de payload n'a pas besoin du réseau, et un test qui
   démarre un process est plus fragile qu'utile pour ce qu'on cherche à geler.

**Conclusion** : voie unique retenue = **tests GTest `tests/core/`, appel direct de
`JsonApiHandlerWS::processApi()` et des builders `JsonApi::build*`, réponses capturées via le
signal `sendData`, comparées à des goldens versionnés.** Aucun démarrage de serveur, aucun port,
aucune dépendance réseau, `make check` reste hermétique.

⚠️ **Prérequis de build, à purger avant d'écrire la première assertion** : l'arbre de travail
actuel est **périmé**. `tests/Makefile` (généré, 11/08) ne connaît que **3** des 20 tests
`core/` déclarés dans `tests/Makefile.am` (16/08), et `src/bin/calaos_server/JsonApi.o` date du
**28/05** alors que `JsonApiHandlerWS.cpp` date du **11/08**. Conséquence directe : un test écrit
et lancé tel quel s'exécuterait contre des objets vieux de trois mois. E4.0a doit commencer par
`autoreconf` + `configure` + un `make` complet de `src/`, et le vérifier.

## L'oracle : comparaison **sémantique**, jamais octet à octet

Contrainte non négociable. `nlohmann::json` **trie** les clés là où jansson préserve l'ordre
d'insertion, et l'utilisateur a **déjà tranché** que ce changement d'ordre est assumé
(DECISIONS.md, « nlohmann standard »). Un test byte-exact échouerait donc à la bascule pour une
raison **déjà acceptée**, et le filet ne servirait à rien.

Preuve que c'est sans risque : l'arbre contient **déjà** les deux ordres sur le même fil. Les deux
surcharges de `JsonApiHandlerWS::sendJson()` émettent la même enveloppe dans deux ordres
différents — `msg, msg_id, data` par la voie jansson (`:63-73`), `data, msg, msg_id` par la voie
nlohmann (`:75-85`, utilisée par `eventlog`, `register_push`, `settings`). Les clients vivent déjà
avec les deux.

**Méthode imposée à tous les sous-tickets** :
1. `nlohmann::json::parse()` des deux côtés (golden et payload produit), comparaison par
   `operator==`. Les objets nlohmann étant des `std::map`, l'égalité est **insensible à l'ordre
   des clés** par construction. Rien à écrire de spécial pour ça.
2. **Les tableaux restent ordonnés** — c'est voulu : l'ordre des pièces, des IOs et des règles
   *est* sémantique (il pilote l'ordre d'évaluation, invariant de la série E4.2). Ne jamais trier
   un tableau avant comparaison.
3. **L'égalité nlohmann est stricte sur les types** (`"3" != 3`) : une migration qui « améliorerait »
   un nombre stringifié en nombre JSON casse le test. C'est exactement ce qu'on veut.
4. **Interdits explicites, à refuser en revue** : `EXPECT_EQ` sur une chaîne sérialisée,
   `EXPECT_EQ(j.dump(), golden)`, `EXPECT_EQ(jansson_to_string(x), "…")`, tout `assert` sur
   l'ordre des clés, toute comparaison de longueur de chaîne JSON.
5. **Diagnostic obligatoire** : en cas d'échec, l'assertion doit imprimer le **chemin du premier
   nœud divergent** (`/home/2/items/5/state`) avec attendu/obtenu. Un `EXPECT_EQ` brut sur un objet
   de 200 clés est inexploitable et rendra la migration insupportable.
6. Goldens stockés en **UTF-8 lisible** (`json.dump(2)`), un fichier par cas, versionnés. Le
   `JSON_ENSURE_ASCII` de jansson (tout non-ASCII sérialisé en échappement `\uXXXX`,
   `Jansson_Addition.h:115`,
   `JsonApiHandlerHttp.cpp:223`) contre l'UTF-8 brut de nlohmann est **dissous par le parsing** :
   rien à faire, mais un cas accentué doit exister pour le prouver.

## Preuve exigée : mutation, pas red-before-green

Ces tests s'ajoutent sur du code **inchangé** : il n'y a pas de « red » naturel. La preuve qu'un
test épingle réellement quelque chose est une **preuve par mutation** : perturber un champ dans le
builder de production (renommer une clé de `buildJsonIO`, changer un `type_str`), reconstruire,
constater le rouge, restaurer.

⚠️ **Piège méthodologique du projet** (FINDINGS.md:371-382, constaté 2×) : **27 occurrences** de
`<name>_DEPENDENCIES = $(top_builddir)/src/lib/libcalaos_common.la` dans `tests/Makefile.am`
(`:179, 234, 251, 290, 306, 320, 777, 1013`…) retirent **tous** les `.o` de
`src/bin/calaos_server/` des prérequis, si bien que **le binaire ne se relinke pas** quand un `.o`
de production change → la mutation est compilée mais **l'ancien binaire est réexécuté** et rend un
faux vert. Ce n'est pas théorique : les horodatages de l'arbre le montrent en flagrant délit
(cf. prérequis de build ci-dessus). Les binaires de cette série suivant la même convention, la
règle s'applique à tous :
**supprimer explicitement le `.o` de production ET le binaire de test, reconstruire, et vérifier
dans la sortie de `make` que la reconstruction a bien eu lieu** avant de conclure quoi que ce soit.
Un rapport de sous-ticket qui affirme une mutation rouge sans montrer ces deux suppressions et la
trace de relink est à **rejeter en revue**.

## Priorisation : **non, on ne teste pas tout** — et voici pourquoi, chiffré

L'exhaustivité stricte, c'est **97 couples (transport, opération)**. Elle n'est pas raisonnable, et
surtout elle n'apporterait presque rien sur son dernier tiers :

- **4 opérations n'ont aucun payload JSON** (réponses `image/jpeg`) → hors périmètre de fait ;
  seuls leurs chemins d'erreur JSON sont couverts (E4.0e). Plus **2 opérations base64**
  (`get_cover` de premier niveau, `get_camera_pic`) qui, elles, ont un payload JSON mais dont la
  mise en scène exige un téléchargement réel → également hors périmètre nominal, chemins d'erreur
  seuls (E4.0e).
- **`config/put`** réécrit les fichiers de configuration réels et déclenche un redémarrage → coût
  de mise en scène élevé, valeur de caractérisation faible. Hors périmètre.
- **Les 16 opérations `audio_db`** passent toutes par le **même** `processDbResult()`
  (`JsonApi.cpp:984-1006`) et produisent la **même forme**. Caractériser les 16 revient à
  caractériser 16 fois la même chose, au prix de 16 mises en scène de lecteur factice.
  → E4.0f caractérise `processDbResult()` **plus 3 représentants** : `get_albums`/`get_album`
  (la divergence HTTP/WS, épinglée **dans les deux sens** — chaque transport rejette l'orthographe
  de l'autre), `get_stats` (forme différente), `get_track_infos` (forme différente).

**Ce que la série livre réellement** : **36 des 56 opérations** entièrement caractérisées (64 %),
**18/18 types d'events poussés**, **100 % des chemins de dispatch et d'erreur** des deux
transports, et les deux enveloppes. Non caractérisées nominalement : **13** `audio_db`
redondantes, **4** réponses binaires, **2** réponses base64 (`get_cover` de premier niveau,
`get_camera_pic`), `config/put`. Recoupe : 56 − 13 − 4 − 2 − 1 = **36**.

**Si le budget doit être coupé**, l'ordre de valeur décroissante est :
**E4.0a → E4.0b → E4.0e → E4.0d → E4.0c → E4.0f.**
E4.0a+b+e (3 tickets) donnent déjà le filet qui compte : le payload que tout client lit, les deux
enveloppes, et le piège UTF-8 qui est le seul de la liste capable de faire **planter** le serveur
après migration.
