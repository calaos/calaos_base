## Findings

### Major — lifetime: pending-request futures leak on timeout / disconnect
`client.py:105` — `self._pending[msg_id] = fut` then `return await asyncio.wait_for(fut, timeout=10.0)`. Entries are popped only when a matching response arrives (`:84`); on `wait_for` timeout or a WS drop the entry (and future) is never removed and never resolved → unbounded `_pending` growth and hung callers. **Fix:** wrap the `wait_for` in `try/finally` that pops `self._pending[msg_id]`; on reconnect, fail all outstanding futures (`set_exception`) and clear the dict.

### Major — correctness: `_ready` not cleared on clean WS close
`client.py:47` — `_ready` is set on connect but not cleared on a clean close, so subsequent tool calls send on a dead socket. **Fix:** clear `_ready` in the close handler and reconnect/queue before sending.

### Major — edge-case: Roon `set_volume` dereferences `zones[zid]` before validating
`ExternProcRoon_main.py:195` — `outputs = self.roon_api.zones[zid].get("outputs")` runs *before* the guard `if zid and output_id and zid in self.roon_api.zones:` (`:200`). An unknown/missing `zone_id` raises `KeyError`/`TypeError`, which propagates out of `message_received` and **terminates the extern-proc run loop**. **Fix:** check `zid and zid in self.roon_api.zones` before indexing, mirroring the other action branches.

### Minor — correctness: Roon now-playing KeyError + leftover `print()`
`ExternProcRoon_main.py` — a `now_playing` access assumes the key exists and can raise inside the state callback; `:143,:151` also carry leftover `print()` debug. **Fix:** use `zone.get("now_playing", {})`; remove the `print()` statements.

### Minor — edge-case: numeric IO validation accepts inf/nan
`tools/io.py:28` — for `float/int/double` var types the check is only `float(value)` in try/except, so `'inf'`, `'-inf'`, `'nan'`, `'1e999'` all pass and the original string is forwarded to `set_state`. **Fix:** reject non-finite values (`math.isfinite`); for int types require an integral value before forwarding.

### Minor — edge-case: `mcp_rate_limit=0` bricks the sidecar
`config.py:74` — `_opt_int` returns `max(0, int(raw))`, and `auth.py` uses `if len(window) >= self._rate_limit`; `mcp_rate_limit=0` yields `rate_limit=0`, so every request returns 429 (unlike `ban_failures=0`, which legitimately disables banning). **Fix:** treat `rate_limit<=0` as "disabled" (skip the window check), or floor to a sane minimum.

## Acceptance
- Pending futures cannot leak on timeout/disconnect; reconnect fails them and clears the dict.
- A clean WS close prevents sends on a dead socket.
- Roon `set_volume` with an unknown zone does not crash the run loop.
- inf/nan rejected for numeric IOs; `mcp_rate_limit=0` does not block all traffic.

## Verification
`pytest`: future cleanup on simulated timeout/disconnect; Roon set_volume with a bad zone id keeps the loop alive; io.py rejects `nan`/`inf`; config `rate_limit=0` disables rather than blocks.
