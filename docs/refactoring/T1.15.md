# T1.15 — Lua sandbox + exec watchdog

| Phase | Type | Depends on | Status |
|---|---|---|---|
| 1 | fix (security) | Phase 0 | 📋 Backlog |

## Owned files
- `src/bin/calaos_server/LuaScript/` (`ScriptManager.{cpp,h}`, `ScriptBindings.{cpp,h}`, `ScriptExec.{cpp,h}`, `ScriptExtern_main.cpp`, `Lunar.h`)

## Findings

### Major — security: the Lua "sandbox" is absent
`ScriptManager.cpp:41` — scripts run with the full standard library open (`luaL_openlibs` / equivalent) — `os`, `io`, and (if built with luajit) `ffi` are all exposed to user-authored rule scripts. There is no allow-list or environment sandbox despite the subsystem being described as isolated. A rule script can run arbitrary shell commands / read-write the filesystem / load native code. **Fix:** restrict the script environment to the intended `calaos:*` API plus safe stdlib subset (remove/stub `os.execute`, `io`, `ffi`, `package.loadlib`, `dofile`, `loadfile`), matching the "isolated subprocess" contract.

### Major — correctness: the script execution-time watchdog is dead code
`ScriptBindings.cpp:97` — the intended time-based abort in the Lua debug hook (`time - start_time > SCRIPT_MAX_EXEC_TIME`) is fully **commented out** (`:96-104`); `LuaDebugHook` only checks an `abort` flag, and `ScriptManager::start_time` (`ScriptManager.cpp:60`) is written but never read. An infinite-loop script is never killed. **Fix:** re-enable a real time-based check in the line hook comparing `getMainLoopTime()` to `start_time` and `lua_error` past a bounded limit.

## Acceptance
- A rule script calling `os.execute`/`io.open`/`ffi` is denied (or those globals are absent).
- An infinite-loop script is aborted after the bounded time limit; the engine stays responsive.

## Verification
`make check`; a test script attempting `os.execute("...")` fails/denied; a `while true do end` script is killed within the watchdog window and the daemon continues.
