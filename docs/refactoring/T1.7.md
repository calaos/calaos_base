## Constat

### F1 — majeur : PRNG faible pour les tokens MCP
`McpServerManager::generateToken()` (`McpServerManager.cpp:46-54`) construit `mcp_token` et `mcp_service_token` en concaténant deux appels à `Utils::createRandomUuid()`. `createRandomUuid()` (`Utils.cpp:841-856`) fait `srand(t1.tv_usec * t1.tv_sec)` puis `rand()`. Deux problèmes cumulés :
1. `rand()` non cryptographique, seed uniquement horloge (le commentaire du code l'admet).
2. **Re-seed `srand()` à chaque appel**, et `generateToken()` appelle 2× de suite → si les deux appels tombent dans la même microseconde, les deux UUID sont identiques (token réduit à 128 bits d'un flux déjà faible) ; plus généralement les deux moitiés sont fortement corrélées.

Ces tokens gardent le proxy `/mcp` et la session service privilégiée `login_service` (capable de piloter `set_state`).

**Remédiation** : générer les tokens via OpenSSL `RAND_bytes` (déjà utilisé par `HMACAuthenticator`/provisioning). Si `createRandomUuid` doit rester ailleurs, seeder une seule fois au démarrage du process.

## Acceptance
- Les tokens MCP proviennent d'un CSPRNG (`RAND_bytes`), 256 bits d'entropie, sans re-seed par appel.
- Deux générations consécutives ne peuvent pas produire de moitiés identiques.

## Vérification
`make check` ; test unitaire : 1000 tokens générés, tous distincts, longueur/entropie attendue.
