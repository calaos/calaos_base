## Owned files
- `src/bin/calaos_server/McpServerManager.{cpp,h}`

## Findings

### F1 — major: weak PRNG for MCP tokens
`McpServerManager::generateToken()` (`McpServerManager.cpp:46-54`) builds `mcp_token` and `mcp_service_token` by concatenating two `Utils::createRandomUuid()` calls. `createRandomUuid()` (`Utils.cpp:841-856`) does `srand(t1.tv_usec * t1.tv_sec)` then `rand()`. Two combined problems:
1. `rand()` is not cryptographic and is seeded only from the clock (the code comment admits it).
2. **`srand()` is re-seeded on every call**, and `generateToken()` calls it twice back-to-back → if both calls fall in the same microsecond, the two UUIDs are identical (token reduced to 128 bits of an already weak stream); more generally the two halves are strongly correlated.

These tokens guard the `/mcp` proxy and the privileged `login_service` session (capable of driving `set_state`).

**Fix:** generate the tokens via OpenSSL `RAND_bytes` (already used by `HMACAuthenticator`/provisioning). If `createRandomUuid` must remain elsewhere, seed once at process start.

> The underlying `createRandomUuid` reseed is also fixed at the source by **T1.12** (owns `Utils.cpp` RNG). This ticket ensures the MCP tokens draw from a CSPRNG regardless.

## Acceptance
- MCP tokens come from a CSPRNG (`RAND_bytes`), 256 bits of entropy, no per-call reseed.
- Two consecutive generations cannot produce identical halves.

## Verification
`make check`; unit test: 1000 generated tokens, all distinct, expected length/entropy.
