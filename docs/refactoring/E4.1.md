# E4.1 — Bibliothèque JSON unique

| Phase | Type | Dépend de | Statut |
|---|---|---|---|
| 4 | epic | Phase 3 | 📋 Backlog |

## Portée
Épic transversal — **à découper en sous-tickets par module** avant exécution.

## Constat
Le codebase utilise **deux** bibliothèques JSON simultanément :
- `jansson` (`json_t`/`json_object`, ~23 fichiers) — requis par `configure.ac:52` (`jansson >= 2.5`).
- `nlohmann/json` (`json.hpp`, ~25 fichiers) — vendored (899 Ko).

Conséquences : deux API de (dé)sérialisation, surface doublée, binaire plus gros, context-switching permanent pour les mainteneurs.

## Remédiation (proposée)
- Converger sur **nlohmann/json** (déjà vendored, API moderne). Alternative : jansson partout — mais nlohmann est plus ergonomique.
- Découpage : un sous-ticket par sous-système (JsonApi, EventManager, drivers, config…), en migrant les `json_t*` vers `nlohmann::json` module par module, avec adaptateurs transitoires (`Jansson_Addition.h`/`Json_Addition.h` servent déjà de ponts).
- Retirer la dépendance `jansson` de `configure.ac` en fin de migration.

## Acceptance (epic)
- Une seule bibliothèque JSON dans le code applicatif.
- `jansson` retiré des dépendances de build.
- Aucune régression fonctionnelle de l'API JSON (port 5454) ni des events temps réel.

## Vérification
Tests d'intégration API JSON complets après chaque sous-ticket ; comparaison des payloads avant/après migration.

## ⛔ Prérequis dur : E4.0 (décision utilisateur, 2026-08-16)

> **Ce ticket ne démarre pas tant que E4.0 n'est pas livré.**

La version initiale de ce fichier annonçait « Prérequis : filet de tests solide (E4.3) sur
l'API JSON avant de démarrer ». **Ce prérequis était faussement satisfait** : E4.3 est bien
fermé en ✅ (40 binaires, 411 cas), mais sa couverture porte sur les règles, le XML corrompu,
le lifecycle IO, `WebSocketFrame`, `tcpsocket`, `ExternProc`, `Timer`, `base64`, `Calendar`,
`Params` et Lua — **`JsonApi` n'y figure pas**. La case était cochée pour un périmètre qui
n'est pas celui dont E4.1 a besoin.

L'utilisateur a tranché la méthode : **caractériser d'abord, migrer ensuite.** On écrit une
série de tests qui gèlent les entrées/sorties de l'API JSON **telle qu'elle est aujourd'hui**
(sous jansson), et la migration se fait sous ce filet. C'est l'objet de **E4.0**.

**Contrainte de comparaison** : les tests de caractérisation comparent les payloads
**sémantiquement** (arbre JSON parsé — structure et valeurs), **jamais octet à octet**.
L'ordre des clés change par décision assumée (`nlohmann::json` standard trie, jansson préserve
l'ordre d'insertion) ; un test byte-exact échouerait intégralement à la bascule pour une raison
déjà acceptée, et ne prouverait rien.
