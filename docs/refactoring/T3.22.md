# T3.22 — Dependabot : surveiller le sidecar pip, et grouper pour ne pas publier à chaque montée

> **Mise à jour 2026-08-24 — le prérequis F-DEP-1 est levé par [T3.23](T3.23.md)** (branche `fix/t3.23`) : `src/bin/calaos_mcp/pyproject.toml` est désormais **réellement installé** par les deux stages du `Dockerfile`, le devcontainer et la CI. Ce que Dependabot surveille est donc enfin ce qui est déployé — la stratégie `groups:` de ce ticket porte maintenant sur un fichier qui a un effet.

**Type** : cleanup / infra · **Phase** : 3
**Origine** : passage Dependabot du 2026-08-24 (voir le journal 🔁 REPRISE d'`ORCHESTRATION.md`).
**Statut** : 📋 backlog — **toujours pertinent** après le passage du 2026-08-24, et pour deux
raisons qui se sont vérifiées sur le terrain, pas seulement par principe.

## Pourquoi ce ticket n'est pas devenu inutile

`.github/dependabot.yml` ne déclare **qu'une** entrée : `npm` sur `/data/debug`, restreinte par
`allow: dependency-type: production` (justification en commentaire dans le fichier, posée par
T3.11). `src/bin/calaos_mcp/pyproject.toml` n'est déclaré **nulle part**. Les PR #174 et #175
n'existent que parce que GitHub a ouvert des *security updates* — un mécanisme distinct, piloté
par les alertes, qui ne s'appuie pas sur `dependabot.yml`.

Conséquence mesurée le 2026-08-24 : **10 des 12 alertes ouvertes** portaient sur `mcp` et
`starlette`, dépendances **d'exécution** du sidecar. Et surtout, les deux PR ouvertes par ce
mécanisme ont montré ses limites :

1. **#175 (`starlette` 0.46.2 → 1.3.1) était irrésoluble.** Les *security updates* montent le
   paquet vulnérable **en isolation**. Or `fastapi==0.115.12` exige `starlette>=0.40.0,<0.47.0` :
   le `pyproject.toml` résultant ne s'installe nulle part (`pip` : `ResolutionImpossible`). Il a
   fallu monter `fastapi` à `0.141.1` en même temps. Un *version update* régulier, avec un
   `group`, aurait proposé le jeu cohérent d'emblée.
2. **La CI n'a rien vu et ne pouvait rien voir.** `.github/workflows/ci.yml` n'a **aucune** étape
   Python, et rien dans le build ne résout jamais ce `pyproject.toml` (il n'est même pas dans
   l'`EXTRA_DIST` de `src/bin/calaos_mcp/Makefile.am` ; le `Makefile.am` installe les `.py`
   directement). Les deux PR étaient **vertes** — ce vert ne portait aucune information sur elles.

## Travail

1. **Ajouter l'entrée pip** à `.github/dependabot.yml` :

   ```yaml
     - package-ecosystem: "pip"
       directory: "/src/bin/calaos_mcp"
       schedule:
         interval: "monthly"
       open-pull-requests-limit: 2
       groups:
         mcp-sidecar:
           patterns: ["*"]
   ```

   Commenter la justification dans le fichier, en symétrie du bloc npm : le sidecar est le seul
   composant Python **d'exécution** de l'arbre, il traite du trafic HTTP authentifié, ses pins
   sont exacts (`==`) donc rien ne bouge sans PR.

2. **La stratégie de groupement est le cœur du ticket, pas un détail.** Sans `groups:`, chaque
   montée ouvre une PR, et **chaque merge dans `master` est une publication** :
   `.github/workflows/docker-publish-dev.yml` se déclenche sur tout push vers `master`, **sans
   `needs:` sur `build-and-test`** — il incrémente la version, crée un tag git, publie
   `ghcr.io/calaos/calaos_base:dev` + un tag versionné, et dispatche un `build_deb` vers
   `calaos/pkgdebs`. Six paquets pinnés × une PR chacun = six cycles de publication par mois.
   Un seul groupe `patterns: ["*"]` sur ce manifeste ramène ça à **une PR mensuelle**, qui a en
   prime le bon comportement technique : `mcp`, `starlette` et `fastapi` sont **couplés** (cf.
   #175), les monter ensemble est la seule façon d'obtenir un jeu résoluble.

   ⚠️ `groups:` ne s'applique **qu'aux** *version updates*. Les *security updates* continueront à
   ouvrir des PR isolées, potentiellement irrésolubles comme #175. Le groupement mensuel réduit
   leur fréquence (le manifeste reste à jour, donc moins d'alertes) mais ne les supprime pas :
   toute PR de sécurité pip doit rester **instruite à la main**, avec vérification de résolution.

3. **Envisager la même chose pour npm/`data/debug`** : `open-pull-requests-limit: 5` sans `groups:`
   peut produire jusqu'à 5 PR, donc 5 publications. Un groupe unique y a le même intérêt.

4. **Question ouverte à trancher dans le ticket** : faut-il aussi déclarer `docker` sur
   `/Dockerfile` ? Voir le finding F-DEP-1 de `FINDINGS.md` — les dépendances Python du sidecar
   y sont installées **non pinnées** (`pip install "mcp[cli]" uvicorn fastapi websockets`), donc
   le `pyproject.toml` que Dependabot surveille ne décrit **pas** ce qui est réellement déployé.
   Tant que ce décalage existe, surveiller `pyproject.toml` protège une fiction. **F-DEP-1 est un
   prérequis de fond à ce ticket** : le corriger d'abord donne du sens à la surveillance.

## Acceptation

- `.github/dependabot.yml` valide (l'onglet Insights → Dependency graph → Dependabot ne signale
  pas d'erreur de parsing) et liste le manifeste `src/bin/calaos_mcp/pyproject.toml`.
- La prochaine fenêtre mensuelle produit **une** PR pour le sidecar, pas une par paquet.
- La justification est écrite **dans le YAML**, en termes de chemin d'exposition et de coût de
  publication — pour que la décision se relise dans six mois sans refaire l'analyse.
