## Owned files

> Path note: `ListeRoom.{cpp,h}` are at the `calaos_server/` top level, **not** under `IO/`.

## Findings

### M6 — major: key/value swapped on the default name
`ListeRoom::createIO` (`ListeRoom.cpp:275`):
```cpp
if (!param.Exists("name")) param.Add("<No Name>", "Input");
```
The key and value are transposed: it adds a param **named** `"<No Name>"` with value `"Input"` instead of `name="<No Name>"`. IOs created without a name still have no `name` param. **Fix:** `param.Add("name", "<No Name>");`

### m9 — `EventIOAdded` emitted even when creation failed
`ListeRoom::createIO` (`ListeRoom.cpp:280-289`) guards `room->AddIO(io)` with `if (io)` but then emits `EventIOAdded` unconditionally → announces a non-existent IO. **Fix:** emit the event only when `io != nullptr`.

### m10 — duplicate ids silently overwritten
`addIOHash` (`ListeRoom.cpp:47-59`) does `io_table[id] = io` with no collision check → two IOs with the same id: the first becomes unreachable by id, `get_io_count()` undercounts, and `delIOHash` of one removes the shared entry. **Fix:** detect the collision, log via `cErrorDom("root")`, reject the duplicate (or suffix). Decide and document the behavior.

> The mutable-`id` re-hash problem (an IO whose `id` param is changed after insertion — `set_param` has no re-hash) is handled by **T1.11** (IOBase/IOFactory side); this ticket owns the `io_table` collision-on-insert path only.

## Acceptance

- Test: failed creation (`io==nullptr`) → no `EventIOAdded`.
- Test: a second IO with an existing id → logged and rejected, `io_table` consistent.
